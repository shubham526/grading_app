# v2.3.3 Design — Programming Submission & Autograding

**Release:** `v2.3.3 — Programming Submission & Autograding`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Date:** August 18, 2026  
**Depends on:** v2.3.2 Submission Core & Provenance Foundation  
**Primary initial language:** Python  
**Primary initial runner:** pytest

---

## 1. Purpose

v2.3.3 adds a first-class **Programming** assessment mode.

The instructor provides an autograder/test package. The app consumes canonical programming `Submission` records from v2.3.2, runs each student's code in an isolated execution environment, calculates deterministic scores, preserves detailed run evidence, supports manual review/adjustment, and exports reports.

This release deliberately does not implement Canvas. Local upload is sufficient because the input boundary is already source-agnostic.

Future Canvas ingestion will create the same canonical `Submission` records and therefore require no autograder redesign.

---

## 2. Product Boundary

The app is an instructor grading backend, not a student-facing coding platform.

Do build:

- programming assessment configuration;
- public/hidden tests;
- isolated execution;
- deterministic scoring;
- batch grading;
- logs;
- review/override;
- reruns;
- grader versioning;
- reports;
- audit history.

Do not build:

- student accounts;
- student submission website;
- online IDE;
- course LMS;
- automatic misconduct verdicts;
- Canvas API in this release;
- LLM code grading.

## 5. Input Contract From v2.3.2

v2.3.3 does **not** own submission identity or upload persistence.

It consumes:

```text
Submission
  submission_id
  student_id
  assessment_id
  attempt
  source_system
  artifacts[]
```

For the initial Python workflow, at least one artifact must satisfy the assignment's submission contract.

Example:

```text
artifact_type = python
role = primary
```

If a Canvas submission arrives later, v2.3.3 sees the same model.

## 8. `assignment.yaml`

Illustrative schema:

```yaml
schema_version: 1

assignment:
  id: lab3-programming
  name: "Lab 3 Programming"
  language: python
  max_points: 70

submission:
  required_files:
    - priority_queue.py

runner:
  type: pytest
  python_version: "3.12"
  timeout_seconds: 10
  memory_mb: 512
  network: false

environment:
  id: cs2580-python-v1
  requirements_file: requirements.txt

groups:
  - id: correctness
    name: "Basic Correctness"
    points: 30

  - id: edge_cases
    name: "Edge Cases"
    points: 20

  - id: efficiency
    name: "Efficiency"
    points: 15

  - id: interface
    name: "Interface / Constraints"
    points: 5

tests:
  mapping:
    - pattern: "tests/public/test_basic.py::*"
      group: correctness

    - pattern: "tests/hidden/test_edge_cases.py::*"
      group: edge_cases

    - pattern: "tests/hidden/test_efficiency.py::*"
      group: efficiency

    - pattern: "tests/public/test_interface.py::*"
      group: interface

scoring:
  method: weighted_tests
  allow_partial_group_credit: true

reporting:
  show_public_test_details: true
  show_hidden_test_names_to_students: false
```

## 9. Package Validation

Before activation, validate:

- supported schema;
- recognized language;
- recognized runner;
- unique group IDs;
- points sum correctly;
- required files are declared;
- test mappings reference valid groups;
- referenced tests exist;
- requirements file exists if declared;
- timeout/memory settings are valid;
- pytest collection succeeds;
- no duplicate/conflicting mappings;
- package is fingerprinted.

Invalid packages cannot become active.

---

## 10. Package Versioning

Once a package has produced grading runs, it is immutable.

Do not edit:

```text
Lab3-v1.0
```

in place.

Create:

```text
Lab3-v1.1
```

Store:

```text
autograder_package_id
display_version
package_sha256
manifest_sha256
tests_sha256
environment_id
created_at
created_by
is_active
```

## 11. Security Principle

Student code is untrusted.

It must never execute in:

- the GUI process;
- the main application interpreter;
- the host repository environment.

Execution must go through a dedicated backend.

---

## 12. Execution Backend

Conceptual interface:

```python
class ExecutionBackend:
    def prepare(self, run_spec):
        ...

    def execute(self, run_spec):
        ...

    def terminate(self, run_id):
        ...

    def cleanup(self, run_id):
        ...
```

Initial implementation:

```text
ContainerExecutionBackend
```

Possible future implementations:

```text
PodmanExecutionBackend
RemoteWorkerExecutionBackend
SlurmExecutionBackend
```

Grading semantics must not depend on backend choice.

---

## 13. Required Isolation Controls

At minimum:

- fresh workspace per run;
- fixed interpreter/runtime;
- instructor-defined dependencies only;
- no network;
- wall-clock timeout;
- process termination;
- stdout/stderr limits;
- no host credentials;
- no app database mount;
- no repository secrets;
- controlled writable directory;
- cleanup after execution.

Where backend supports it:

- non-root execution;
- memory cap;
- CPU cap;
- PID/process cap;
- dropped Linux capabilities;
- read-only root filesystem;
- seccomp/AppArmor profile.

The app should not claim stronger hostile-code isolation than its backend provides.

---

## 14. Dependency Policy

Allowed:

```text
instructor requirements.txt
prebuilt grading environment
```

Not automatically executed/installed:

```text
student requirements.txt
student setup.py
student pyproject hooks
student shell scripts
```

This keeps execution deterministic and reduces attack surface.

---

## 15. Environment Identity

Store:

```text
environment_id
container_image
container_image_digest
python_version
dependency_lock_hash
```

A friendly environment name is not sufficient for reproducibility.

## 16. Pytest Runner

The initial runner is Python + pytest.

It should request machine-readable output and normalize each test into:

```text
test_id
display_name
group_id
visibility
status
duration_ms
message
traceback
stdout
stderr
points_possible
points_awarded
```

Normalized test statuses:

```text
PASS
FAIL
ERROR
SKIP
XFAIL
XPASS
TIMEOUT
```

Do not scrape terminal output as the primary result format.

---

## 17. Stable Test Identity

Default stable identity:

```text
pytest node id
```

Example:

```text
tests/hidden/test_edge_cases.py::test_duplicate_priority
```

Support optional explicit stable IDs so moving a test between files does not destroy historical comparison.

## 18. Scoring

Recommended hierarchy:

```text
Assessment
  └── Group
       └── Test
```

Example:

```text
Basic Correctness       30
Edge Cases              20
Efficiency              15
Interface                5
TOTAL                   70
```

Initial deterministic policy:

```text
pass => assigned points
fail => 0 assigned points
```

Support either:

1. explicit test points; or
2. equal distribution within a weighted group.

The persisted schema should allow both even if the first UI ships with group-equal allocation.

## 20. Student Failure vs Grader Failure

This distinction is mandatory.

### Student result

Examples:

```text
AssertionError
student SyntaxError
student import failure
uncaught student exception
```

These may affect score according to policy.

### Grader/infrastructure failure

Examples:

```text
missing instructor test file
invalid grader package
container unavailable
grader dependency missing
result parser crash
```

These must not silently become student zeros.

Use:

```text
GRADER_ERROR
Score: not finalized
Requires review: yes
```

---

## 21. Timeout Policy

Default:

1. terminate run at wall-clock limit;
2. mark `TIMEOUT`;
3. preserve available logs;
4. preserve reliably completed test results;
5. uncompleted tests receive zero;
6. flag run for review.

This policy should be explicit in assessment configuration.

---

## 22. Output Limits

Capture:

```text
stdout
stderr
```

with configurable caps.

Example:

```text
1 MB each
```

If truncated:

```text
stdout_truncated = true
stderr_truncated = true
```

Infinite printing must not exhaust host storage.

## 24. Raw Score vs Final Score

Never destroy the raw result.

```text
raw_autograder_score = 65
manual_adjustment = +5
final_score = 70
```

Manual adjustment requires:

- reason;
- actor/reviewer;
- timestamp.

Prefer deriving final score from raw score + approved adjustments.

---

## 25. Review State

Keep execution and human review separate.

```text
execution_status = COMPLETED_WITH_FAILURES
review_status = UNREVIEWED
```

Review states:

```text
UNREVIEWED
FLAGGED
REVIEWED
APPROVED
```

This becomes important for Canvas publication later.

## 29. Queue and Concurrency

Batch execution must not freeze the UI.

Use a job queue/worker model.

Configure:

```text
max_parallel_runs
```

based on host resources.

Do not start unbounded containers.

Persist run creation before execution so crashes can be recovered as `INTERRUPTED`.

---

## 30. Cancellation

Support:

```text
Cancel Run
Cancel Remaining Batch
```

Cancellation terminates execution, preserves captured evidence, and does not finalize a score automatically.

---

## 31. Reruns

Two distinct actions:

### Re-run Exact Historical Configuration

```text
same submission
same autograder package
same environment digest
```

### Run With Current Grader

```text
same submission
new/current package
new designated environment
```

Never overwrite prior run records.

---

## 32. Grader Correction Comparison

If a test is wrong:

```text
Lab3-v1.0 -> Lab3-v1.1
```

Batch rerun can compare:

| Student | Old | New | Delta |
|---|---:|---:|---:|
| A | 60 | 65 | +5 |
| B | 70 | 70 | 0 |
| C | 55 | 60 | +5 |

v2.3.3 stores all data necessary for the dedicated v2.3.5 regrade workflow.

## 41. Minimum Acceptance Workflow

The release is operationally useful only if an instructor can:

1. open/create a programming assessment;
2. load a valid Python/pytest package;
3. import 20+ canonical `.py` submissions;
4. click `Run All`;
5. execute each in isolation;
6. get deterministic scores;
7. see test failures/errors/timeouts distinctly;
8. review flagged cases;
9. apply a documented manual adjustment;
10. rerun an exact submission;
11. export CSV and HTML;
12. restart the app without losing runs/results.

---

## 42. Acceptance Criteria

- [ ] programming assessment type exists;
- [ ] v2.3.2 canonical submissions are the only authoritative input;
- [ ] valid autograder packages can be uploaded/validated/versioned;
- [ ] student code never executes in the main app process;
- [ ] network is disabled by default;
- [ ] timeout enforcement works;
- [ ] output is capped;
- [ ] machine-readable per-test results persist;
- [ ] raw score is deterministic;
- [ ] student failures and grader failures are distinct;
- [ ] historical runs are immutable;
- [ ] manual adjustment preserves raw score;
- [ ] batch grading is non-blocking;
- [ ] exact rerun works;
- [ ] current-grader rerun works;
- [ ] instructor and student-safe reports exist;
- [ ] malicious/defective fixtures behave as expected;
- [ ] existing written grading and similarity still pass regression tests.

---

## 43. Release Blockers

Do not release if:

- arbitrary student code runs in-process;
- timeout cannot reliably terminate execution;
- grader failures can become student zeros silently;
- autograder packages are mutable after use;
- historical runs are overwritten;
- raw scores are destroyed by manual overrides;
- hidden test source is leaked in student-safe export;
- batch grading freezes the app;
- v2.3.2 submission provenance is bypassed.
