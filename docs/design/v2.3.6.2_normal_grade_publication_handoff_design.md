# v2.3.6.2 Design — Normal Grade Publication Handoff

**Release:** `v2.3.6.2 — Normal Grade Publication Handoff`
**Parent feature:** `v2.3.6 — Distributed CAM Integration & Grade Publication`
**Repository:** `grading_app`
**Status:** Definitive design specification
**Date:** August 21, 2026
**Depends on:** v2.3.6.1, v2.3.5, finalized grading records
**CAM counterpart:** CAM v0.7.1 normal grade publication
**Canvas access:** None
**Canvas write owner:** CAM

---

## 1. Purpose

v2.3.6.2 adds the missing ordinary grading path:

```text
Grading App
    ↓
finalized raw academic grades
    ↓
grade_publication_request
    ↓
distributed relay
    ↓
CAM
    ↓
authoritative policy + Canvas preflight
    ↓
guarded Canvas write
    ↓
reread / verification
    ↓
grade_publication_result
    ↓
distributed relay
    ↓
Grading App
```

This release does not publish to Canvas directly.

It publishes **academic intent to CAM**.

---

## 2. Core Principle

> **Finalizing a grade academically and publishing the policy-correct grade to Canvas are separate operations owned by different systems.**

The grading app owns:

```text
raw score
points possible
grading record/version
source submission/provenance
finalization
```

CAM owns:

```text
Canvas identity/mapping
current Canvas state
late-policy context
published target
Canvas write
verification
```

---

## 3. Goals

v2.3.6.2 shall support:

1. ordinary first-time finalized grade publication requests;
2. one-student publication;
3. selected-student publication;
4. full-ready-assessment batch publication;
5. explicit preview;
6. exclusion of unfinalized/flagged records;
7. immutable publication-request snapshots;
8. exact grading-record/version provenance;
9. durable local outbox;
10. relay transport through v2.3.6.1;
11. local queued/pending status;
12. CAM result ingestion;
13. mixed per-item outcomes;
14. retry-safe/idempotent request handling;
15. stale local grade detection before request creation;
16. no late-policy calculation;
17. no direct Canvas call;
18. no direct Canvas token;
19. no automatic publication immediately upon grading;
20. preservation of v2.3.5 regrade publication behavior.

---

## 4. Non-Goals

v2.3.6.2 shall not:

- download Canvas submissions;
- synchronize Canvas roster;
- map Canvas assignments directly;
- query Canvas state;
- calculate late penalties;
- inspect late-day balances;
- decide excused/absence policy;
- publish Canvas comments;
- publish rubric assessments;
- change Canvas posting policy;
- publish unreviewed autograder output;
- implement systematic corrections;
- silently republish a newer academic record under an older request;
- treat Canvas published score as academic raw truth.

Score publication only is required in this release.

Feedback/rubric publication is explicitly deferred.

## 6. Publication Is Not Automatic

Finalizing a grading record does not immediately publish it.

Required sequence:

```text
grade/finalize
→ prepare publication
→ review selection
→ confirm Send to CAM
```

This protects against accidental batch publication and keeps academic grading separate from operational synchronization.

## 7. Publishable Academic Record

Conceptual normalized source:

```python
@dataclass
class PublishableAcademicGrade:
    student_id: str
    assessment_id: str

    grading_record_id: str
    grading_record_version: int

    submission_id: str | None
    submission_attempt: int | None

    raw_score: float
    points_possible: float

    finalized: bool
    finalized_at: str | None
    finalized_by: str | None

    blocking_flags: list[str]
```

Only current authoritative local grading records are eligible.

---

## 8. Eligibility Rules

Default eligible:

```text
FINALIZED
no blocking grading error
raw score valid
points possible valid
current grading_record_version known
student identity known
assessment identity known
```

Default ineligible:

```text
UNREVIEWED
DRAFT
FLAGGED
GRADER_ERROR
NO_LOCAL_GRADE
INVALID_SCORE
STALE_RECORD
```

The app should exclude ineligible rows from batch publication by default.

CAM still independently validates its own required mappings/policy state.

---

## 9. No Canvas Mapping Requirement in Grading App

The grading app does not need:

```text
canvas_user_id
canvas_assignment_id
canvas_course_id
```

to create a valid publication request.

It sends stable local/course workflow identity.

CAM resolves Canvas mappings.

If CAM cannot resolve a mapping:

```text
status = blocked
```

with an operational error/result.

This avoids duplicating Canvas mapping infrastructure.

---

## 10. `grade_publication_request`

The Grading App mirrors the CAM v0.7.1 external contract.

Definitive Grading App-side shape:

```json
{
  "schema_version": 1,
  "event_type": "grade_publication_request",

  "publication_request_id": "gpr_01XYZ",
  "publication_version": 1,

  "course": "CS2500",
  "assessment": "PS2",

  "reason_type": "initial_grading",

  "created_at": "2026-09-15T18:42:00Z",
  "created_by": "grading_app",

  "grades": [
    {
      "student_id": "abc123",
      "grading_record_id": "gr_01AAA",
      "grading_record_version": 4,
      "raw_score": 90.0,
      "points_possible": 100.0,
      "finalized": true
    }
  ]
}
```

The CAM and Grading App implementations must freeze and test the same schema before release.

---

## 11. Event Identity

Logical batch identity:

```text
publication_request_id + publication_version
```

Recommended ID:

```text
gpr_<uuid>
```

Each item is correlated by:

```text
student_id
grading_record_id
grading_record_version
```

One assessment batch should not contain two active rows for the same student/grading record.

---

## 12. Publication Version Semantics

`publication_version` is a transport/request version.

It is not:

```text
grading_record_version
decision_version
case_version
external regrade version
```

A newer academic grading record should normally create a new publication request rather than silently mutate an already-emitted request.

If a request payload itself must be corrected before processing, preserve the old version and emit a new explicit `publication_version`.

Never rewrite an emitted request in place.

---

## 13. Reason Type

v2.3.6.2 produces:

```text
reason_type = initial_grading
```

Reserved for future releases:

```text
systematic_correction
manual_adjustment
```

Regrades continue to use the v2.3.5 `ApprovedGradeChange` / `regrade_decision` flow.

Do not duplicate regrade publication through normal-grade batch requests.

---

## 14. Immutable Request Snapshot

On confirmation, persist:

```text
publication_request_id
publication_version
course
assessment
created_at
created_by

for each item:
    student_id
    grading_record_id
    grading_record_version
    raw_score
    points_possible
    finalized state
```

After persistence, the request is immutable.

Later changes to academic grading create new academic history and, if needed, a new publication request.

## 16. Durable Outbox

Request confirmation transaction:

```text
validate selected records
→ snapshot immutable request
→ persist request/items
→ append audit
→ create durable outbound event
→ return success to user
→ attempt bridge/relay delivery asynchronously
```

If relay unavailable:

```text
Publication request = QUEUED LOCALLY
Transport = PENDING
```

No data is lost.

---

## 17. Local Transport Status vs Publication Status

Do not conflate:

### Transport

```text
PENDING
DELIVERED_TO_LOCAL_BRIDGE
DELIVERED_TO_RELAY
TRANSPORT_ERROR
```

### CAM/Canvas publication

```text
queued
awaiting_policy
synced
already_synced
conflict
blocked
failed
not_required
```

`DELIVERED_TO_RELAY` does not mean Canvas changed.

---

## 18. Late-Policy Boundary

The grading app never computes the Canvas target.

Example:

```text
Grading App:
raw = 90

CAM:
Canvas submission = late
authoritative policy = 20% penalty
target = 72

Canvas:
verified = 72
```

The Grading App stores:

```text
academic raw = 90
CAM published = 72
```

without modifying raw academic truth.

---

## 19. Unresolved Late Policy

If CAM reports:

```text
awaiting_policy
```

the grading app displays:

```text
Academic grade: Finalized
Raw score: 90 / 100

Canvas publication:
Awaiting course-policy resolution
```

Do not mark publication failed merely because CAM is waiting for authoritative late-day context.

Do not attempt to calculate the missing context locally.

## 20. CAM Publication Result Contract

CAM returns:

```json
{
  "schema_version": 1,
  "event_type": "grade_publication_result",

  "publication_request_id": "gpr_01XYZ",
  "publication_version": 1,

  "course": "CS2500",
  "assessment": "PS2",

  "completed_at": "2026-09-15T19:02:00Z",

  "items": [
    {
      "student_id": "abc123",
      "grading_record_id": "gr_01AAA",

      "status": "synced",

      "raw_score": 90.0,
      "published_score": 72.0,

      "late_policy_state": "penalty_applied",
      "late_penalty_percent": 20.0,

      "previous_canvas_score": null,
      "verified_canvas_score": 72.0,

      "error": null
    }
  ]
}
```

The exact schema must match CAM v0.7.1 tests.

---

## 21. Result Validation

Before applying a result locally:

- validate schema;
- validate `publication_request_id`;
- validate `publication_version`;
- validate course/assessment correlation;
- validate each `grading_record_id`;
- ensure item belongs to the immutable request;
- validate returned raw score matches request snapshot;
- reject conflicting same-result identity;
- exact replay no-op.

A result must never be applied to a different or newer grading record merely because student/assessment names match.

---

## 22. Result Statuses

Required operational statuses:

```text
queued
awaiting_policy
synced
already_synced
conflict
blocked
failed
not_required
```

Interpretation:

### `queued`

CAM accepted but has not completed publication.

### `awaiting_policy`

CAM cannot safely compute target yet.

### `synced`

CAM wrote/reread/verified the intended target.

### `already_synced`

Canvas already equaled intended target; no new effective write required.

### `conflict`

Canvas state changed unexpectedly; CAM did not blindly overwrite.

### `blocked`

Required mapping/data/eligibility failed.

### `failed`

Operational attempt failed.

### `not_required`

No Canvas mutation required.

---

## 23. Batch Independence

One student's outcome must not define the whole batch.

Example:

```text
60 requested

54 synced
2 already_synced
1 awaiting_policy
1 conflict
1 blocked
1 failed
```

The UI must preserve each terminal/non-terminal item separately.

Successful items must not be blindly resent when retrying failed ones.

## 26. No False Success

Do not display `Synced` merely because:

```text
request queued
relay upload succeeded
CAM accepted event
Canvas write call returned
```

`Synced` is accepted only from CAM's verified result contract.

---

## 27. Academic Record Changes After Request

Suppose:

```text
request snapshot:
grading_record_id = gr_A
version = 4
raw = 90

later local grading:
same record evolves to version 5
raw = 92
```

The original request remains historical:

```text
requested raw = 90 from v4
```

It must not silently become 92.

The UI marks the older publication request:

```text
ACADEMIC RECORD ADVANCED
```

If 92 should be published, create a new publication request from v5.

---

## 28. Regrade Compatibility

v2.3.6.2 does not replace v2.3.5 regrade handoff.

Regrade:

```text
RegradeDecision
    contains ApprovedGradeChange
        reason_type = regrade
```

Normal grading:

```text
GradePublicationRequest
    reason_type = initial_grading
```

Both eventually use CAM's guarded Canvas publication machinery, but the Grading App academic events remain distinct.

---

## 29. Autograder Compatibility

A programming grade may be published only after the local grading policy marks the authoritative grading record finalized.

Do not send raw test-run output before instructor/TA review requirements are satisfied.

Publication references the authoritative grading record, not an arbitrary `GradingRun` score.

Audit may link the grading record back to the `GradingRun`.

---

## 30. Written Grading Compatibility

Written/question-centric grading publishes the finalized assessment raw total.

Question/criterion detail remains local academic evidence.

v2.3.6.2 does not publish detailed Canvas rubric state.

---

## 31. Retry Model

### Transport retry

Same logical event.

No new publication request.

### CAM `failed`

User may prepare a new retry action if CAM classifies it retryable.

Prefer resubmitting the same immutable request identity only when CAM's protocol explicitly supports retry of that logical request.

### Academic grade changed

Create new request from new grading-record version.

Never use operational retry to smuggle in changed academic data.

---

## 32. Idempotency

Repeated request delivery must not create duplicate logical publication.

Repeated CAM result delivery must not duplicate history or mutate academic score.

Stable correlation:

```text
publication_request_id + publication_version
student_id + grading_record_id + grading_record_version
```

## 40. Release Blockers

Do not release if:

- Grading App needs Canvas credentials;
- Grading App calculates late policy;
- unfinalized grades can be published;
- request does not capture exact grading-record version;
- emitted request can mutate in place;
- same request replay duplicates effective publication;
- result can apply to wrong grading record;
- policy-adjusted Canvas score overwrites local raw score;
- one failed item causes successful batch items to be resent blindly;
- `synced` can be inferred without CAM verification result;
- publication conflict rolls back academic truth;
- regrade publication behavior regresses.

## 42. Resulting v2.3.6.2 Contract

After v2.3.6.2:

```text
A TA can finalize ordinary grades in the Grading App and submit
selected/batch grades for Canvas publication without Canvas credentials.

The Grading App sends immutable raw academic grade snapshots to CAM.

The Linux relay makes publication asynchronous across separate Macs.

CAM resolves Canvas identity and authoritative course policy,
calculates the correct Canvas target, performs guarded writes,
rereads/verifies Canvas, and returns per-item results.

The Grading App preserves raw academic truth and displays CAM's
operational publication outcome separately.

A raw 90 and verified Canvas 72 can be simultaneously correct.

v2.3.6.3 adds richer publication reconciliation and audit UX.
```
