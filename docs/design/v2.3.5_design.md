# v2.3.4 Design — Structured Regrade Request Workflow

**Release:** `v2.3.4 — Structured Regrade Request Workflow`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Application scope:** Problem Sets and Exams only  
**Depends on:** v2.1 question-centric grading, v2.3.3 ABET evidence model  
**Primary users:** Instructor / grader  
**Student submission model for v2.3.4:** Structured external form/CSV import

## 1. Purpose

v2.3.4 adds a structured regrade-request workflow to the grading app.

The goal is to replace ad hoc regrade handling through email, handwritten notes, or manually edited grades with a question- and criterion-aware process that:

- links every request to the exact student, assessment, question, and rubric criterion,
- preserves the original grade and feedback,
- records the student's stated reason,
- supports instructor/TA adjudication,
- updates grades only through an explicit decision,
- preserves a complete audit history,
- integrates with the question-centric grading workflow,
- and handles ABET-counted criteria safely.

The central design principle is:

> **A regrade is not an overwrite. It is an auditable revision to an existing grading record.**

## 2. Scope

### 2.1 In scope

v2.3.4 shall support regrade requests for:

```text
Problem Sets
Exams
```

It shall support:

1. Structured request import.
2. Validation against existing graded assessments.
3. Stable request IDs.
4. Question-level requests.
5. Criterion-level requests.
6. Request-type classification.
7. Original-grade snapshots.
8. Instructor/TA review.
9. Approve / partially approve / deny decisions.
10. Optional score increases or decreases.
11. Reviewer comments.
12. Append-only audit history.
13. Question-centric grading integration.
14. Regrade queue UI.
15. Filtering by assessment/question/criterion/status.
16. ABET-aware regrade handling.
17. Instructor-initiated systematic corrections.
18. Exportable regrade reports.
19. Regrade analytics.
20. Synthetic acceptance fixtures and regression tests.

### 2.2 Out of scope

v2.3.4 shall not:

- create a hosted student web portal,
- manage authentication,
- send email automatically,
- integrate directly with Canvas regrade forms,
- create Canvas grade changes,
- allow students to edit grading-app data directly,
- automatically approve or deny requests,
- use an LLM to adjudicate requests,
- silently alter grades,
- silently alter ABET ratings,
- replace the existing grading workflow,
- manage regrade requests for Knowledge Checks or Workshops.

## 3. Student Submission Model

For v2.3.4, students should submit regrade requests through a structured external form.

Possible front ends:

```text
Canvas form
Microsoft Form
Google Form
department-provided web form
```

The grading app consumes a normalized CSV export.

The app does **not** depend on a specific external form provider.

## 4. Student Regrade Request Contract

A student request should identify a specific alleged grading error.

Minimum required fields:

```text
student_id
assessment_id
question_id
request_type
student_reason
submitted_at
```

Criterion-level requests should additionally include:

```text
criterion_id
```

Optional fields:

```text
current_score_claimed
requested_score
page_reference
line_reference
supporting_reference
student_attachment_reference
```

### 4.1 Recommended request types

```text
arithmetic_error
score_entry_error
rubric_misapplied
correct_approach_not_recognized
feedback_mismatch
other_specific_grading_error
```

Avoid a generic `please_give_more_points` category.

### 4.2 Student-facing policy text

Recommended form language:

> Identify a specific grading error and explain why the rubric, reference solution, or grading criteria support your request. Requests that only ask for additional points without identifying an error may be denied without re-evaluation.

If course policy allows scores to decrease:

> Regrading reopens the requested question/criterion. The score may increase, remain unchanged, or decrease if a grading error is discovered during review.

The software must support either policy.

## 5. Regrade Request Data Model

Introduce:

```python
@dataclass
class RegradeRequest:
    request_id: str
    student_id: str
    assessment_id: str
    question_id: str
    criterion_ids: list[str]
    request_type: str
    student_reason: str
    submitted_at: str

    status: str
    current_score_claimed: float | None = None
    requested_score: float | None = None
    page_reference: str | None = None
    supporting_reference: str | None = None

    imported_at: str | None = None
    source_batch_id: str | None = None
```

Recommended statuses:

```text
submitted
under_review
needs_information
approved
partially_approved
denied
withdrawn
invalid
```

## 6. Stable Request IDs

Requests need stable identifiers independent of row order.

Recommended format:

```text
RG-<semester>-<assessment>-<student>-<question>-<sequence>
```

Example:

```text
RG-F2026-PS3-12345678-Q4-001
```

If the external form already produces a stable unique ID, preserve it.

Do not use student display names as the sole identifier.

## 7. Regrade State Machine

Recommended workflow:

```text
submitted
    ↓
under_review
    ├── needs_information
    │       ↓
    │   under_review
    │
    ├── approved
    ├── partially_approved
    ├── denied
    └── withdrawn
```

Invalid imported requests may enter `invalid`, but should never silently disappear.

## 8. Import Format

Recommended CSV schema:

```text
request_id
student_id
assessment_id
question_id
criterion_id
request_type
student_reason
submitted_at
current_score_claimed
requested_score
page_reference
supporting_reference
```

Multiple criterion IDs may use a delimiter or separate rows sharing one request ID.

Preferred v2.3.4 behavior:

```text
one request_id
one question
one or more criteria
```

Avoid allowing one request to span unrelated questions.

## 9. Import Validation

Each imported request must be validated against existing grading data.

Validate:

- request ID is unique,
- student exists,
- assessment exists,
- graded assessment exists for that student,
- question exists,
- criterion exists if supplied,
- criterion belongs to the requested question,
- current grade can be resolved,
- request is not an exact duplicate,
- request is within deadline or explicitly overridden,
- request type is supported,
- required explanation is non-empty.

Possible validation errors:

```text
UNKNOWN_STUDENT
UNKNOWN_ASSESSMENT
ASSESSMENT_NOT_GRADED
UNKNOWN_QUESTION
UNKNOWN_CRITERION
CRITERION_QUESTION_MISMATCH
DUPLICATE_REQUEST_ID
DUPLICATE_REQUEST_CONTENT
MISSING_REASON
LATE_REQUEST
MALFORMED_TIMESTAMP
```

Invalid requests should appear in a dedicated `Needs Attention` view.

## 10. Regrade Deadline Model

Each assessment may define:

```json
{
  "regrade_policy": {
    "enabled": true,
    "window_days": 7,
    "allow_score_decrease": true
  }
}
```

or explicit timestamps:

```json
{
  "regrade_policy": {
    "enabled": true,
    "opens_at": "2026-10-08T08:00:00-05:00",
    "closes_at": "2026-10-15T23:59:59-05:00",
    "allow_score_decrease": true
  }
}
```

Instructor override must remain possible, and override actions must be logged.

## 11. Original Grade Snapshot

Before adjudication begins, the system must snapshot the relevant original grading state.

For each affected criterion preserve:

```text
criterion_id
points_awarded
points_possible
feedback
selected/counting status
ABET result if applicable
```

Example:

```json
{
  "original_snapshot": {
    "question_id": "Q4",
    "criteria": [
      {
        "criterion_id": "PS3_Q4_PROOF_LOGIC",
        "points_awarded": 5,
        "points_possible": 8,
        "feedback": "The inductive step is incomplete."
      }
    ],
    "question_total": {
      "awarded": 7,
      "possible": 10
    }
  }
}
```

This snapshot is immutable.

## 12. Append-Only Regrade Audit Log

Every important action should create an event.

Recommended structure:

```json
{
  "events": [
    {
      "event_type": "request_imported",
      "timestamp": "...",
      "actor": "system"
    },
    {
      "event_type": "review_started",
      "timestamp": "...",
      "actor": "instructor_id"
    },
    {
      "event_type": "criterion_score_changed",
      "criterion_id": "PS3_Q4_PROOF_LOGIC",
      "old_value": 5,
      "new_value": 7,
      "timestamp": "...",
      "actor": "instructor_id"
    },
    {
      "event_type": "request_resolved",
      "decision": "partially_approved",
      "timestamp": "...",
      "actor": "instructor_id"
    }
  ]
}
```

Do not edit or delete prior events during normal operation. Corrections should create new events.

## 13. Regrade Decision Model

```python
@dataclass
class RegradeDecision:
    request_id: str
    decision: str
    reviewer_id: str
    reviewed_at: str
    reviewer_reason: str
    criterion_changes: list[CriterionRegradeChange]
```

Criterion change:

```python
@dataclass
class CriterionRegradeChange:
    criterion_id: str
    old_points: float
    new_points: float
    old_feedback: str | None
    new_feedback: str | None
```

Allowed decisions:

```text
approved
partially_approved
denied
```

A denied request should normally have no grade change.

## 14. Score Decrease Policy

The engine must support:

```text
allow_score_decrease = true | false
```

If false, `new_points < old_points` is blocked unless an instructor explicitly overrides policy with a logged reason.

If true, decreases are allowed but require explicit confirmation.

Opening a request must never by itself decrease a grade.

## 17. Question-Centric Grading Integration

In question-centric grading, add a regrade indicator:

```text
Alice    8/10

```

Selecting the indicator opens the request.

Useful filters:

```text

```

## 18. Criterion-Level Regrade Behavior

A request may target a whole question or a specific criterion.

If only a question is supplied, the reviewer may select one or more affected criteria during review.

If a criterion ID is supplied, the app should focus that criterion automatically.

## 19. ABET-Aware Regrades

This behavior is mandatory after v2.3.3.

If a regrade touches a criterion where:

```text
abet_counted == true
```

the app must not automatically infer a new ABET performance level from the new point score.

Example:

```text
Before:
course score   5 / 6
ABET level     Adequate

After regrade:
course score   6 / 6
```

The UI must show:

```text
This criterion is official ABET evidence.

Course score changed:
5 / 6 → 6 / 6

Current ABET rating:
Adequate

Review ABET rating before resolving this request.
```

The reviewer may keep or change the rating explicitly.

### 19.1 ABET audit record

If ABET rating changes, log:

```text
old performance level
new performance level
reviewer
timestamp
reason
```

### 19.2 Evidence status

A regrade may also change an evidence state such as:

```text
missing → valid
```

Such changes must be audited.

## 20. Grade Recalculation

After a criterion score changes:

```text
criterion total
    ↓
question total
    ↓
assessment total
    ↓
course-grade-facing assessment output
```

must be recalculated through the canonical grading engine.

The regrade subsystem must not implement a second independent grade calculator.

## 21. Regrade Result Persistence

The student's current saved assessment should reflect the final accepted score while preserving regrade history.

Example summary:

```json
{
  "regrade_summary": {
    "has_regrade_history": true,
    "request_ids": [
      "RG-F2026-PS3-12345678-Q4-001"
    ],
    "original_total_awarded": 82,
    "current_total_awarded": 84
  }
}
```

Detailed event history should live in dedicated regrade storage rather than being duplicated into every saved assessment.

## 22. Dedicated Regrade Storage

Recommended layout:

```text
<assessment>/
  assessments/
  regrades/
    requests.jsonl
    decisions.jsonl
    audit.jsonl
```

or one file per request:

```text
regrades/
  RG-F2026-PS3-12345678-Q4-001.json
```

The storage design should prioritize auditability, portability, easy backup, and no external database requirement.

## 23. Multiple Requests from One Student

Support:

```text
same student + same assessment + different questions
```

Recommended default:

- one open request per student × assessment × question,
- a later request is allowed only after the prior one is resolved,
- instructor override is possible and logged.

## 24. Withdrawal

If a student withdraws a request, preserve it with:

```text
status = withdrawn
```

Do not delete the record.

## 25. Needs Information

Optional state:

```text
needs_information
```

Store:

```text
reviewer_question
requested_at
student_response
response_at
```

v2.3.4 does not need automatic messaging; the app can export or copy the clarification request.

## 26. Instructor-Initiated Systematic Corrections

A systematic grading issue is distinct from an individual regrade request.

Introduce:

```text
GradeCorrectionBatch
```

Example:

```text
Exam 1 Q3 recurrence criterion was scored too strictly.
```

Possible model:

```python
@dataclass
class GradeCorrectionBatch:
    correction_id: str
    assessment_id: str
    question_id: str
    criterion_id: str
    reason: str
    affected_students: list[str]
    created_by: str
    created_at: str
```

Every individual change still creates an audit event.

## 27. Batch Correction Safety

Do not support blind `+2 points to everyone` without previewing the affected student/criterion set.

Before applying, show the proposed before/after values and require explicit confirmation.

If the criterion is ABET-counted, ABET ratings are reviewed under the same rule as individual regrades.

The app should generate a clean decision summary:

```text

...
```

This can be copied into Canvas manually or exported.

## 31. Privacy and Security

Regrade records are educational records and should be handled like grading data.

Requirements:

- store locally with assessment evidence,
- avoid public paths,
- minimize unnecessary student data,
- use stable student IDs,
- preserve reviewer identity where configured,
- do not log secrets or tokens,
- sanitize imported values before HTML rendering,
- never execute student-provided content.

## 32. Conflict / Concurrency Handling

If the assessment changed after request import but before review, detect the mismatch.

Example:

```text
⚠ Grade changed after request import.

Request snapshot:
5 / 8

Current grading record:
6 / 8
```

Reviewer must choose whether to refresh, continue against the original snapshot, or cancel review. The choice is logged.

## 33. Idempotency

Re-importing the same CSV must not duplicate requests.

Use `request_id` as the primary idempotency key.

If a request ID already exists:

- identical content → skip safely,
- conflicting content → flag conflict,
- never silently replace.

## 34. Undo / Correction Model

A resolved regrade should not be deleted.

If the reviewer made an error, create a correction event:

```text
decision_corrected
old final score: 7
new final score: 6
reason: arithmetic mistake during regrade
```

History remains reconstructible.

## 38. Regrade Policy Configuration

Recommended assessment-level policy:

```json
{
  "regrade_policy": {
    "enabled": true,
    "window_days": 7,

```

## 39. Validation Before Resolution

The Resolve action should be blocked until requirements are satisfied.

For approved/partially approved requests:

- reviewer reason exists,
- proposed criterion scores are valid,
- totals recalculate successfully,
- ABET-counted changed criteria have explicit ABET review,
- no unresolved concurrency conflict exists.

For denied requests:

- reviewer reason exists,
- no unintended score changes remain pending.

## 40. Audit Invariants

Enforce:

1. Original snapshot is immutable.
2. Every grade change has actor and timestamp.
3. Every grade change references a request or correction batch.
4. Every resolved request has a decision.
5. Every approved/partial request has a reviewer reason.
6. Every ABET change preserves before/after values.
7. Current assessment state can be reconciled with event history.
8. Duplicate request IDs cannot silently overwrite records.

## 41. Backward Compatibility

Existing graded assessments without regrade metadata continue to load.

Default:

```text
has_regrade_history = false
```

Do not rewrite all historical assessments merely to add empty regrade fields.

## 43. Testing Strategy

All automated tests must be offline.

### 43.1 Model tests

Test valid/invalid requests, state transitions, stable IDs, decision models, and criterion-change models.

### 43.2 Import tests

Test valid CSV, duplicate IDs, malformed rows, unknown student/assessment/question/criterion, criterion-question mismatch, late requests, and missing explanations.

### 43.3 Engine tests

Test approve with score increase, partial approval, denial, score decrease allowed/blocked, recalculation, and idempotent application.

### 43.4 Audit tests

Test snapshot immutability, append-only events, before/after values, correction events, and reviewer identity.

### 43.5 ABET tests

Test non-ABET regrades, ABET-counted score changes with rating unchanged, explicit ABET rating changes, evidence-status changes, and resolution blocking until ABET review is complete.

### 43.6 Concurrency tests

Test unchanged current grade, grade changed after import, stale snapshot warning, and explicit conflict resolution.

### 43.7 UI tests

Test queue filtering, request opening, original submission/grading visibility, decision controls, status changes, ABET warning, and resizable layout.

### 43.8 Export tests

Test request CSV, criterion-change CSV, summary report, and decision record.

## 48. Resulting Instructor Workflow

### Student request

```text
student submits structured form
    ↓
CSV export
    ↓
grading app import
    ↓
request validation
    ↓
Regrade Queue
```

### Review

```text
open request
    ↓
student explanation
+ original submission
+ original grading
    ↓
review affected criterion
    ↓
approve / partial / deny
```

### Resolution

```text
update criterion score if needed
    ↓
review ABET rating if applicable
    ↓
recalculate assessment
    ↓
append audit event
    ↓
resolve request
```

### End-of-assessment reporting

```text
regrade summary
request outcomes
point changes
criterion/question patterns
audit export
```

The intended end state is that regrade handling becomes a structured extension of normal grading rather than a disconnected collection of emails and manual grade edits.
