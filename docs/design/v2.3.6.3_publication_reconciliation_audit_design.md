# v2.3.6.3 Design — Publication Reconciliation & Audit

**Release:** `v2.3.6.3 — Publication Reconciliation & Audit`
**Parent feature:** `v2.3.6 — Distributed CAM Integration & Grade Publication`
**Repository:** `grading_app`
**Status:** Definitive design specification
**Date:** August 21, 2026
**Depends on:** v2.3.6.2, v2.3.6.1, v2.3.5
**CAM counterpart:** CAM v0.7.1 publication planning/results/conflicts
**Direct Canvas access:** None
**Completion meaning:** Grading App side of distributed publication is operationally explainable and auditable

---

## 1. Purpose

v2.3.6.3 makes CAM-mediated publication easy to reason about after requests and results begin accumulating.

It replaces the old direct-Canvas reconciliation assumption.

The old model:

```text
baseline Canvas
vs
local app grade
vs
current Canvas
```

is not valid when CAM applies policy adjustments.

The new model distinguishes:

```text
L = current local raw academic state
R = immutable raw academic state that was requested for publication
T = CAM-computed policy-correct Canvas target
C = CAM-verified Canvas state
```

The central principle:

> **Academic divergence and operational publication divergence are different things.**

---

## 2. Why the Old Raw-vs-Canvas Model Is Wrong

Example:

```text
L raw academic = 90
Settled late penalty = 20%
T CAM target = 72
C Canvas verified = 72
```

This is fully synchronized operationally.

Therefore:

```text
L != C
```

is not sufficient to classify a conflict.

v2.3.6.3 must never encourage the TA to "fix" Canvas from 72 to 90 merely because the raw academic record is 90.

---

## 3. Goals

v2.3.6.3 shall:

1. display publication history per assessment/student;
2. correlate each request to exact grading record/version;
3. correlate each result to its request;
4. distinguish academic freshness from Canvas publication convergence;
5. detect publication requests made from stale academic versions;
6. display CAM expected/published/verified values;
7. display late-policy explanation returned by CAM;
8. represent conflict/blocked/failed/awaiting-policy separately;
9. preserve mixed batch outcomes;
10. provide safe issue-resolution actions;
11. prevent false raw-vs-Canvas conflicts;
12. preserve append-only publication audit history;
13. cross-link regrade-driven and initial-grade publication history;
14. export publication/audit reports;
15. avoid any direct Canvas call.

---

## 4. Non-Goals

v2.3.6.3 shall not:

- fetch current Canvas state directly;
- build a Grading App Canvas client;
- store Canvas credentials;
- calculate late-day policy;
- auto-adopt Canvas grades as academic truth;
- force-overwrite Canvas;
- change academic raw grades based only on Canvas state;
- implement full continuous Canvas drift monitoring;
- use Gradebook History APIs;
- publish comments/rubrics;
- resolve absence/late-day policy;
- implement systematic academic corrections.

Any future live Canvas reconciliation remains CAM-side or requires a separately designed CAM contract.

---

## 5. Four-State Publication Model

### `L` — Local Current Academic State

```text
current grading_record_id
current grading_record_version
current raw score
current points possible
current finalized status
```

### `R` — Requested Academic Snapshot

Immutable values from `grade_publication_request`:

```text
grading_record_id
grading_record_version
raw score
points possible
```

### `T` — CAM Publication Target

Operational value computed by CAM after policy resolution.

Example:

```text
raw 90
late policy 20%
T = 72
```

### `C` — CAM-Verified Canvas State

Value observed by CAM after reread.

```text
C = 72
```

---

## 6. Two Independent Reconciliation Questions

### Academic freshness

```text
Does current local academic state L still equal the academic snapshot R
that this publication request represented?
```

### Operational convergence

```text
Did CAM verify Canvas state C equals its policy-correct target T?
```

These questions must never be collapsed.

---

## 7. Academic Freshness Classifications

Recommended:

```text
ACADEMIC_CURRENT
ACADEMIC_RECORD_ADVANCED
ACADEMIC_RECORD_REPLACED
ACADEMIC_RECORD_MISSING
ACADEMIC_POINTS_CHANGED
```

### Current

```text
same grading_record_id
same grading_record_version
same raw score
same points possible
```

### Advanced

Same logical record evolved to a newer version after request.

### Replaced

A later authoritative grading revision superseded the requested record.

This does not retroactively mutate the old publication history.

---

## 8. Operational Publication Classifications

Derived primarily from CAM result:

```text
QUEUED
AWAITING_POLICY
SYNCED
ALREADY_SYNCED
CONFLICT
BLOCKED
FAILED
NOT_REQUIRED
```

For terminal verified success:

```text
T == C
```

within numeric normalization/tolerance.

A CAM-reported `conflict` remains conflict even if the Grading App cannot independently inspect Canvas.

CAM is the Canvas operational authority.

---

## 9. Combined Status Examples

### Healthy policy-adjusted publication

```text
Academic:
L raw = 90
R raw = 90
freshness = CURRENT

Operational:
T = 72
C = 72
status = SYNCED
```

### Academic advanced after successful publication

```text
R raw = 90 / record v4
CAM published 90 successfully

Later:
L raw = 92 / record v5

freshness = ACADEMIC_RECORD_ADVANCED
operational history = prior request SYNCED
```

Action:

```text
Prepare new publication request from v5
```

### Canvas conflict

```text
R raw = 90
CAM target T = 72
Canvas observed unexpected = 75
status = CONFLICT
```

Academic record remains 90.

### Awaiting policy

```text
R raw = 90
T not yet safe to compute
status = AWAITING_POLICY
```

No academic issue exists.

## 11. No Local Recalculation of `T`

The Grading App does not reconstruct CAM target.

It uses values explicitly returned by CAM.

Never derive:

```text
T = raw * inferred penalty
```

from Canvas score or lateness hints.

If CAM has not provided a target:

```text
target = unknown
```

until result/context arrives.

---

## 12. Result Integrity

When CAM returns:

```text
raw_score
published_score
verified_canvas_score
late_policy_state
late_penalty_percent
```

the Grading App treats those as operational result metadata.

It does not overwrite the request snapshot.

If returned `raw_score` disagrees with the immutable request item:

```text
RESULT_CONTRACT_CONFLICT
```

Do not apply silently.

## 16. Issue Actions

Allowed:

```text
Refresh local publication state
Prepare new publication request from current finalized grade
Retry relay transport
View CAM error/conflict detail
View audit
```

Potential CAM retry actions may be exposed only when CAM contract says retry is safe.

Not allowed:

```text
Force Canvas = raw score
Apply inferred late penalty
Adopt Canvas as academic grade automatically
Edit academic grade from publication screen
```

Academic edits return to normal grading/regrade workflows.

---

## 17. Conflict Handling

CAM conflict means:

> CAM found current Canvas state incompatible with the safe write expectation.

The Grading App displays:

```text
requested raw
CAM target if known
Canvas value observed by CAM if supplied
error code/message
time
request/grading-record identity
```

The grading app does not independently decide which Canvas value is correct.

---

## 18. Blocked Handling

Examples:

```text
missing CAM course mapping
missing assignment mapping
missing student mapping
points mismatch
invalid publication request
unsupported reason type
```

The Grading App displays CAM's reason.

If the problem is academic/local, fix locally and create a new request.

If the problem is CAM configuration, instructor resolves it in CAM.

The TA should not be required to access CAM.

---

## 19. Failed Handling

Operational failure does not imply academic invalidity.

Display:

```text
Academic grade remains finalized.
Canvas publication failed.
```

Keep exact CAM error.

Do not roll back grading record.

---

## 20. Awaiting Policy Handling

Display:

```text
Academic grade finalized.
CAM is waiting for authoritative course-policy context.
No Canvas publication has been verified yet.
```

This is neither academic conflict nor grading failure.

---

## 21. `already_synced`

This is a success-equivalent operational state.

Meaning:

```text
CAM determined Canvas already matched intended target
and did not need a second effective write.
```

Treat as operationally converged.

Audit retains that no new write was necessary.

---

## 22. `not_required`

Examples may include a request/item for which no Canvas state transition is required.

Do not force it into `synced` if CAM intentionally reports `not_required`.

Preserve exact meaning.

---

## 23. Publication Currentness

A student can have many historical publication requests.

The current publication indicator should reflect:

```text
latest finalized academic grading record
vs
latest publication request/result that represents that record
```

Possible aggregate states:

```text
CURRENT_SYNCED
CURRENT_AWAITING_POLICY
CURRENT_CONFLICT
CURRENT_BLOCKED
CURRENT_FAILED
NOT_YET_REQUESTED
NEWER_ACADEMIC_GRADE_EXISTS
```

---

## 24. Regrade Publication in the Same History

v2.3.5 regrade-driven publication remains a different source event but should appear in the unified operational history.

Example:

```text
Initial grade
raw 80
published 64
source = initial_grading

Regrade
raw 80 → 90
published 72
source = regrade rg_123
```

The audit makes both the academic source and operational Canvas result clear.

Do not rewrite the initial publication record after regrade.

---

## 28. Alerts in Normal Workflow

Assessment UI should expose small indicators:

```text
CAM ✓
```

or:

```text
CAM ⚠ 3 publication issues
```

Do not require the TA to hunt through an administrative screen to notice a failed publication.

---

## 29. No Full Live Canvas Reconciliation Claim

v2.3.6.3 may only reconcile against **Canvas state reported by CAM**.

If Canvas changes days after a verified result and CAM has not re-read it, the Grading App cannot know that independently.

Therefore the UI/documentation must not claim:

```text
live Canvas synchronized
```

unless CAM has supplied sufficiently fresh state.

A future CAM reconciliation feature can enrich this model without changing academic ownership.

---

## 30. Testing — Policy-Adjusted Values

Required:

```text
raw 90 / target 72 / Canvas 72
→ healthy synced

raw 90 / target 90 / Canvas 90
→ healthy synced

raw 90 / target 72 / Canvas 75
→ conflict

raw 90 / target unknown
→ awaiting policy
```

No false raw-vs-Canvas conflict.

---

## 31. Testing — Academic Freshness

- same record/version;
- newer version same record;
- replacement revision;
- record missing/corrupt;
- points possible changed;
- new regrade after initial publication.

Historical request must remain immutable.

---

## 32. Testing — Mixed History

Example:

```text
initial request synced
later local grade advanced
new request failed
regrade then approved
regrade publication synced
```

UI must identify the currently authoritative academic grade and preserve all operational history.

---

## 33. Testing — Result Contract Conflict

- returned raw score mismatch;
- wrong grading record;
- unknown request;
- duplicate result exact replay;
- duplicate result conflicting body;
- older result arrives after newer request;
- out-of-order relay delivery.

No wrong-record mutation.

---

## 34. Testing — Audit

Verify:

- append-only history;
- no failed result deletion after later success;
- all correlation IDs preserved;
- no secrets;
- report generation observational only.

---

## 35. Acceptance Workflow

1. Use a batch containing on-time and late-policy-adjusted items.
2. Publish through v2.3.6.2/CAM.
3. Receive mixed CAM results.
4. Open assessment publication view.
5. Verify raw vs target vs verified Canvas columns.
6. Confirm raw 90 / Canvas 72 is healthy when CAM says policy-adjusted synced.
7. Advance one local grading record after successful publication.
8. Verify `NEWER_ACADEMIC_GRADE_EXISTS`.
9. Confirm old request remains historical.
10. Prepare a new request from the new version.
11. Inject a CAM conflict for another item.
12. Verify academic grade unchanged.
13. Review audit timeline.
14. Replay all result events.
15. Verify no duplicate history or mutations.

---

## 36. Release Blockers

Do not release if:

- raw academic score is assumed equal to Canvas score;
- late-policy adjustment is recalculated locally;
- CAM conflict can mutate academic grade;
- publication request snapshot can mutate;
- result applies to wrong grading-record version;
- newer academic grade is hidden by an older successful publication;
- failed history disappears after later success;
- UI claims live Canvas state without CAM evidence;
- TA must access CAM to understand ordinary publication status;
- reconciliation requires direct Canvas credentials.

## 39. Resulting v2.3.6.3 Contract

After v2.3.6.3:

```text
The Grading App knows:
- what raw academic grade is currently authoritative,
- what exact raw academic record/version was sent to CAM,
- what policy-correct published target CAM reported,
- what Canvas value CAM verified,
- whether the local academic record has advanced since that request,
- and whether publication is synced, waiting, conflicted, blocked, or failed.

The Grading App never assumes raw score must equal Canvas score.

The Grading App never calculates the policy adjustment itself.

CAM remains the operational Canvas authority.

Publication history never rewrites academic grading history.

The TA can understand publication state entirely from the Grading App
without needing CAM access.
```
