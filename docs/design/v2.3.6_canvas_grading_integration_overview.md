# v2.3.6 Design Overview — Full Canvas Grading Integration

**Parent release family:** `v2.3.6 — Canvas Grading Integration`  
**Repository:** `grading_app`  
**Status:** Architecture overview  
**Date:** August 18, 2026

---

## 1. Purpose

v2.3.6 is the complete Canvas grading-integration program.

The goal is not merely read-only import. The goal is a reliable, controlled two-way grading workflow:

```text
Canvas
  ↓
courses / roster / sections / assignments
  ↓
official submissions / attempts / files
  ↓
grading app canonical models
  ↓
manual grading / autograding / ZIP ingestion / regrades
  ↓
approved grade state
  ↓
controlled Canvas publish
  ↓
reconciliation / conflict detection / audit
```

The implementation is split into four independently testable releases so write capability is introduced only after read synchronization is trusted.

---

## 2. Sub-Releases

### v2.3.6.1 — Canvas Connection, Course/Roster/Assignment Sync

Direction:

```text
Canvas → App
```

Provides:

- secure token/base-URL configuration;
- Test Connection;
- course linking;
- roster/enrollment sync;
- section sync;
- assignment sync;
- assignment override metadata;
- local student mapping;
- local assessment mapping;
- pagination/throttling handling;
- sync history.

No submission file downloads. No writes.

---

### v2.3.6.2 — Canvas Submission & File Sync

Direction:

```text
Canvas → App
```

Provides:

- `Pull Canvas Submissions`;
- submission metadata;
- attempts;
- timestamps;
- missing/late/excused source state;
- attachment download;
- immutable local files;
- SHA-256;
- smart incremental sync;
- current Canvas grade baseline;
- routing into v2.3.3 autograding, v2.3.4 ZIP ingestion, or existing written grading.

Still no Canvas writes.

---

### v2.3.6.3 — Controlled Canvas Grade & Feedback Publishing

Direction:

```text
App → Canvas
```

Provides:

- publish queue;
- current-state preflight;
- preview;
- selective publication;
- score write-back;
- optional feedback;
- optional mapped rubric write-back;
- regrade `ApprovedGradeChange` publication;
- idempotent retry;
- post-write verification;
- audit.

This is the first release allowed to mutate Canvas.

---

### v2.3.6.4 — Canvas Reconciliation, Conflict Detection & Audit

Direction:

```text
Canvas ↔ App
```

Provides:

- last-synced baseline;
- current local state;
- current Canvas state;
- three-way conflict classification;
- newer-attempt conflicts;
- Canvas-only change detection;
- local-only change detection;
- points/mapping drift;
- explicit adopt-Canvas / publish-local actions;
- integration audit trail;
- optional grade-history enrichment.

After this release, v2.3.6 is considered complete.

## 3. Scope Boundary

v2.3.6 **does** integrate grading-relevant Canvas state.

It does not recreate other systems already in use.

Out of scope:

```text
absence-request intake/decisions
late-day request/ledger automation
Microsoft Forms replacement
Power Automate replacement
SharePoint replacement
Canvas page/module authoring
student-facing LMS
```

Regrades are special because the grading app owns the academic adjudication in v2.3.5. Canvas integration only publishes/reconciles the resulting approved grade change.

---

## 4. Architectural Boundary

Canvas must plug into the v2.3.2 canonical submission layer.

Correct:

```text
Canvas
  ↓
CanvasSubmissionSourceAdapter
  ↓
Submission
  ↓
grading engines
```

Incorrect:

```text
Canvas-specific programming grader
Canvas-specific written grader
Canvas-specific ZIP parser
```

There should be one Canvas adapter and one set of grading engines.

---

## 5. Internal Identity

Local IDs remain authoritative:

```text
course_id
student_id
assessment_id
submission_id
artifact_id
grading_run_id
grade_revision_id
```

Canvas identifiers are external references:

```text
canvas_course_id
canvas_user_id
canvas_section_id
canvas_assignment_id
canvas_file_id
```

This allows the app to work offline/local and prevents LMS implementation details from becoming the grading database schema.

---

## 6. Reliability Principles

1. Read before write.
2. Preserve original Canvas artifacts locally.
3. Preserve attempts.
4. Hash downloaded files.
5. Preview consequential writes.
6. Refresh Canvas state immediately before publication.
7. Never overwrite an external change silently.
8. Verify Canvas state after writes.
9. Record every sync/publish/reconciliation run.
10. Do not require privileged grade-history APIs for correctness.

---

## 7. API Client Requirements

One `CanvasClient` owns:

```text
authorization
timeouts
pagination
throttling
retry/backoff
JSON/error normalization
download behavior
redacted logging
```

Higher-level services do not implement HTTP mechanics independently.

Canvas list APIs are paginated and the client must follow `Link` headers.

Canvas dynamic throttling must be treated as a recoverable condition.

---

## 8. Service Boundary

Conceptual service set:

```text
CanvasClient
CanvasCourseSyncService
CanvasRosterSyncService
CanvasAssignmentSyncService
CanvasSubmissionSourceAdapter
CanvasPublishService
CanvasReconciliationService
CanvasAuditStore
```

The UI calls services, not raw endpoints.

## 9. User-Facing Workflow

### Setup once

```text
Settings → Canvas
[Test Connection]

Course Settings
[Link Canvas Course]

Assessment
[Link Canvas Assignment]
```

### Routine grading

```text
[Sync Canvas]
[Pull Canvas Submissions]
[Grade / Run Autograder]
[Review / Approve]
[Prepare Canvas Publish]
[Publish Approved Grades]
[Reconcile with Canvas]
```

These should be the normal instructor-facing actions.

---

## 10. Completion Criteria for the Parent Feature

v2.3.6 is complete only when:

- Canvas metadata sync is reliable;
- official Canvas submission files can be pulled incrementally;
- canonical local grading works unchanged;
- approved grades can be published with explicit confirmation;
- post-write state is verified;
- external/local divergence is detected;
- true conflicts cannot be overwritten silently;
- audit history makes each operation explainable.

---

## 11. Official API Resources Used

Implementation should use current official Instructure Canvas LMS API resources for:

- Users/Profile;
- Courses;
- Enrollments;
- Sections;
- Assignment Groups;
- Assignments and Overrides;
- Submissions;
- Files;
- Rubrics where used;
- Gradebook History / Grade Change Log only as optional enrichment.

The exact endpoint/parameter contract must be verified against the current official API documentation when implementation begins.
