# v2.3.2 Design — Submission Core & Provenance Foundation

**Release:** `v2.3.2 — Submission Core & Provenance Foundation`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Date:** August 18, 2026  
**Depends on:** v2.3.1 Advanced Similarity Review and the existing v2.2 written/LaTeX/PDF ingestion stack  
**Primary purpose:** Create one source-agnostic submission model that every later grading and Canvas feature can reuse.

---

## 1. Purpose

v2.3.2 extracts submission identity, artifact preservation, provenance, attempt handling, and import/mapping behavior into a first-class subsystem.

This release intentionally does **not** add a new grading algorithm. Its job is to make all later grading features consume the same canonical input.

After v2.3.2, these sources:

```text
local PDF
local .tex
local .py
Overleaf ZIP
Canvas file
future Git/other source
```

must converge on one core model:

```text
Source Adapter
      ↓
Submission
      ↓
Artifact Files
      ↓
Derived / Parsed Artifacts
      ↓
Grading Engines
```

The release exists to prevent v2.3.3 autograding, v2.3.4 ZIP ingestion, and v2.3.6 Canvas integration from independently inventing incompatible submission records.

---

## 2. Why This Must Be Its Own Release

The previous programming-autograding design already required:

- stable internal submission IDs;
- immutable original files;
- SHA-256 hashes;
- source-system metadata;
- attempts;
- student mapping;
- external identifiers;
- duplicate handling;
- artifact storage;
- reproducible provenance.

The Overleaf design required the same concepts for ZIP/PDF pairs.

Canvas will require the same concepts again for:

- Canvas user IDs;
- course IDs;
- assignment IDs;
- attempt numbers;
- Canvas file IDs;
- submission timestamps;
- resubmissions.

Those are not programming-specific or ZIP-specific concepts. They are application infrastructure.

Therefore:

> **v2.3.2 defines the canonical submission boundary. Later releases plug into it.**

---

## 3. Release Goals

v2.3.2 shall provide:

1. stable internal submission identity;
2. source-agnostic provenance;
3. immutable original artifact preservation;
4. SHA-256 fingerprinting;
5. multi-file submission support;
6. submission-attempt history;
7. active-attempt selection;
8. student-to-submission mapping;
9. batch import records;
10. duplicate detection;
11. normalized artifact typing;
12. derived-artifact lineage;
13. portable storage metadata;
14. structured validation/error states;
15. import audit history;
16. UI components reusable by later ingestion sources;
17. migrations/backward compatibility for existing saved written submissions;
18. adapter interfaces for local files, Canvas, ZIP, and future sources.

---

## 4. Non-Goals

v2.3.2 shall **not**:

- run student code;
- add pytest;
- add Docker/Podman execution;
- parse Overleaf ZIP projects;
- connect to Canvas;
- publish grades;
- implement regrade adjudication;
- change similarity algorithms;
- change ABET scoring;
- add LLM grading;
- replace existing question-centric grading;
- create a student submission portal;
- enforce course late-day or absence policy.

---

## 5. Architectural Principle

The grading app's internal IDs are authoritative.

External systems provide **provenance**, not identity.

```text
CANVAS / LOCAL FILE / ZIP
          ↓
   external identifiers
          ↓
  canonical local record
```

The app must continue to work when a submission has no Canvas ID, and Canvas integration must continue to work without changing the grading model.

## 7. Canonical Domain Model

### 7.1 `Submission`

A `Submission` is the logical student submission/attempt.

Conceptual model:

```python
@dataclass
class Submission:
    submission_id: str
    assessment_id: str
    student_id: str

    attempt: int | None
    is_active_attempt: bool

    source_system: str
    submitted_at: str | None
    imported_at: str

    status: str

    artifacts: list[ArtifactFile]
    external_refs: list[ExternalReference]

    metadata: dict
```

A submission is **not** synonymous with one file.

A single submission may contain:

```text
PS1.pdf
PS1.zip
```

or later:

```text
main.py
helpers.py
```

---

### 7.2 `ArtifactFile`

```python
@dataclass
class ArtifactFile:
    artifact_id: str
    submission_id: str

    role: str
    artifact_type: str

    original_filename: str
    stored_relative_path: str

    mime_type: str | None
    size_bytes: int
    sha256: str

    created_at: str
    metadata: dict
```

Recommended `role` values:

```text
primary
rendered
source
attachment
supporting
derived
```

Recommended `artifact_type` values:

```text
pdf
tex
latex_project_zip
python
zip
docx
text
image
unknown
```

Artifact type is descriptive, not a security trust decision.

---

### 7.3 `ExternalReference`

External IDs should be typed rather than scattered across unrelated fields.

```python
@dataclass
class ExternalReference:
    system: str
    entity_type: str
    external_id: str
    metadata: dict
```

Examples:

```text
system = canvas
entity_type = course
external_id = 410438
```

```text
system = canvas
entity_type = assignment
external_id = 3889170
```

```text
system = canvas
entity_type = file
external_id = 82177342
```

This prevents Canvas-specific columns from becoming mandatory everywhere.

---

### 7.4 `DerivedArtifact`

Parsed or generated outputs must preserve lineage.

```python
@dataclass
class DerivedArtifact:
    derived_artifact_id: str
    source_artifact_ids: list[str]

    kind: str
    stored_relative_path: str | None
    sha256: str | None

    generator: str
    generator_version: str
    created_at: str

    metadata: dict
```

Examples:

```text
parsed_questions
normalized_text
compiled_validation_pdf
extracted_project_manifest
autograder_execution_copy
```

A derived artifact never replaces the original.

---

### 7.5 `ImportBatch`

Batch imports need stable audit identity.

```python
@dataclass
class ImportBatch:
    import_batch_id: str
    source_system: str

    started_at: str
    completed_at: str | None

    created_by: str | None

    candidate_count: int
    imported_count: int
    skipped_count: int
    error_count: int

    status: str
    metadata: dict
```

---

### 7.6 `ImportCandidate`

Before persistence, every incoming artifact should exist as a candidate.

```python
@dataclass
class ImportCandidate:
    candidate_id: str
    source_system: str

    source_locator: str | None
    proposed_student_id: str | None
    proposed_assessment_id: str | None
    proposed_attempt: int | None

    files: list[CandidateFile]

    match_status: str
    validation_status: str
    warnings: list[str]
    errors: list[str]
```

This makes preview/confirmation possible before committing data.

---

## 8. Stable Internal ID Rules

Recommended ID families:

```text
sub_<uuid>       Submission
art_<uuid>       ArtifactFile
drv_<uuid>       DerivedArtifact
imp_<uuid>       ImportBatch
cand_<uuid>      ImportCandidate
```

Do not derive canonical IDs from:

- student display name;
- filename;
- Canvas assignment ID;
- row number;
- file hash alone.

Hashes support identity checks but are not application primary keys.

---

## 9. Immutability Rules

### 9.1 Original Files

Once imported successfully:

- original bytes are never modified;
- file hash is never recalculated from modified content;
- path may be relocated only through controlled storage operations;
- logical metadata may be amended through audit events;
- a new attempt creates a new `Submission`.

### 9.2 Corrections

If the wrong file was imported:

```text
do not replace bytes in-place
```

Instead:

```text
mark prior submission/artifact superseded
create/import correct artifact
record audit event
```

---

## 10. Hashing

Use SHA-256 for original artifacts.

Store:

```text
sha256
size_bytes
```

For multi-file logical submissions, compute an optional submission fingerprint over a canonical manifest:

```text
sort by normalized relative path
path + NUL + sha256
```

The exact canonical algorithm must be documented and covered by tests.

---

## 11. Source Systems

Initial recognized source values:

```text
local_upload
legacy_local
```

Reserved/future:

```text
canvas
latex_project
git
external_import
```

`source_system` answers:

> Where did this submission enter the grading app?

It does not answer:

> What file type is this?

```text
LocalFileSourceAdapter
```

```text

```

## 13. Artifact Router

After import:

```python
class ArtifactRouter:
    def classify(self, submission: Submission) -> RouteDecision:
        ...
```

Possible routes:

```text
written_pdf
latex_source
programming_python
latex_project_zip
unsupported
mixed
```

Routing does **not** perform grading.

It answers:

> Which downstream ingestion/grading handler is eligible?

## 14. Multi-Artifact Submission Semantics

The core must support one submission containing multiple evidence files.

Example:

```text
Submission sub_123
├── art_pdf
│   role = rendered
│   type = pdf
└── art_zip
    role = source
    type = latex_project_zip
```

This is essential for v2.3.4.

The core must not require one globally designated `file_path`.

---

## 15. Attempt Semantics

### 15.1 Attempt Number

`attempt` may be:

- known from source (Canvas);
- assigned by import sequence;
- `None` for legacy records.

### 15.2 Active Attempt

At most one attempt per:

```text
student × assessment
```

may be `is_active_attempt = true`.

Historical attempts remain preserved.

### 15.3 Newer Attempt

When a later attempt arrives:

1. create new `Submission`;
2. preserve old attempt;
3. mark new attempt active;
4. mark prior attempt inactive;
5. do not delete prior grading history;
6. flag if a grade already exists for the older attempt.

---

## 16. Duplicate Semantics

Different duplicate conditions must be distinguished.

### Exact artifact duplicate

Same student + assessment + artifact SHA-256.

Possible action:

```text
reuse existing artifact
skip
import as explicit new attempt
```

### Same filename, different bytes

Not a duplicate.

### Same bytes, different student

Import separately but optionally expose similarity/exact-hash information to the existing similarity layer.

Never infer misconduct from the core import layer.

---

## 17. Student Mapping

Batch imports should map candidates to existing roster/student records.

Matching signals can include:

1. stable student ID;
2. login/email local part;
3. known filename convention;
4. normalized display name;
5. previously confirmed mapping.

Statuses:

```text
matched
needs_confirmation
ambiguous
unmatched
ignored
```

The system must never silently assign an ambiguous candidate.

---

## 18. Assessment Mapping

Local upload may occur inside a known assessment and therefore already have `assessment_id`.

Generic batch import may require mapping.

The same mapping mechanism will later support Canvas assignment mapping.

---

## 19. Local Import Workflow

```text
Open assessment
    ↓
Import Submissions
    ↓
Select files
    ↓
Build candidates
    ↓
Hash / inspect metadata
    ↓
Propose student mapping
    ↓
Preview
    ↓
Resolve ambiguous entries
    ↓
Commit import
    ↓
Create Submission + ArtifactFile records
```

No downstream parser should run before successful canonical import unless specifically implemented as a validation preview.

## 24. Storage Model

Recommended layout:

```text
data/
  courses/
    <course_id>/
      assessments/
        <assessment_id>/
          submissions/
            <student_id>/
              <submission_id>/
                originals/
                derived/
                metadata/
```

Rules:

- store relative paths in persisted records;
- never persist host-specific absolute paths as portable identity;
- originals are read-only after import;
- derived outputs live separately;
- temporary processing workspaces are not evidence storage.

---

## 25. Safe Filename Handling

Incoming names must be sanitized for storage/display.

Reject or neutralize:

```text
../
absolute paths
drive-root paths
NUL
path separators where not expected
reserved device names where relevant
```

Display name and storage name may differ.

Always preserve original filename as metadata.

## 28. Compatibility With Existing Written Ingestion

Existing v2.2 paths may currently take raw paths directly.

v2.3.2 should introduce a compatibility layer:

```text
SubmissionArtifact/ArtifactFile
       ↓
resolve read-only original path
       ↓
existing parser
```

Do not rewrite the written parser unnecessarily.

The migration goal is:

> existing behavior continues, but input identity comes from the new core.

---

## 29. Migration Strategy

### Stage 1

Add new schema/types alongside legacy fields.

### Stage 2

When loading an old saved assessment:

- generate canonical submission records in memory;
- preserve legacy values;
- mark migration origin.

### Stage 3

On explicit save/migration:

- persist canonical records;
- retain version metadata.

Do not silently destroy fields required by old releases.

---

## 30. Schema Versioning

Add or increment the appropriate persistence schema version.

Migration must be:

- deterministic;
- idempotent;
- tested on representative old saves;
- reversible through backup/version control where practical.

## 32. Testing Strategy

### 32.1 ID tests

Verify:

- unique IDs;
- stable persisted IDs;
- no row-order dependence.

### 32.2 Hash tests

Verify:

- identical bytes => identical SHA;
- changed bytes => different SHA;
- canonical multi-file fingerprint determinism.

### 32.3 Import tests

Test:

- one file;
- many files;
- duplicate;
- same filename different bytes;
- ambiguous mapping;
- unknown student;
- unreadable file;
- missing file.

### 32.4 Attempt tests

Test:

- first attempt;
- second attempt;
- active-attempt switch;
- historical preservation;
- explicit rollback to older active attempt if permitted.

### 32.5 Multi-artifact tests

Test:

- PDF + ZIP;
- multi-file programming submission;
- supporting attachment.

### 32.6 Migration tests

Load representative pre-v2.3.2 saved assessments.

Verify no scoring/grading changes.

### 32.7 Security tests

Test path traversal filenames and malformed metadata.

### 32.8 Regression

Run the complete existing repository suite.

## 35. Acceptance Criteria

v2.3.2 is complete when:

- [ ] every new imported submission receives a stable internal `submission_id`;
- [ ] original artifacts are immutable after import;
- [ ] every artifact has SHA-256 and size metadata;
- [ ] one submission can contain multiple artifacts;
- [ ] source/provenance metadata is independent of file type;
- [ ] external IDs are represented without becoming local primary IDs;
- [ ] batch import can preview and resolve student mappings;
- [ ] ambiguous mappings are never silently accepted;
- [ ] attempts are preserved rather than overwritten;
- [ ] one active attempt is clearly designated;
- [ ] duplicate conditions are detected and handled explicitly;
- [ ] derived artifacts preserve lineage;
- [ ] old saved assessments load correctly;
- [ ] existing written grading behavior remains unchanged;
- [ ] existing similarity behavior remains unchanged;
- [ ] import/audit metadata persists across restart;
- [ ] full repository tests pass.

---

## 36. Release Gate

Do not tag v2.3.2 if:

- downstream code still depends on arbitrary raw file paths as identity;
- importing a new attempt overwrites the prior attempt;
- original bytes can be modified in place;
- Canvas-specific IDs have been made mandatory fields;
- multi-artifact submissions cannot be represented;
- old assessment saves regress.

---

## 37. Resulting Contract

After v2.3.2, every later feature can assume:

```text
I receive a canonical Submission.
I can identify its student and assessment.
I can inspect immutable artifacts.
I can identify its source and attempt.
I can reproduce exactly which bytes were used.
I do not care whether the bytes came from Canvas or local upload.
```

That contract is the core purpose of this release.
