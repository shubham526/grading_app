# v2.3.4 Design — Overleaf / LaTeX Project ZIP Ingestion

**Release:** `v2.3.4 — Overleaf / LaTeX Project ZIP Ingestion`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Date:** August 18, 2026  
**Depends on:** v2.3.2 Submission Core & Provenance Foundation and existing v2.2 LaTeX/PDF parsing  
**Does not depend on:** v2.3.3 autograding

---

## 1. Purpose

v2.3.4 extends the written-submission ingestion stack to accept a complete Overleaf/LaTeX source project as a ZIP while preserving the student's submitted PDF as rendered evidence.

The standard target submission is:

```text
lastname_firstname_PS1.pdf
lastname_firstname_PS1.zip
```

The ZIP is the complete source project. The PDF is the student's official rendered output.

The release safely extracts and validates the source project, resolves a deterministic root document, records project provenance, optionally compiles in an isolated validation environment, and then feeds the existing written question-extraction/grading pipeline.

---

## 2. Architectural Change From the Old Design

The previous ZIP design had to own pairing and provenance itself.

After v2.3.2, that responsibility belongs to the canonical `Submission`.

Therefore v2.3.4 consumes:

```text
Submission
├── ArtifactFile(role=rendered, type=pdf)
└── ArtifactFile(role=source, type=latex_project_zip)
```

and produces derived project/parsed artifacts.

It does **not** invent another student/submission identity model.

---

## 3. Goals

v2.3.4 shall:

1. accept Overleaf-style source ZIP artifacts;
2. pair source ZIP and submitted PDF through the v2.3.2 multi-artifact submission model;
3. safely inspect/extract ZIP contents;
4. require deterministic project entry point `main.tex`;
5. support multi-file LaTeX projects;
6. preserve original ZIP bytes;
7. preserve submitted PDF bytes;
8. create a project manifest;
9. hash extracted source files;
10. compile/validate the project safely when enabled;
11. reuse the existing v2.2 LaTeX parser;
12. preserve provenance/derived-artifact lineage;
13. provide actionable UI diagnostics;
14. keep legacy `.tex + .pdf` support;
15. keep downstream grading/similarity unaware of ZIP internals.

---

## 4. Non-Goals

v2.3.4 shall not:

- change grading logic;
- change similarity algorithms;
- change ABET scoring;
- use the Overleaf API;
- repair broken student LaTeX automatically;
- rewrite student source;
- silently guess among multiple plausible main documents;
- execute arbitrary student shell scripts;
- enable unrestricted shell escape;
- replace the submitted PDF with a locally compiled PDF;
- connect to Canvas.

Canvas will later supply the same ZIP/PDF artifacts through v2.3.6.2.

---

## 5. Submission Contract

Recommended course template:

```text
main.tex
```

at ZIP root.

Students may add:

```text
macros.tex
answers/
figures/
references.bib
styles/
```

but should not rename/move the root `main.tex`.

Recommended student-facing requirement:

> Submit both the compiled PDF and the complete Overleaf source ZIP. Do not manually remove project files from the ZIP. Keep `main.tex` at the project root.

---

## 6. Canonical Input

Normal valid input:

```text
Submission sub_...
├── rendered artifact
│   ├── type = pdf
│   └── role = rendered
└── source artifact
    ├── type = latex_project_zip
    └── role = source
```

Possible submission completeness states:

```text
complete_pair
missing_rendered_pdf
missing_source_zip
duplicate_rendered_pdf
duplicate_source_zip
legacy_tex_pdf
```

Completeness is derived from artifacts; it does not create a separate submission ID.

---

## 7. High-Level Pipeline

```text
canonical Submission
       ↓
select source ZIP + rendered PDF
       ↓
archive structural validation
       ↓
safe extraction into disposable workspace
       ↓
project manifest + extracted hashes
       ↓
require ./main.tex
       ↓
optional isolated compile validation
       ↓
LaTeXProjectSource derived metadata
       ↓
existing v2.2 parser
       ↓
ParsedSubmission / question answers
       ↓
existing grading / similarity
```

---

## 8. `LaTeXProjectSource`

Conceptual model:

```python
@dataclass
class LaTeXProjectSource:
    source_artifact_id: str
    rendered_artifact_id: str | None

    main_tex_relative_path: str
    project_files: list[ProjectManifestEntry]

    archive_sha256: str
    project_manifest_sha256: str

    total_uncompressed_bytes: int
    file_count: int

    validation_status: str
    compile_validation: dict | None
```

Absolute extraction paths must not be persisted as portable provenance.

---

## 9. `ProjectManifestEntry`

```python
@dataclass
class ProjectManifestEntry:
    relative_path: str
    size_bytes: int
    sha256: str
    file_type: str
```

The manifest itself should have a canonical hash.

---

## 10. Main Document Resolution

Deterministic rule:

```text
ZIP root contains ./main.tex
    → valid main document

ZIP root lacks ./main.tex
    → MISSING_MAIN_TEX
```

A nested-only `main.tex` does not satisfy the contract.

The app should not guess.

An advanced configurable entry point can be considered later, but the default course workflow should remain deterministic.

---

## 11. ZIP Security

Student archives are untrusted.

Do not blindly call unrestricted `extractall()`.

Reject:

- `../` traversal;
- absolute paths;
- Windows drive-root paths;
- paths that resolve outside extraction root;
- symlinks;
- hard links where detectable;
- special/device files;
- conflicting duplicate paths;
- malformed archives;
- excessive file count;
- excessive total uncompressed size;
- excessive individual file size.

Recommended defaults:

```text
max archive size             50 MB
max uncompressed size       250 MB
max file count             1000
max single extracted file   50 MB
```

These are app safety limits, not course grading rules.

---

## 12. ZIP Bomb / Compression-Ratio Protection

In addition to total uncompressed size, optionally flag extreme compression ratios.

The extractor should evaluate metadata before writing files where possible.

Any limit failure must leave no successful parsed-submission record.

---

## 13. Extraction Workspace

Use a fresh disposable workspace:

```text
tmp/
  ingestion_<uuid>/
    source_project/
```

Never reuse a prior student's extraction directory.

The canonical original ZIP remains in v2.3.2 artifact storage.

---

## 14. Project Compilation

Compilation is useful for:

- validation;
- reproducibility diagnostics;
- resolving normal `\input`/figure/bibliography behavior;
- optional rendered comparison.

But LaTeX projects are untrusted executable-like inputs.

Compile only through a constrained process/container.

Required safeguards:

- shell escape disabled;
- no network;
- timeout;
- memory/process limits where available;
- no host secrets;
- no app database access;
- fresh workspace;
- instructor-controlled TeX distribution.

Do not execute:

```text
Makefile
build.sh
arbitrary scripts
```

as part of v2.3.4.

---

## 15. Compilation Working Directory

Compile from project root:

```text
cwd = source_project/
entry = main.tex
```

This preserves normal relative references:

```latex
\input{answers/q1.tex}
\includegraphics{figures/tree.pdf}
\bibliography{references}
```

Do not copy `main.tex` out of its project tree and compile it alone.

---

## 16. Submitted PDF Is Authoritative Rendered Evidence

The locally compiled PDF, if produced, is a **derived validation artifact**.

It must not silently replace:

```text
student-submitted PDF
```

Recommended semantics:

```text
source authority      = original ZIP
rendered authority    = submitted PDF
compiled local PDF    = derived validation artifact
```

---

## 17. Compilation Comparison

Optional diagnostic:

```text
submitted PDF hash != locally compiled PDF hash
```

should not automatically mean misconduct or invalid submission.

Rendering may differ because of:

- TeX distribution;
- metadata;
- timestamps;
- fonts;
- package versions.

If comparison is implemented, use it only as diagnostic evidence.

---

## 18. Source Parsing

After `main.tex` resolution, reuse existing v2.2 parsing.

The parser must support normal project inclusion.

If v2.2 only understands a single source file, v2.3.4 may introduce a project-aware source resolver that recursively follows approved LaTeX include commands.

Do not interpret arbitrary shell/process directives.

---

## 19. Include Resolution

Expected support:

```latex
\input{...}
\include{...}
```

Potentially support bibliography/figure references for validation, but question extraction should focus on text-bearing source.

Include resolution must:

- stay inside project root;
- detect cycles;
- avoid infinite recursion;
- preserve source-file references for diagnostics.

---

## 20. Derived Question Provenance

Each extracted answer should be traceable back to project source.

Example:

```text
Q3 answer
source files:
  main.tex
  answers/q3.tex
source spans:
  ...
```

This is valuable for debugging and later LLM/submission-chat features.

---

## 21. Similarity Implications

Preserve distinct signals:

```text
archive SHA-256
project manifest hash
main.tex SHA-256
per-file hashes
normalized answer text
```

These mean different things.

Examples:

- identical ZIP => exact project identity;
- different ZIP but identical source file => exact file identity;
- different source layouts but identical answer => normalized-answer identity.

No similarity algorithm is changed in this release.

---

## 22. Provenance

Derived project metadata should link to the original canonical artifacts.

Example:

```json
{
  "kind": "latex_project",
  "source_artifact_id": "art_zip",
  "rendered_artifact_id": "art_pdf",
  "main_tex": "main.tex",
  "archive_sha256": "...",
  "project_manifest_sha256": "...",
  "file_count": 7,
  "total_uncompressed_bytes": 184203,
  "validation_status": "valid"
}
```

Do not duplicate huge manifests into every question-level grading record.

## 24. Actionable Errors

Examples:

```text
Missing root main.tex
Unsafe archive path
Archive exceeds configured limit
No matching submitted PDF
Duplicate source ZIP
Project include escapes root
LaTeX compile validation failed
Parser failed to resolve included source
```

Show student/assessment/submission identity with every error.

## 26. Backward Compatibility

Continue supporting:

```text
PDF only where allowed
PDF + .tex
saved assessments from prior versions
```

Legacy source may map to:

```text
ArtifactFile(type=tex, role=source)
ArtifactFile(type=pdf, role=rendered)
```

Downstream grading should not receive ZIP-specific branches.

---

## 27. Canvas Future Compatibility

v2.3.6.2 will be able to import Canvas attachments:

```text
PS1.pdf
PS1.zip
```

into one canonical `Submission`.

At that point v2.3.4 automatically activates through artifact routing.

No Canvas code belongs in the ZIP parser.

## 36. Acceptance Criteria

- [ ] ZIP/PDF pairs use v2.3.2 multi-artifact submissions;
- [ ] original ZIP remains immutable;
- [ ] original PDF remains immutable;
- [ ] unsafe archive paths are rejected;
- [ ] resource limits are enforced;
- [ ] root `main.tex` is required;
- [ ] multi-file projects work;
- [ ] compilation, if enabled, runs in a constrained environment;
- [ ] shell escape is disabled;
- [ ] local compiled PDF never silently replaces submitted PDF;
- [ ] project manifest and hashes persist;
- [ ] parsed questions preserve source lineage;
- [ ] legacy `.tex + .pdf` still works;
- [ ] existing grading is unchanged;
- [ ] existing similarity is unchanged;
- [ ] full repository tests pass.

---

## 37. Release Gate

Do not release if:

- ZIP extraction can escape its workspace;
- project compilation can execute unrestricted shell commands;
- original source/rendered artifacts are overwritten;
- ZIP logic bypasses the canonical submission model;
- downstream grading has to understand ZIP internals;
- legacy written submissions regress.

---

## 38. Resulting Contract

After v2.3.4:

```text
Given a canonical LaTeX-project Submission,
the app can safely validate and parse the complete source project
while retaining the submitted PDF and source ZIP as immutable evidence.
```
