# v2.3.2 Design Document — Programming Submission & Autograding

**Project:** Grading App  
**Feature:** Programming Submission & Autograding  
**Target Version:** v2.3.2  
**Status:** Proposed Design  
**Date:** August 18, 2026  
**Primary Initial Language:** Python  
**Primary Initial Test Runner:** pytest  

---

## 1. Executive Summary

v2.3.2 adds a new first-class grading mode to the grading app: **Programming Submission & Autograding**.

The feature allows an instructor to:

1. create or open a programming assessment;
2. upload an instructor-controlled autograder/test package;
3. upload one or many student programming submissions;
4. map uploaded files to students;
5. execute each student's submission against the configured test suite in an isolated environment;
6. capture per-test results, failures, errors, timeouts, stdout, stderr, runtime, and scoring details;
7. review and manually override results when needed;
8. re-run exact submissions reproducibly;
9. generate per-student and batch grading reports; and
10. preserve a full audit trail of the submission artifact and every grading run.

The feature is intentionally **source-agnostic**. v2.3.2 must work without Canvas. Local file upload is the initial submission source, while future versions may add Canvas, ZIP, Git repository, or other ingestion adapters without changing the grading model.

The app will **orchestrate** program execution but will never execute arbitrary student code inside the grading application's own process. Student code must run through an isolated execution backend with fixed dependencies, no network access, time limits, and resource limits.

This is not intended to create a student-facing Gradescope clone. Canvas or another LMS remains responsible for student-facing submission, roster, deadline, and grade-portal workflows. The grading app remains the instructor-side grading, execution, review, audit, and reporting system.

# 2. Motivation

The grading app already supports or is evolving toward several complementary grading workflows:

- written/question-centric manual grading;
- rubric-based grading;
- LaTeX/PDF submission ingestion;
- similarity review;
- ABET/outcome reporting;
- regrade workflows;
- future LLM-assisted grading;
- future Canvas ingestion and grade publication.

Programming assignments are currently a missing artifact type.

A `.py` file should be treated as another submission artifact associated with:

- a course;
- an assessment;
- a student;
- a specific submitted file;
- a stable internal submission ID;
- source/provenance metadata; and
- one or more grading records.

Once code becomes a first-class submission artifact, the same submission can eventually support:

- deterministic autograding;
- similarity review;
- regrades;
- ABET evidence;
- audit history;
- manual review;
- LLM-assisted explanation/review; and
- Canvas synchronization.

The feature therefore belongs inside the grading app rather than in a permanent collection of disconnected course-specific scripts.

# 4. Goals

## 4.1 Functional Goals

v2.3.2 must allow an instructor to:

- define an assessment as a programming assessment;
- configure a Python grading environment;
- upload test files and grading configuration;
- distinguish public and hidden tests;
- configure weighted grading groups;
- upload individual or batch student `.py` submissions;
- associate uploaded submissions with existing students;
- validate required files before execution;
- run selected or all submissions;
- isolate every student execution;
- enforce execution timeouts;
- enforce configurable CPU/memory restrictions where supported;
- disable network access in the execution environment;
- capture structured test results;
- calculate deterministic scores;
- display failures and diagnostic information;
- flag abnormal grader outcomes for review;
- permit manual score adjustment without destroying the original autograder result;
- store all grading-run provenance;
- re-run an exact submission;
- re-run groups of submissions;
- compare old and new runs when tests change;
- export per-student results;
- export batch results; and
- preserve backward compatibility with existing written assessments.

## 4.2 Architectural Goals

The implementation must:

- remain independent of Canvas;
- preserve internal app IDs as authoritative;
- treat submission source IDs as provenance only;
- isolate execution logic from UI code;
- allow additional programming languages/runners later;
- allow Docker, Podman, or another backend without changing grading semantics;
- keep test configuration separate from test implementation;
- version grading configurations;
- produce reproducible grading records;
- never mutate or overwrite the original uploaded student artifact;
- distinguish student-code failures from grader/infrastructure failures; and
- support future integration with regrade, similarity, ABET, and Canvas features.

## 4.3 User Experience Goals

The system should make the common workflow fast:

```text
Create/Open Programming Assessment
              |
              v
      Load Autograder Package
              |
              v
    Upload Student Submissions
              |
              v
       Confirm Student Mapping
              |
              v
          Run All
              |
              v
       Review Flagged Runs
              |
              v
        Export / Finalize
```

For normal submissions, the instructor should not need to inspect logs manually.

Exceptional cases should be highly visible.

The following are explicitly out of scope:

- student-facing submission portal;
- student accounts;
- course roster management;
- live code editor;
- in-browser IDE;
- LMS replacement;
- Canvas API ingestion;
- Canvas grade write-back;
- GitHub Classroom integration;
- Git repository cloning;
- automatic plagiarism/misconduct verdicts;
- LLM grading;
- LLM code repair;
- OCR;
- arbitrary language support;
- interactive programs requiring user input;
- multi-container distributed systems grading;
- GPU workloads;
- long-running benchmark infrastructure;
- sandboxing hostile native binaries beyond the guarantees of the selected execution backend;
- automatic installation of arbitrary untrusted student dependencies;
- automatic execution of student-provided shell scripts.

Some of these may be added later, but v2.3.2 should remain focused and deterministic.

# 7. Core Design Principles

## 7.1 Internal IDs Remain Authoritative

The app's own IDs remain the canonical identity:

```text
course_id
assessment_id
student_id
submission_id
grading_run_id
grading_record_id
```

External/source-specific IDs belong in provenance metadata.

Example:

```text
source_system = "local_upload"

external_course_id = null
external_assignment_id = null
external_submission_id = null
external_file_id = null
```

A future Canvas-imported artifact may instead use:

```text
source_system = "canvas"

external_course_id = "410438"
external_assignment_id = "3889170"
external_submission_id = "..."
external_file_id = "..."
```

The grading engine should not care which source produced the artifact.

---

## 7.2 Original Student Artifacts Are Immutable

The uploaded submission must be retained exactly as received.

The app may create derived working copies, extracted directories, normalized views, or execution copies, but the original artifact must never be altered.

A SHA-256 digest must be recorded for every submitted file used in grading.

---

## 7.3 Student Code Is Untrusted

Student code must never run in the main grading-app process.

The grading app must treat every student submission as potentially malicious or defective.

Execution must occur through an execution backend with:

- process isolation;
- temporary workspace;
- no network;
- read-only instructor test assets where practical;
- controlled writable working directory;
- fixed interpreter/runtime;
- fixed dependency set;
- timeout;
- process termination;
- stdout/stderr capture;
- exit-code capture;
- resource limits where available.

---

## 7.4 Grading Must Be Reproducible

A grading result is meaningful only if the app can answer:

> Which exact submission, test suite, configuration, and environment produced this result?

Every grading run must therefore capture:

- student;
- assessment;
- submission ID;
- submission file hashes;
- autograder-definition version/hash;
- test-suite version/hash;
- environment version;
- execution backend;
- start/end time;
- result status;
- raw output;
- structured test results;
- raw score; and
- final reviewed score.

---

## 7.5 Raw Autograder Results Must Never Be Destroyed

Manual adjustments must be layered on top of the automatic result.

Example:

```text
raw_autograder_score = 65
max_score = 70

manual_adjustment = +5
manual_adjustment_reason =
  "Equivalent output incorrectly rejected by test v1.0"

final_score = 70
```

The original 65/70 remains part of the immutable grading-run history.

# 9. Proposed Component Model

## 9.1 `ProgrammingAssessmentConfig`

Represents the grading configuration attached to a programming assessment.

Responsibilities:

- language;
- runner;
- required files;
- grading groups;
- timeouts;
- environment;
- package metadata;
- report settings.

---

## 9.2 `SubmissionArtifact`

Represents one immutable student artifact.

Responsibilities:

- internal submission ID;
- student ID;
- assessment ID;
- filename;
- content hash;
- original location;
- source/provenance;
- submitted/imported timestamp;
- attempt number where known.

---

## 9.3 `AutograderPackage`

Represents the instructor-controlled grading assets.

Responsibilities:

- package manifest;
- tests;
- public/hidden classification;
- environment definition;
- grader version;
- package hash;
- validation state.

---

## 9.4 `AutograderRunner`

High-level orchestration API.

Conceptual interface:

```python
class AutograderRunner:
    def validate(self, assessment, submission):
        ...

    def run(self, assessment, submission):
        ...

    def rerun(self, prior_grading_run_id):
        ...
```

This layer should not contain Docker-specific UI logic.

---

## 9.5 `ExecutionBackend`

Abstracts the sandbox/container system.

Conceptual interface:

```python
class ExecutionBackend:
    def prepare(self, run_spec):
        ...

    def execute(self, run_spec):
        ...

    def terminate(self, run_id):
        ...

    def cleanup(self, run_id):
        ...
```

Initial likely implementation:

```text
ContainerExecutionBackend
```

Possible future implementations:

```text
PodmanExecutionBackend
RemoteWorkerExecutionBackend
SlurmExecutionBackend
```

The grading semantics must remain independent of the execution backend.

---

## 9.6 `PytestRunner`

Python-specific runner adapter.

Responsibilities:

- invoke pytest inside the isolated environment;
- request machine-readable result output;
- collect individual test results;
- map tests to grading groups;
- distinguish failure/error/timeout infrastructure cases;
- return a normalized `AutograderRunResult`.

---

## 9.7 `AutograderRunResult`

Normalized execution result independent of pytest/container details.

Conceptual structure:

```text
run_id
status
started_at
finished_at
duration_ms

tests[]
groups[]

stdout
stderr
process_exit_code

raw_score
max_score

warnings[]
errors[]
```


# 13. Configuration Validation

Before an autograder package can be activated, the app must validate it.

Validation should check:

- supported `schema_version`;
- assignment ID/name present;
- recognized language;
- recognized runner;
- `max_points > 0`;
- grading-group IDs unique;
- grading-group names present;
- group points nonnegative;
- sum of group points equals assessment programming points;
- required files declared;
- test mapping references valid group IDs;
- referenced files exist;
- requirements file exists when declared;
- timeout is within allowed bounds;
- memory limit is within allowed bounds;
- network setting is supported;
- no duplicate test mapping conflicts;
- public/hidden directories are recognized;
- test suite can be collected by pytest;
- optional dry-run/smoke test succeeds using instructor fixture code.

Invalid packages should fail activation with actionable validation errors.

---

# 14. Test Visibility

Tests can be:

```text
PUBLIC
HIDDEN
```

Public tests may be distributed to students later.

Hidden tests remain instructor-only.

Visibility controls what may appear in student-facing exports, not whether the instructor can see the result.

For example:

```text
Instructor Review:
  hidden_edge_duplicate_priority   FAILED

Student Report:
  Hidden edge-case test            FAILED
```

Exact hidden test contents, expected values, or implementation details should not be exposed unless the instructor explicitly selects an instructor-only report.

# 16. Student Mapping

The import system should attempt to associate submissions with roster students.

Potential matching signals:

1. exact student ID embedded in filename;
2. username/email local part;
3. normalized student name;
4. configured filename convention;
5. manually remembered mapping.

The app must never silently guess an ambiguous match.

Proposed import table:

| Submission | Suggested Student | Confidence | Status |
|---|---|---:|---|
| `jdoe_lab3.py` | Jane Doe | High | Ready |
| `smith_lab3.py` | Robert Smith | High | Ready |
| `lab3_final.py` | — | — | Needs mapping |

Actions:

```text
[Confirm All High-Confidence Matches]
[Resolve Selected]
[Ignore File]
[Import]
```

Manual resolutions may be remembered for the current assessment/import session.

---

# 17. Submission Validation

Before execution, validate each submission.

Possible validation results:

```text
READY
MISSING_REQUIRED_FILE
UNSUPPORTED_ARCHIVE
DUPLICATE_SUBMISSION
UNMAPPED_STUDENT
INVALID_FILENAME
EMPTY_FILE
IMPORT_ERROR
```

Validation failures must be shown before batch execution.

A validation failure is not necessarily an autograder score of zero; it should first become a reviewable submission state.

The instructor may choose an assessment policy such as:

```text
Missing required file => score 0
```

but this should be explicit and not hard-coded globally.

---

# 18. Submission Attempts

The core model should permit more than one submission per student even if local upload is the initial source.

Suggested fields:

```text
submission_id
student_id
assessment_id
attempt
is_active_attempt
submitted_at
imported_at
source_system
```

When multiple local files are imported for the same student:

- warn the instructor;
- do not silently replace prior artifacts;
- permit selection of the active submission;
- retain prior submissions if desired.

This prepares the model for Canvas attempts later.

# 19. Execution Security Model

## 19.1 Threat Model

Student code may:

- crash;
- hang forever;
- fork processes;
- allocate excessive memory;
- write huge amounts of output;
- read local files;
- attempt network access;
- inspect environment variables;
- attempt subprocess execution;
- intentionally interfere with tests;
- intentionally inspect hidden tests;
- intentionally exploit weak sandboxing.

v2.3.2 should provide practical isolation appropriate for course autograding.

It should not claim to be a formally secure multi-tenant hostile-code platform.

---

## 19.2 Required Isolation Controls

At minimum:

- execution outside the GUI/main app process;
- one fresh workspace per run;
- no network;
- timeout;
- stdout size cap;
- stderr size cap;
- working-directory isolation;
- fixed interpreter;
- fixed installed dependencies;
- no host source-tree mount;
- no host credential mount;
- no inherited secrets/environment variables;
- cleanup after completion;
- kill on timeout;
- explicit process exit-code capture.

Where supported by the backend:

- CPU limit;
- memory limit;
- process/PID limit;
- read-only root filesystem;
- non-root execution;
- seccomp/apparmor profile;
- dropped Linux capabilities.

---

# 20. Containerized Execution

Recommended initial execution model:

```text
Host grading app
       |
       v
Create grading run
       |
       v
Create temporary workspace
       |
       +-- copy student artifact
       +-- attach tests read-only
       +-- load fixed image/environment
       |
       v
Start container
       |
       +-- no network
       +-- non-root user
       +-- memory cap
       +-- CPU/process limits
       +-- wall-clock timeout
       |
       v
Run pytest adapter
       |
       v
Write structured result file
       |
       v
Capture stdout/stderr/exit
       |
       v
Destroy container/workspace
```

The app must not depend on the TA/instructor host Python environment being identical to the grading environment.

# 21. Environment Definition

Every active autograder package references a stable environment.

Example:

```text
environment_id:
    cs2580-python-v1

python:
    3.12.x

packages:
    pytest==...
    numpy==...
```

The exact execution image should be fingerprinted.

Recommended stored fields:

```text
environment_id
container_image
container_image_digest
python_version
dependency_lock_hash
```

A human-friendly environment version is useful, but the immutable digest is the reproducibility anchor.

---

# 22. Dependency Policy

v2.3.2 should support **instructor-defined dependencies only**.

Do not automatically install dependencies declared by the student's submission.

Allowed:

```text
Instructor requirements.txt
```

Not automatically allowed:

```text
student requirements.txt
student setup.py
student pyproject installation hooks
```

This avoids executing arbitrary package-install code and keeps grading deterministic.

---

# 23. Runner Design

The first runner is:

```text
Python + pytest
```

But runner-specific code should implement an interface.

Conceptually:

```python
class LanguageRunner:
    def prepare_command(self, run_spec):
        ...

    def parse_results(self, execution_output):
        ...
```

Future implementations might include:

```text
JUnitRunner
CMakeCTestRunner
NodeJestRunner
GenericCommandRunner
```

They should all return the same normalized result model.

# 24. Pytest Integration

pytest should produce structured output rather than forcing the app to scrape terminal text.

Preferred options include a machine-readable plugin/output format such as JSON.

The app should capture, for every test:

```text
test_id
display_name
group_id
visibility
status
duration
message
traceback
stdout
stderr
```

Normalized statuses:

```text
PASS
FAIL
ERROR
SKIP
XFAIL
XPASS
TIMEOUT
```

Grading policy determines whether SKIP/XFAIL/XPASS contribute points.

---

# 25. Test Identity

Test identity must remain stable across runs where possible.

Do not use only a human-readable test name.

Recommended:

```text
test_id = normalized pytest node id
```

Example:

```text
tests/hidden/test_edge_cases.py::test_duplicate_priority
```

Optionally add an explicit stable ID in configuration if tests may move between files.

Example:

```yaml
test_ids:
  "tests/hidden/test_edge_cases.py::test_duplicate_priority":
    id: edge_duplicate_priority
```

Stable IDs make historical comparison easier.

---

# 26. Scoring Model

The initial scoring model should be deterministic.

Recommended hierarchy:

```text
Assessment
    |
    +-- Group
          |
          +-- Tests
```

Example:

```text
Programming: 70 points

Basic Correctness:       30
Edge Cases:              20
Efficiency:              15
Interface:                5
```

---

# 27. Test-Level Points

Two valid scoring styles should eventually be possible:

## 27.1 Explicit Test Points

```yaml
tests:
  - id: insert
    group: correctness
    points: 5

  - id: extract
    group: correctness
    points: 10
```

## 27.2 Group-Weighted Equal Tests

```yaml
groups:
  - id: correctness
    points: 30
```

If the group contains 6 tests:

```text
5 points/test
```

The first implementation may use group-weighted equal allocation if that reduces complexity, but the persistent schema should not block explicit test points later.

---

# 28. Partial Credit

For deterministic v1 grading:

```text
passed test => assigned points
failed test => 0 points
```

Group score:

```text
sum(points of passing tests)
```

Possible future scoring types:

```text
threshold
performance curve
rubric/manual
custom plugin
```

Do not implement arbitrary instructor Python scoring hooks in v2.3.2 unless safely isolated and clearly needed.

---

# 29. Efficiency Tests

Efficiency tests can initially be ordinary hidden pytest tests with:

- internal timing assertion;
- problem-size stress test;
- separate group points.

The grading app should not attempt sophisticated benchmarking in v2.3.2.

Environment reproducibility is especially important for runtime-sensitive tests.

# 31. Distinguish Student Failure from Grader Failure

This is critical.

Examples:

### Student Failure

```text
AssertionError
student function returned incorrect result
```

This may legitimately lose points.

### Student Runtime Failure

```text
SyntaxError
ImportError caused by student file
uncaught exception
```

This may legitimately produce a low/zero score depending on policy.

### Grader Failure

```text
missing instructor test file
corrupt container image
grader plugin crash
invalid configuration
```

This must **not** silently become a student zero.

Instead:

```text
Status: GRADER_ERROR
Score: Not finalized
Requires Review: Yes
```

---

# 32. Timeout Handling

If a run exceeds the configured wall-clock limit:

1. terminate the execution;
2. mark the run `TIMEOUT`;
3. retain partial output;
4. retain any completed test results if technically reliable;
5. apply configured timeout scoring policy;
6. flag for review.

Default policy recommendation:

```text
Uncompleted tests receive zero.
Completed tests retain earned credit.
Run is flagged for review.
```

The exact policy should be configurable later if needed.

# 33. Output Capture

# 61. Hidden-Test Protection

The execution model should minimize student-code access to hidden-test assets.

Perfect secrecy may not be achievable in every local container configuration, but the design should avoid unnecessarily exposing test paths/content.

Possible strategies:

- mount tests read-only;
- run through a harness;
- avoid copying hidden tests into exported student workspaces;
- redact hidden test source from reports;
- clean the workspace immediately after execution.

# 87. Concurrency and Resource Control

The scheduler must enforce:


# 88. Determinism

Autograder tests should be deterministic whenever possible.

The app may set a stable environment:

```text
PYTHONHASHSEED
locale
timezone
```

where appropriate.

Tests involving randomness should explicitly seed random generators.

The system cannot guarantee deterministic student code, but grader-controlled nondeterminism should be minimized.

---

# 89. Time and Locale

Container environment should use a fixed locale/timezone unless the assignment explicitly requires otherwise.

Example:

```text
TZ=UTC
LANG=C.UTF-8
```

This avoids host-dependent failures.

# 90. Network Policy

Default:

```text
network = false
```

v2.3.2 should not expose a normal UI switch that casually enables network access unless there is a concrete course need.

Future network-enabled grading should be a deliberate advanced capability.

---

# 91. File-System Policy

Student program should have:

- working-directory access;
- access to its own submission;
- access to required fixtures;
- no access to host user files;
- no access to application database;
- no access to application secrets.

Where possible, instructor tests should be mounted read-only.

---

# 92. Process Policy

Apply a PID/process limit where supported.

This mitigates fork bombs and accidental runaway subprocess creation.

---

# 93. Grading Policy vs Infrastructure Policy

Keep these separate.

### Grading Policy

```text
how many points is a failed test worth?
what happens on timeout?
what happens on syntax error?
```

### Infrastructure Policy

```text
10-second execution limit
512 MB memory cap
no network
```

The scoring engine should not conflate infrastructure errors with academic scoring rules.

---

# 94. Default Scoring Policies

Recommended defaults:

| Condition | Default |
|---|---|
| Passing test | Full test points |
| Failing test | 0 test points |
| Student exception in test | 0 test points |
| Syntax/import error caused by submission | 0 for unreachable tests; flag |
| Timeout | Completed tests retain points; remaining tests 0; flag |
| Missing required file | No automatic finalization; flag |
| Grader/infrastructure error | No score finalization |
| Cancelled | No score finalization |

These should eventually be configurable per assessment if needed.

# 95. Validation Dry Run

The instructor should be able to run:

```text

```

against known instructor reference submissions.

Ideal package may optionally include:

```text

├── reference_good/
└── reference_bad/
```

The app can verify expected outcomes before grading students.

This dramatically reduces accidental bad-test deployments.

It may be optional for the initial implementation, but package validation should be designed to allow it.

# 96. Reference Solution Protection

If an instructor reference solution is included for smoke testing:

- keep it outside student exports;
- do not include it in student-safe reports;
- do not expose its path in normal UI;
- treat it as instructor-sensitive data.

# 97. Test Collection Failure

If pytest cannot collect tests:

```text
TEST_COLLECTION_ERROR
```

No student score should be finalized.

This usually indicates an instructor/autograder problem unless the collection failure is specifically caused by importing student code.

The runner should distinguish these cases as well as practical.

---

# 98. Syntax Errors

A syntax error in the student's required file should produce a clear student-code status.

Example:

```text
Status: SYNTAX_ERROR

priority_queue.py:42
    return x
    ^
SyntaxError: ...
```

The instructor can see the exact traceback.

The score policy may assign zero to affected tests.

---

# 99. Import Errors

Differentiate:

```text
student module import failure
```

from:

```text
grader dependency import failure
```

Only the former is a student execution result.

The latter is an infrastructure/grader failure.

---

# 100. Test Isolation

Ideally, tests should not contaminate each other.

For v2.3.2, ordinary pytest isolation may be sufficient, depending on assignment design.

Future enhancement:

```text
fresh process per test/group
```

if necessary for assignments with mutable global state.

Do not over-engineer this initially.

---

# 101. Performance Considerations

Typical expected workload:

```text
20-100 submissions
seconds per submission
small Python source files
```

The design should comfortably support this workload on an instructor machine or department server.

Do not optimize for tens of thousands of submissions.

---

# 102. Data Privacy

Student submissions are education records.

The app should:

- avoid uploading them to third-party services for this deterministic grading feature;
- keep execution local/institution-controlled unless explicitly configured otherwise;
- avoid putting student identifiers unnecessarily into container image layers or public logs;
- keep reports within normal course data handling practices.

---

# 103. No LLM Dependency

Autograding in v2.3.2 is deterministic.

There is no need to send code to an LLM.

Future LLM-assisted code explanation/review may use the stored submission and grading evidence through separate, explicitly enabled functionality.

---

# 104. Testing Strategy

The feature requires significant automated testing.

At minimum:

1. configuration parser tests;
2. schema validation tests;

# 112. Acceptance Criteria

## AC-1 — Programming Assessment

---

The instructor can upload a package containing:

```text

```

The instructor can upload multiple Python files in one operation.

The app proposes student mappings and requires manual resolution for ambiguous files.

---

Every imported submission has a stable internal ID and SHA-256 hash.

Student code does not execute in the grading application's process.

---

Student code cannot access the network through the default execution environment.

An infinite loop is terminated at the configured limit and recorded as a timeout.

---

## AC-9 — Structured Tests

The app stores individual pytest test outcomes rather than only terminal output.

---

## AC-10 — Scoring

The app calculates a raw score according to configured grading groups/tests.

---

## AC-11 — Error Classification

Student failures and grader/infrastructure failures are not treated as the same condition.

- test results;
- score;
- stdout;
- stderr;
- traceback;
- runtime;
- submission hash;
- grader version.

The instructor can add a manual score adjustment with a required reason.

## AC-14 — Re-run

The instructor can re-run the exact same submission.

---

A new run does not overwrite a prior grading run.

---

## AC-16 — Batch Operation

The instructor can run all ready submissions without opening each student individually.

## AC-17 — Report

The system generates:

- class HTML report.

Closing and reopening the app preserves imported submissions, grader configuration, run results, and adjustments.

The existing full test suite passes.

# 116. Open Implementation Decisions

The following should be resolved during repository-level implementation planning:

1. Which container technology is the best default on the supported deployment platforms?
2. Does the current app already have a worker/job abstraction suitable for batch runs?
3. How are immutable artifacts currently stored?
4. Should autograder packages live inside the course project directory or a central artifact store?
5. What exact pytest structured-output mechanism should be standardized?
6. What level of resource controls is portable across macOS/Linux instructor environments?
7. Should v2.3.2 support only one `.py` file or generic multi-file submissions from the start?
8. How does the existing assessment schema represent max points?
9. Can the existing rubric/outcome schema reuse programming group IDs directly?
10. How should user/reviewer identity be represented in a local application?
11. Should the initial report be generated through existing export infrastructure?
12. Should execution environments be built by the app or only referenced by pre-built image IDs?
13. How should grader-package migrations be handled?
14. Should hidden-test names themselves be considered sensitive in student-facing output?
15. Should a run with student syntax/import failure be automatically finalized or always flagged?

These are implementation decisions rather than reasons to change the high-level architecture.

# 120. Final Recommendation

Implement **v2.3.2 — Programming Submission & Autograding** as a general, source-agnostic grading subsystem.

The first release should focus on:

1. Python;
2. pytest;
3. instructor-uploaded tests/configuration;
4. local student `.py` uploads;
5. batch grading;
6. isolated execution;
7. deterministic scoring;
8. reproducible run metadata;
9. review and manual adjustments;
10. re-runs;
11. CSV/HTML reporting.

Do **not** make Canvas a dependency of the feature.

Do **not** execute student code inside the main app process.

Do **not** overwrite original submissions, raw autograder results, or historical runs.

Do **not** build a student-facing Gradescope clone.

If these boundaries are maintained, v2.3.2 becomes a reusable grading engine that can later accept Canvas submissions, participate in formal regrades, feed ABET/outcome evidence, support code similarity review, and integrate naturally with the planned v2.4 LLM features without requiring a redesign.
