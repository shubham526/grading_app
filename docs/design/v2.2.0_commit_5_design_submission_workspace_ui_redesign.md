# v2.2.0 Commit 5 Design: Submission Evidence Integration and Grading Workspace Redesign

**Status:** Proposed design — implementation not started  
**Release:** v2.2.0 — LaTeX/PDF Submission Ingestion  
**Commit:** 5 of 6  
**Planned commit message:** `feat(v2.2): integrate submission evidence into question-centric grading`  

---

## 1. Purpose

Commit 5 is the UI-integration commit for v2.2.0. Commits 1–4 established the submission backend: strict LaTeX ingestion, explicit PDF-accommodation handling, assistive handwriting transcription, persistent evidence, provenance, and transcription caching. Commit 5 makes those capabilities usable from the desktop grading application and, because the main window must be substantially reorganized to accommodate submission evidence, also modernizes the grading workspace.

The goal is not merely to add a PDF panel to the existing screen. The goal is to turn the main window into a coherent grading workspace in which the instructor can simultaneously:

- inspect the student's actual submission;
- inspect the extracted current-question answer or source/transcription;
- grade against the existing rubric;
- navigate students/questions without losing context;
- resize the workspace to prioritize reading or scoring;
- work offline from persisted evidence when the GPU server is unavailable.

All existing grading semantics must remain unchanged.

---

## 2. Foundational Invariants from Earlier Commits

Commit 5 must preserve the following decisions already established by v2.1.0 and v2.2.0.

### 2.1 Grading workflow invariants

The app supports two manual workflows:

- **Student-by-student:** grade all questions for one student, then move to the next student.
- **Question-by-question:** grade one question across students while keeping the selected question fixed during student navigation.

Question-centric navigation, filtering, progress tracking, and partial-save behavior are already implemented. Commit 5 must reuse those mechanisms rather than create a second navigation system.

Question-centric partial saves must continue to preserve hidden criteria, prior scores/comments, assessment-level metadata, grading progress, selected/counted flags, and ABET metadata.

### 2.2 Submission-policy invariants

Normal submissions are **LaTeX-first and LaTeX-canonical**.

- `.tex` is the canonical submitted source.
- The app compiles it to PDF for display.
- A student-provided PDF may be retained as an optional reference, but it is not canonical.
- PDF-only submissions are not silently treated as normal submissions.

PDF-only ingestion is available only through the explicit generic accommodation path.

For a PDF accommodation:

- the original PDF is authoritative evidence;
- rendered page images are derived evidence;
- selectable PDF text is assistive;
- machine handwriting transcription is assistive only;
- transcription never replaces the original PDF;
- no medical/disability/accommodation reason is stored.

### 2.3 Transcription invariants

The default production handwriting model is `gemma4:31b` through Ollama.

The current deployment architecture is:

```text
Mac grading application
    |
    | HTTP to localhost:11435
    v
SSH tunnel
    |
    v
GPU server Ollama :11434
    |
    v
Gemma 4 31B
```

Commit 5 must not manage SSH credentials, SSH processes, or remote GPU lifecycle. The application sees a configurable Ollama-compatible endpoint. The default UI configuration may target `http://127.0.0.1:11435`, but the backend remains endpoint-configurable.

If inference is unavailable, the original submission must remain gradeable.

### 2.4 Persistence/cache invariants

Commit 4 already supports persistent evidence and offline reopening.

A persisted submission may contain:

```text
submission_evidence/
└── <student_id>/
    ├── source/
    ├── pages/
    ├── compiled/
    ├── submission_meta.json
    ├── extracted_answers.json
    ├── raw_text.txt
    ├── transcription.json
    └── transcription_cache.json
```

Commit 5 must prefer persisted evidence when available.

A valid transcription cache hit must not contact Ollama. Reopening a previously prepared handwritten submission must work even when the tunnel/GPU server is unavailable.

## 3. Scope

### 3.1 Commit 5 will implement

1. A redesigned, responsive main grading window.
2. A resizable submission/evidence workspace.
3. A two-pane document + answer/source layout for both LaTeX and PDF accommodations.
4. Embedded PDF viewing with zoom and page navigation.
5. LaTeX source viewing.
6. Current-question extracted-answer viewing.
7. Assistive transcription viewing with explicit provenance labels.
8. Submission-folder loading and student/submission association.
9. Explicit PDF-accommodation selection.
10. Persistent-evidence loading.
11. On-demand transcription generation/refresh through the configured Ollama endpoint.
12. Background execution for long-running parsing/transcription work so the UI does not freeze.
13. Integration of `submission_meta` and `extracted_answers` into assessment saves.
14. Modernized typography, color, spacing, buttons, cards, and status presentation.
15. Persistent window/splitter preferences.
16. Targeted UI/backend-integration tests required to safely land the feature.

### 3.2 Commit 5 will not implement

Commit 5 will **not** implement:

- LLM-assisted grading or score suggestions;
- LLM-generated feedback;
- submission chat;
- plagiarism/similarity review;
- automatic misconduct decisions;
- automatic OCR outside the established VLM transcription path;
- automatic correction of student text;
- SSH credential management;
- starting/stopping Ollama on the server;
- a built-in remote shell;
- PDF annotation/editing;
- LaTeX editing or recompilation after instructor edits;
- full Overleaf-style collaborative editing;
- full dark-mode support;
- continuous-scroll/high-performance PDF rendering as a hard requirement;
- automatic question-to-PDF-page alignment beyond the evidence already available.

These exclusions keep Commit 5 focused on grading-workspace integration rather than expanding into unrelated features.

## 4. Problems with the Current Main Window

The existing window is functional but was built incrementally before submission evidence became part of the workflow. The current visual structure has several limitations:

- large saturated blue section headers consume vertical space;
- most actions have equal visual weight even though they are not equally frequent;
- the top toolbar is crowded;
- grading configuration and workflow controls occupy large cards;
- the most important area—the actual grading workspace—does not dominate the window;
- the window does not currently contain a first-class submission viewer;
- the existing global font explicitly uses Segoe UI even on macOS rather than allowing the native platform font;
- spacing, borders, disabled colors, and card treatment are visually heavy;
- resizing works at a basic layout level but the screen was not designed around nested resizable work areas.

Commit 5 should improve hierarchy rather than simply reskin existing widgets.

## 5. UX Design Principles

### 5.1 Evidence first, grading second

The student's submission and the rubric must be visible in the same workspace. The grader should not need to repeatedly open external files or switch windows.

### 5.2 One consistent two-pane evidence model

Both LaTeX and PDF-accommodation submissions use the same basic layout:

```text
LEFT                                      RIGHT
Document / rendered evidence              Answer / source / transcription
```

The exact meaning changes by submission type, but the interaction model stays consistent.

### 5.3 Source authority must always be visible

The UI must never visually imply that derived text is equivalent to canonical/authoritative evidence.

Labels must use both text and iconography; color alone is insufficient.

### 5.4 Resize everything that benefits from resizing

The grader must be able to:

- resize the overall application window;
- resize submission workspace vs. grading area vertically;
- resize document vs. text pane horizontally;
- collapse either evidence pane;
- collapse the entire submission workspace when grading without evidence;
- zoom independently inside the document viewer.

### 5.5 Do not block grading on AI availability

A transcription failure is an evidence-assistance failure, not a grading failure.

### 5.6 Avoid hidden expensive work

Cached transcription should load automatically. A new uncached handwriting transcription should be explicitly initiated from the UI rather than unexpectedly sending many pages to the GPU when a student is selected.

### 5.7 Preserve existing semantics

A visual redesign must not alter:

- criterion scoring;
- selected/counted logic;
- best-N-of-M logic;
- total-score calculations;
- ABET outcome calculations;
- analytics;
- semester reports;
- partial-save semantics.

Inside `SubmissionWorkspaceWidget`, create a horizontal `QSplitter` containing:

1. document viewer;
2. answer/source panel.

Both sides are independently collapsible and restorable.

### 6.3 Existing grading splitter

The existing rubric-scroll + question-summary splitter may remain, but its styling and default proportions should be improved. The summary should not dominate vertical space.

## 7. Two-Pane Behavior by Submission Type

### 7.1 Normal LaTeX submission

Default presentation:

```text
LEFT                                         RIGHT
Rendered Submission                          Current Question
Compiled from canonical LaTeX               [Answer] [LaTeX Source]
```

#### Left pane

Shows the app-compiled PDF.

Label:

**Rendered submission**  
`Compiled from canonical LaTeX`

The PDF is a derived rendering. It is not labeled authoritative/canonical.

#### Right pane — Answer tab

In question-centric mode:

- show `extracted_answers[current_question_id]`;
- title the tab with the selected question where practical, e.g. `Q2 Answer`;
- if no answer was mapped, show a clear empty state rather than fabricating one.

In student-centric mode:

- show all extracted answers in natural question order;
- each answer is clearly headed by `Q1`, `Q2`, etc.

#### Right pane — LaTeX Source tab

Shows the canonical `.tex` source read-only in a monospaced source viewer.

Label:

**Canonical LaTeX source**

This tab provides the equivalent of the source side of an Overleaf-style view, but it is read-only because the grading application is not a LaTeX editor.

#### Compile failure behavior

If LaTeX extraction succeeds but compilation fails:

- keep the Answer and LaTeX Source tabs usable;
- show a non-blocking warning in the document pane;
- display compile diagnostics through a details action;
- grading remains possible from the canonical source/extracted answer.

### 7.2 PDF accommodation with handwriting transcription

Default presentation:

```text
LEFT                                         RIGHT
Original PDF                                 Current Question
AUTHORITATIVE                                [Answer] [Full Transcription]
                                             Assistive — Gemma 4 31B
```

#### Left pane

Shows the original persisted submitted PDF.

Label:

**Original submitted PDF**  
`Authoritative evidence`

#### Right pane — Answer tab

Shows the current question's derived answer when question mapping succeeded.

Label:

`Assistive text — verify against original`

#### Right pane — Full Transcription tab

Shows full page-aligned transcription and provenance.

At minimum show:

- model;
- status;
- whether the result came from cache;
- page number;
- transcription text;
- `Assistive only` label.

Do not clutter the default view with low-level token/timing metadata. Detailed provenance can be exposed through a details button/dialog.

### 7.3 PDF accommodation with sufficient selectable text

Default presentation:

```text
LEFT                                         RIGHT
Original PDF                                 Current Question
AUTHORITATIVE                                [Answer] [Extracted Text]
```

Do not describe selectable-text extraction as AI transcription.

### 7.4 PDF accommodation with no usable transcription

The left pane remains fully usable.

The right pane displays one of the explicit states:

- `Transcription not generated`
- `GPU/Ollama unavailable`
- `Model unavailable`
- `Generation stopped at limit`
- `Output rejected due to repetition`
- `Transcription failed`

When appropriate, show a **Generate Transcription** or **Retry Transcription** button.

No state may imply that the original submission is unavailable merely because assistive text is unavailable.

### 7.5 No submission loaded

The submission workspace should use a purposeful empty state:

```text
No submission loaded for this student.

[Load Submissions Folder]
```

If persisted evidence exists, it should be loaded before showing this state.

## 8. Embedded Document Viewer

Create a reusable `PdfDocumentViewer` rather than embedding document-view logic directly in `main_window.py`.

### 8.1 Technology decision

Use **PyMuPDF** for display rendering because it is already a v2.2 dependency and avoids introducing QtWebEngine or relying on optional QtPdf packages.

The UI viewer must render from the actual PDF path. It should not treat the standardized 200-DPI transcription PNG as the only viewable representation.

This distinction is important:

- 200-DPI persisted pages are stable derived evidence/transcription inputs;
- interactive display rendering is a UI concern and may re-render the current PDF page at the requested zoom.

### 8.2 Viewer controls

Toolbar:

```text
[−] [100%] [+]   [Fit Width] [Fit Page]   [◀] Page 1 / 6 [▶]
```

Required controls:

- zoom out;
- zoom percentage;
- zoom in;
- fit width;
- fit page;
- previous page;
- next page;
- current page / total pages.

Recommended zoom range:

- minimum: 25%;
- maximum: 400%;
- step: 10–25% depending on current scale.

### 8.3 Keyboard behavior

Use standard Qt key sequences where possible.

Recommended:

- `Cmd/Ctrl + +` — zoom in;
- `Cmd/Ctrl + -` — zoom out;
- `Cmd/Ctrl + 0` — fit page or reset zoom;
- page navigation buttons remain explicit.

Keyboard shortcuts must not conflict with grading navigation shortcuts.

### 8.4 Rendering behavior

For v2.2.0, a paged viewer is acceptable and preferred over a complicated continuous-scroll implementation.

Only the current page needs to be rendered at high resolution. The viewer may cache a small number of recently rendered pages/zoom levels.

Resizing in Fit Width/Fit Page mode should use a short debounce so the page is not rerendered for every individual resize pixel.

### 8.5 Error behavior

Malformed/unavailable PDFs should produce an in-pane error state, not crash the main window.

## 9. Answer and Source Viewer

Create a dedicated `SubmissionTextPanel`/`AnswerSourcePanel`.

Responsibilities:

- display the current extracted answer;
- display all answers in student-centric mode;
- display canonical LaTeX source;
- display selectable PDF text;
- display full assistive transcription;
- show source/provenance labels;
- expose Open Original/Open Source actions;
- update when current student or question changes.

Text views are read-only.

### 9.1 Typography

- normal extracted answer: readable proportional UI font or neutral reading font;
- raw LaTeX: native monospace font;
- transcription: readable text with preserved line breaks and math notation;
- metadata: smaller secondary text.

Do not attempt mathematical re-typesetting in Commit 5. The rendered PDF is available beside the text whenever exact mathematical appearance matters.

## 10. Explicit PDF-Accommodation Flow

The UI must preserve the backend rule that PDF-only submissions are not silently promoted to normal submissions.

### 10.1 Normal folder loading

**Load Submissions Folder** discovers normal LaTeX submissions using the existing matcher.

A PDF-only file is not automatically treated as a valid normal submission.

### 10.2 Add PDF Accommodation

Provide a separate explicit action:

**Add PDF Accommodation…**

Flow:

1. choose the student from the current roster/student list;
2. choose the submitted PDF;
3. confirm generic `PDF accommodation` mode;
4. ingest/persist the original PDF;
5. do not request or store a reason;
6. load cached transcription if one exists;
7. if no cache exists, show a Generate Transcription action.

The UI should never contain a text box asking why the student has an accommodation.

### 10.3 Persisted accommodation reopening

Once persisted, `submission_meta.submission_mode` and generic `accommodation_mode` are sufficient to reconstruct the correct UI mode on later launches.

## 11. Submission Folder Loading and Student Association

### 11.1 New main-window action

Add:

**Load Submissions**

This should select an assignment submissions directory and run discovery only.

Do not compile/transcribe every student synchronously during folder selection.

### 11.2 Lazy preparation

Preferred strategy:

- discover submission records immediately;
- map them to student IDs;
- prepare/compile an uncached student's submission when that student is first viewed;
- persist the result;
- reuse persisted evidence thereafter.

This avoids blocking the UI for an entire class during initial folder loading.

### 11.3 Mapping

Use the existing student-ID normalization and roster model.

Maintain a mapping such as:

```python
self.submission_records_by_student_id: dict[str, SubmissionRecord]
```

Persisted evidence takes precedence over reprocessing the raw submission when it is still valid for display/reopening.

### 11.4 Missing and unmatched submissions

Do not interrupt grading with repeated modal dialogs.

Use non-blocking status indicators such as:

- `Submission ready`
- `No submission found`
- `Submission not yet prepared`
- `Persisted evidence loaded`

A one-time summary after folder discovery may report unmatched/missing IDs.

## 12. Evidence Storage Location

Commit 5 needs a deterministic persistent evidence root.

### 12.1 Proposed rule

When an assessment folder is selected:

```text
<assessments_dir>/submission_evidence/
```

becomes the default evidence root.

This keeps:

- student source submissions read-only;
- assessment JSON files and derived grading evidence together;
- the grading session portable as a directory tree.

### 12.2 If no assessment folder is selected

When the user first loads submissions, prompt for/select an assessment folder before persistent preparation begins.

The old student-centric manual workflow may continue to work without an assessment folder if no submission evidence is being used.

### 12.3 Do not store evidence only in `/tmp`

Temporary rendering remains acceptable internally, but UI-integrated prepared evidence must be persisted before it is treated as the student's prepared submission workspace.

## 13. Background Work and UI Responsiveness

Long-running work must not run on the Qt GUI thread.

Potentially slow operations include:

- LaTeX compilation;
- PDF rendering;
- Ollama preflight;
- Gemma page transcription;
- multi-page persistence/hash work.

### 13.1 Worker architecture

Add a UI worker layer, for example:

```text
src/ui/workers/
    __init__.py
    submission_worker.py
```

Use `QObject` + `QThread` or `QRunnable` + `QThreadPool`.

The worker may call the already-tested submission APIs. It must not duplicate parser/transcription logic.

### 13.2 Signals

Suggested signals:

```text
started(student_id, operation)
progress(student_id, message)
completed(student_id, parsed_submission)
failed(student_id, error_message)
```

### 13.3 Stale-result protection

If the user changes students while a background operation is running, its result must never replace the currently displayed student's evidence.

Use a request/job token or verify the returned `student_id` against the current student before updating widgets.

The completed job may still persist its result for later use.

### 13.4 Interaction while transcription runs

The original PDF must remain viewable while transcription runs.

Only the text/transcription part should show a busy state such as:

`Generating assistive transcription…`

Do not freeze the rubric grading controls.

## 14. Transcription UX and Remote Ollama Configuration

### 14.1 Cache-first behavior

When a PDF accommodation is opened:

1. load persisted evidence;
2. if successful cached transcription exists, display it immediately;
3. if no successful cache exists, show `Transcription not generated`;
4. do not automatically launch a new expensive model job merely because the student was selected.

### 14.2 Generate/refresh action

Provide:

- **Generate Transcription** when none exists;
- **Refresh Transcription** when a result already exists.

Refreshing must preserve all grading scores/comments.

### 14.3 Connection settings

Add a small Submission/AI settings dialog or section accessible through Settings.

Fields:

```text
Ollama endpoint:  http://127.0.0.1:11435
Model:            gemma4:31b
[Test Connection]
```

Do not expose all low-level inference settings in the main window. Production defaults from the backend remain authoritative unless advanced configuration is explicitly needed later.

Do not store API keys in ordinary project JSON. Existing environment-variable support may remain the credential path.

### 14.4 Status display

Examples:

```text
Transcription: Cached · gemma4:31b
Transcription: Ready · gemma4:31b
Transcription: Not generated
Transcription: GPU server unavailable
```

Status text must distinguish `cached` from `generated now` when useful, but neither status changes evidentiary authority.

## 16. Visual Design System Refresh

### 16.1 Font

Remove the hard-coded global `Segoe UI` font.

Use Qt's native application/system font. On macOS this gives the native system UI face; other platforms use their native/fallback UI font.

Use native monospace for source views.

Recommended hierarchy:

```text
App title                 17–19 px / semibold
Section title             13–15 px / semibold
Normal UI                 platform default ~13 px
Secondary metadata        11–12 px
```

Avoid oversized bold labels throughout the screen.

### 16.2 Color palette

Replace the current saturated Material-indigo-everywhere treatment with a quieter neutral interface and a restrained indigo/blue accent.

Proposed semantic palette:

```text
primary                   #3B5CCC
primary_hover             #304DAF
primary_soft              #EEF2FF
background                #F6F7F9
surface                   #FFFFFF
surface_alt               #F9FAFB
text_primary              #1F2937
text_secondary            #667085
border                    #D9DEE7
divider                   #E6E9EF
success                   #2E7D5B
warning                   #A66B16
error                     #B94A48
disabled_text             #98A2B3
disabled_background       #EEF1F5
```

Exact values may be adjusted during visual implementation, but the hierarchy should remain neutral-first and accent-second.

### 16.3 Buttons

Define button roles:

- **Primary:** save, main load/confirm actions;
- **Secondary:** outlined/neutral navigation and utilities;
- **Danger:** only destructive operations;
- **Toolbar/icon:** low-emphasis controls such as zoom and pane collapse.

Do not render all actions as filled indigo buttons.

### 16.4 Cards and section headers

Remove large solid-blue title bars from ordinary cards.

Prefer:

```text
Section title
────────────────
content
```

or a white surface with subtle border and compact header.

### 16.5 Spacing

Use an 8-pixel spacing system where practical:

- 4 px micro spacing;
- 8 px normal control gap;
- 12–16 px section padding;
- 20–24 px major separation.

Avoid arbitrary per-widget spacing values.

### 16.6 Status bar

Restyle the status bar to a neutral/light surface with a top border rather than a large solid-indigo strip.

Continue displaying:

- application status;
- auto-save state;
- version.

Submission/transcription status should primarily live near the submission workspace, not only in the global status bar.

## 17. Resizing, Collapsing, and Preference Persistence

### 17.1 Main-window resizing

No fixed central widths/heights.

Use `QSizePolicy.Expanding` and nested layouts/splitters.

Suggested minimum application size:

```text
~850–900 × 600
```

Suggested default size:

```text
~1400 × 900
```

The final default should be bounded to available screen geometry.

### 17.2 Splitter behavior

Persist and restore:

- outer submission/grading splitter sizes;
- document/text splitter sizes;
- grading/summary splitter sizes;
- window geometry;
- maximized state where appropriate.

Use `QSettings` so these are user preferences, not assignment data.

### 17.3 Pane collapse

Each evidence pane header gets a compact collapse control.

Collapsing must remember the prior non-zero splitter size so restoring a pane returns it to a useful width.

### 17.4 No layout breakage

At narrower widths, low-priority toolbar actions should live in menus rather than being squeezed off-screen.

## 18. Current Student / Current Question Synchronization

The submission workspace must be driven from the same navigation state used for grading.

### 18.1 Student changes

When current student changes:

1. preserve the existing dirty-save navigation behavior;
2. update current assessment;
3. load persisted submission evidence for the new student if available;
4. otherwise prepare their discovered LaTeX submission lazily;
5. update both document and text panes;
6. keep current question fixed in question-centric mode.

### 18.2 Question changes

When current question changes:

1. preserve existing dirty-save behavior;
2. filter criterion widgets using existing v2.1 logic;
3. keep the current student unless the existing workflow chooses otherwise;
4. update the right answer pane to the selected question;
5. do not needlessly reload/reparse the document.

### 18.3 Student-centric mode

The submission viewer still appears.

The document pane shows the full document and the answer pane shows all extracted answers rather than pretending there is a current question.

## 19. Assessment Save Integration

Commit 4 provides:

```python
assessment_submission_fields(parsed_submission)
```

Commit 5 must use it.

### 19.1 Full student-centric save

Before writing the assessment JSON:

```python
assessment_data.update(
    assessment_submission_fields(self.current_parsed_submission)
)
```

only when a submission is loaded.

### 19.2 Question-centric partial save

After merging the visible criterion update into the full assessment object, attach/refresh:

```text
submission_meta
extracted_answers
```

without altering hidden criterion data.

### 19.3 Auto-save

If a submission is currently loaded, auto-save should include the same supporting submission fields.

### 19.4 Loading an existing assessment

If the assessment contains `submission_meta.evidence_dir`, attempt to restore persisted evidence from that location when safe/available.

Failure to restore evidence must not invalidate an otherwise valid assessment.

### 19.5 Scoring isolation

`submission_meta` and `extracted_answers` must remain display/support metadata and must not enter scoring or ABET calculations.

## 20. Proposed Main-Window State Additions

`RubricGrader` will likely need state similar to:

```python
self.submissions_dir = None
self.evidence_dir = None
self.submission_records_by_student_id = {}
self.current_parsed_submission = None
self.current_submission_student_id = None
self.current_submission_job_id = None
```

Inference configuration should be represented separately, for example:

```python
self.submission_inference_config = {
    "base_url": "http://127.0.0.1:11435",
    "model": "gemma4:31b",
}
```

Do not mix these values into grading configuration (`best_scores`, selected questions, etc.).

## 22. Main-Window Refactoring Rule

Commit 5 should keep `RubricGrader` as the orchestration/controller layer, not the implementation home for every visual component.

`main_window.py` should own:

- current rubric/student/question/workflow state;
- submission-record association;
- save/load orchestration;
- navigation coordination;
- starting background jobs;
- connecting worker results to the workspace.

Child widgets should own rendering and local presentation details.

This reduces the risk of making future v2.3/v2.4 features harder to integrate.

---

## 23. Error and Warning Presentation

Prefer non-modal warnings for submission-specific issues.

Examples:

```text
⚠ Compiled PDF unavailable — canonical LaTeX source is still available.
⚠ Assistive transcription unavailable — grade from the original PDF.
⚠ No extracted answer mapped to Q3 — inspect the full source.
```

Reserve modal dialogs for actions requiring a decision, such as:

- unsaved grading changes before navigation;
- selecting a PDF accommodation;
- destructive refresh/replace confirmation if needed;
- unrecoverable configuration problems.

Do not show repetitive modal warnings each time a student without a submission is selected.

## 24. Accessibility and Interaction Requirements

1. Do not encode authority/status by color alone.
2. All icon-only controls require tooltips/accessibility text.
3. Keyboard focus order should follow visual order.
4. Text must remain selectable/copyable in source/transcription panes.
5. Zoom controls must be usable without a mouse.
6. Disabled states must retain readable contrast.
7. Splitter handles should be wide enough to discover and drag comfortably.
8. Long student names/file paths must elide rather than force the window wider.

---

## 25. Performance Requirements

The UI should feel immediate for navigation when evidence is cached.

Targets are qualitative rather than strict benchmarks:

- changing current question: no submission reparse;
- changing to a student with persisted evidence: local disk load only;
- cache-hit handwriting: no Ollama call;
- uncached transcription: UI remains interactive while inference runs;
- window resize: no uncontrolled repeated full-document rendering.

---

## 26. Security and Privacy Requirements

1. Never store accommodation reasons or medical/disability details.
2. Never expose Ollama directly to the public network as part of app setup.
3. Do not manage/store SSH passwords in the grading app.
4. Open local files with Qt's local-file APIs, not shell interpolation.
5. Continue respecting existing symlink/path-safety checks in submission ingestion.
6. The UI must not silently substitute assistive transcription for the authoritative original PDF.
7. Inference endpoint/model details are technical provenance, not evidence authority.

## 31. Decisions to Lock Before Implementation

The following are the proposed design choices for implementation. They should be treated as the default plan unless explicitly changed before coding.

### Decision 1 — Keep two panes for both submission types

**Yes.**

- LaTeX: compiled PDF | Answer + canonical source tabs.
- PDF accommodation: authoritative original PDF | Answer + transcription/extracted-text tabs.

### Decision 2 — Use a read-only Overleaf-inspired LaTeX view

**Yes.**

The app is a grading tool, not an editor. Source is inspectable but not editable.

### Decision 3 — Use PyMuPDF for embedded PDF display

**Yes.**

This avoids a new browser/QtPdf dependency and supports zoom/page rendering consistently.

### Decision 4 — Use nested `QSplitter`s

**Yes.**

This is the primary mechanism for user-controlled workspace proportions.

### Decision 5 — Persist layout preferences with `QSettings`

**Yes.**

Window/splitter state is a user preference and should not be stored in rubric/assessment data.

### Decision 6 — Cache hit is automatic; new transcription is explicit

**Yes.**

Cached text loads automatically. An uncached Gemma run begins only after Generate Transcription is requested.

### Decision 7 — Do not manage SSH in v2.2.0

**Yes.**

The UI configures an endpoint; the user/environment manages the secure tunnel.

### Decision 8 — Evidence is stored under the assessment workspace

**Yes.**

Default:

```text
<assessments_dir>/submission_evidence/
```

### Decision 9 — Keep continuous PDF scrolling out of scope

**Yes for v2.2.0.**

A reliable paged viewer with zoom/fit controls is sufficient. Continuous/lazy scroll can be added later if useful.

### Decision 10 — No grading logic rewrite

**Absolutely.**

Commit 5 changes presentation and submission orchestration, not scoring semantics.
