# v2.3.6 Design Overview — Distributed CAM Integration & Grade Publication

**Parent release family:** `v2.3.6 — Distributed CAM Integration & Grade Publication`
**Repository:** `grading_app`
**Status:** Definitive architecture overview
**Date:** August 21, 2026
**Depends on:** v2.3.5 Structured Regrade Adjudication & CAM Integration
**CAM counterpart:** CAM v0.7.1 Distributed Grading Bridge & Normal Grade Publication
**Direct Canvas dependency:** None
**Direct Microsoft dependency:** None

---

## 1. Purpose

v2.3.6 completes the Grading App side of the Fall 2026 CAM integration.

The target deployment is:

```text
INSTRUCTOR MAC

OneDrive / Microsoft
       ↕
      CAM
       ↕
CAM local integration endpoint
       ↕
───────────────────────────────
SHARED UNIVERSITY LINUX SERVER
durable grading relay
───────────────────────────────
       ↕
Grading App local integration endpoint
       ↕
   Grading App

TA MAC
```

The release family has two operational goals:

1. make the existing v2.3.5 regrade bridge work reliably across separate machines; and
2. allow ordinary finalized academic grades to be handed to CAM for safe, policy-aware Canvas publication.

The Grading App remains a grading application.

CAM remains the Canvas/Microsoft automation service.

---

## 2. Superseded v2.3.6 Designs

The previous direct-Canvas v2.3.6 family is superseded and must not be implemented as written:

```text
v2.3.6_canvas_grading_integration_overview
v2.3.6.1_canvas_connection_course_sync_design
v2.3.6.2_canvas_submission_file_sync_design
v2.3.6.3_canvas_grade_feedback_publishing_design
v2.3.6.4_canvas_reconciliation_audit_design
```

Those designs assumed the Grading App would:

```text
store a Canvas API token
build its own CanvasClient
sync Canvas courses/roster/assignments directly
download Canvas submissions directly
write Canvas grades/comments/rubrics directly
reconcile directly against Canvas
```

That is no longer the chosen architecture.

Useful domain concepts from those documents may be reused, but they are not implementation authority.

---

## 3. Final Ownership Boundary

```text
Grading App
    owns:
        raw academic grades
        grading evidence
        grading-record versions
        finalization
        regrade adjudication
        local audit/provenance
        publication intent

CAM
    owns:
        Canvas credentials
        Canvas mappings
        Canvas reads
        Canvas writes
        publication preflight
        late-policy-aware target calculation
        conflict detection
        post-write verification
        operational Canvas audit

Microsoft
    owns:
        late-day policy/accounting
        regrade intake/status
        student-facing administrative workflow

Linux relay
    owns:
        nothing except durable message transport
```

---

## 4. Architectural Invariants

1. The Grading App has no Canvas token.
2. The Grading App does not call Canvas.
3. The TA does not need CAM access.
4. The TA does not need the instructor's Canvas credentials.
5. The Linux server does not run CAM or the Grading App.
6. The Linux server is a durable mailbox only.
7. Each application works against its own local filesystem integration endpoint.
8. Internal processing directories never synchronize across machines.
9. Cross-machine event replay is idempotent.
10. Endpoint sleep/offline state causes delay, not data loss.
11. Grading App raw score may legitimately differ from Canvas published score.
12. CAM applies authoritative settled policy; Grading App never does.
13. Canvas publication success requires CAM reread verification.
14. Publication failure never rolls back academic grading truth.

## 5. Sub-Releases

### v2.3.6.1 — Distributed CAM Bridge

Purpose:

```text
Grading App local bridge
        ↕
shared Linux relay
        ↕
CAM local bridge
```

Provides:

- SSH/rsync relay transport;
- automatic push/pull;
- atomic relay arrival;
- no destructive synchronization;
- endpoint-local claim/staging/processed state;
- offline/sleep recovery;
- relay health;
- manual Sync/Test controls;
- regrade traffic across two Macs;
- generic transport support for later normal-grade events.

No normal-grade publication yet.

---

### v2.3.6.2 — Normal Grade Publication Handoff

Purpose:

```text
finalized academic grades
        ↓
grade_publication_request
        ↓
CAM
        ↓
policy-aware Canvas publication
        ↓
grade_publication_result
        ↓
Grading App
```

Provides:

- single/batch finalized-grade selection;
- publication preview;
- immutable request snapshot;
- grading-record/version provenance;
- durable local outbox;
- relay delivery;
- queued/pending state;
- CAM result ingestion;
- mixed batch outcomes;
- no late-policy calculation;
- no Canvas calls.

---

### v2.3.6.3 — Publication Reconciliation & Audit

Purpose:

> Make local academic state and CAM-reported operational publication state explainable without pretending the raw grade must equal the Canvas grade.

Uses:

```text
L = current local raw academic state
R = immutable publication-request academic snapshot
T = CAM-computed Canvas target
C = CAM-verified Canvas state
```

Provides:

- stale-request detection (`L` vs `R`);
- expected-vs-verified operational reconciliation (`T` vs `C`);
- policy-adjusted score visibility;
- conflict/blocked/failed state;
- retry/republication workflow;
- publication audit trail;
- cross-linking to grading records, regrades, requests, and CAM results.

No direct Canvas reconciliation.

---

## 6. Why Three Sub-Releases

The boundaries are intentionally independent:

```text
Transport correctness
        ↓
Publication correctness
        ↓
Operational explainability/reconciliation
```

A faulty transport layer must not be debugged simultaneously with grade-write semantics.

A normal publication path must be proven before adding richer reconciliation UI.

---

## 7. What Is Not in v2.3.6

The following are deliberately outside the family:

```text
direct Canvas authentication
direct Canvas API calls
Canvas course/roster/assignment sync in the Grading App
Canvas submission/file downloading
Canvas comments/feedback publishing
Canvas rubric write-back
absence handling
late-day accounting
systematic/batch academic corrections
full live Canvas reconciliation from the Grading App
```

If automatic Canvas submission import is later desired, it should be a separate CAM-mediated feature with an artifact-transfer design. It should not be smuggled into the JSON event relay.

## 8. Regrade Interaction

v2.3.5 remains academic authority for regrades.

v2.3.6.1 changes transport only:

```text
CAM regrade_request_delivery
→ Linux relay
→ Grading App

Grading App regrade_decision
→ Linux relay
→ CAM
```

The regrade academic contract does not change.

---

## 9. Normal Grade Interaction

For ordinary grading:

```text
TA grades
→ Grading App finalizes raw grade
→ publication request
→ Linux relay
→ CAM
→ Canvas/policy preflight
→ safe write
→ verification
→ result
→ Linux relay
→ Grading App
```

The TA can finish grading even if the instructor Mac is asleep.

Only Canvas publication is delayed until CAM processes the queued event.

---

## 10. Raw vs Published Score

Example:

```text
Grading App raw academic score = 90
Settled late penalty          = 20%
CAM Canvas target             = 72
Canvas verified score         = 72
```

This state is healthy.

Therefore v2.3.6 must never define:

```text
local raw score != Canvas score
→ conflict
```

Instead it distinguishes:

```text
academic truth
policy-adjusted publication target
actual verified Canvas state
```

---

## 11. Shared Contract Philosophy

v2.3.6 uses versioned immutable bridge events.

New normal-grade event:

```text
grade_publication_request
```

CAM returns:

```text
grade_publication_result
```

Exact schemas must match CAM v0.7.1.

v2.3.5 regrade schemas remain frozen.

No release may silently reinterpret an existing schema-v1 regrade payload.

---

## 12. User Experience

Routine TA workflow after v2.3.6:

```text
Open Grading App
→ integration sync runs
→ regrades appear if any
→ grade normally
→ finalize grades
→ Prepare Publication
→ review selected finalized records
→ Send to CAM
→ status = Queued
→ continue working
```

Later:

```text
CAM result arrives
→ status updates automatically
→ Synced / Awaiting Policy / Conflict / Blocked / Failed
```

The TA does not open CAM.

---

## 13. Local vs Relay State

Each Mac owns local processing state.

Example Grading App local root:

```text
CourseAutomationIntegration/
    to-grading/
    from-grading/
    processed/
    quarantine/
    .staging/
    .event-claims/
```

Linux relay:

```text
grading_bridge/
    schema-v1/
        cam-to-grading/
        grading-to-cam/
```

Only finalized transport messages move.

Never synchronize:

```text
processed/
quarantine/
.staging/
.event-claims/
```

---

## 14. Security

- SSH key authentication preferred;
- no plaintext server password in app config;
- no Canvas/Microsoft tokens on TA Mac for this integration;
- no secrets in relay events;
- relay permissions restricted to authorized users/group;
- event content treated as untrusted data;
- never execute files received through the relay;
- no raw student artifacts in this JSON relay.

## 16. Completion Criteria

v2.3.6 is complete only when:

- [ ] Grading App and CAM communicate across separate Macs through the Linux relay;
- [ ] relay outages do not lose events;
- [ ] duplicate transfers do not duplicate logical work;
- [ ] regrades work through the relay with no academic contract change;
- [ ] finalized ordinary grades can be submitted to CAM in single/batch form;
- [ ] grading-record/version provenance is immutable;
- [ ] Grading App never computes late penalties;
- [ ] CAM results return and correlate to exact local records;
- [ ] mixed publication outcomes are represented correctly;
- [ ] raw score vs policy-adjusted published score is modeled correctly;
- [ ] publication conflict never mutates academic history;
- [ ] operational audit explains what was requested and what CAM verified;
- [ ] full repository regression suite passes.

## 18. Resulting v2.3.6 Contract

After v2.3.6:

```text
The TA uses only the Grading App.

The instructor runs CAM on the instructor Mac.

The shared Linux server is a durable transport relay.

Regrade events and normal-grade publication events cross the relay
without requiring the two applications to run on the same machine.

The Grading App remains academic truth.

CAM remains Canvas publication truth.

The Grading App can request publication but does not know or calculate
course-policy adjustments.

CAM computes the correct Canvas target, verifies the write, and returns
operational results.

A raw academic grade and Canvas-published grade are allowed to differ
when CAM has applied authoritative course policy.

The Grading App preserves exactly what it graded, exactly what it asked
CAM to publish, and exactly what CAM reported happened.
```
