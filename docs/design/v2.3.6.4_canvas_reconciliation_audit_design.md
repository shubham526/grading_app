# v2.3.6.4 Design — Canvas Reconciliation, Conflict Detection & Audit

**Release:** `v2.3.6.4 — Canvas Reconciliation, Conflict Detection & Audit`  
**Parent feature:** `v2.3.6 — Canvas Grading Integration`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Date:** August 18, 2026  
**Depends on:** v2.3.6.1, v2.3.6.2, v2.3.6.3  
**Completion meaning:** Reliable two-way grading integration is complete after this release.

---

## 1. Purpose

v2.3.6.4 makes Canvas synchronization safe enough to rely on operationally.

It introduces a three-way reconciliation model:

```text
last synchronized Canvas baseline
             vs
current grading-app state
             vs
current Canvas state
```

The app detects divergence rather than treating either system as universally authoritative.

It provides:

- conflict classification;
- newer-attempt detection;
- grade mismatch detection;
- assignment/configuration drift detection;
- explicit resolution actions;
- sync/publish audit history;
- optional Canvas grade-history enrichment when permissions allow.

The central rule:

> **Never silently overwrite a state that changed outside the grading app.**

---

## 2. Why Reconciliation Is Required

Without reconciliation:

```text
App grade = 76
Canvas grade = 79
```

could be caused by:

- TA manually edited Canvas;
- instructor edited Canvas;
- regrade was applied only in one system;
- app publish partially failed;
- newer submission attempt was graded differently;
- assignment points changed;
- stale local cache.

Blind "publish all" would destroy information.

v2.3.6.4 makes those situations explicit.

---

## 3. Goals

v2.3.6.4 shall:

1. maintain last-synced Canvas baselines;
2. fetch current Canvas state;
3. compare local/current/baseline state;
4. classify conflicts deterministically;
5. detect Canvas-only grade changes;
6. detect local-only grade changes;
7. detect both-sides changes;
8. detect newer submission attempts;
9. detect assignment points/configuration drift relevant to grades;
10. expose resolution UI;
11. allow adopt-Canvas or publish-local decisions explicitly;
12. preserve history of every resolution;
13. support batch reconciliation;
14. integrate with publish queue;
15. maintain course/assessment/student-level audit trail;
16. optionally enrich conflicts using Canvas Gradebook History / Grade Change Log when permissions allow;
17. function correctly without privileged history APIs.

---

## 4. Non-Goals

v2.3.6.4 shall not:

- automatically decide that local is always correct;
- automatically decide that Canvas is always correct;
- manage absences/late days;
- recreate Microsoft regrade intake;
- change posting policy;
- require admin-only Canvas permissions;
- auto-resolve true conflicts;
- rewrite historical grading runs.

---

## 5. Three-Way Reconciliation Model

Define:

```text
B = last synchronized Canvas baseline
L = current local intended/final state
C = current Canvas state
```

For grade value:

### In sync

```text
L == B == C
```

### Local-only change

```text
L != B
C == B
```

Safe candidate for publication.

### Canvas-only change

```text
L == B
C != B
```

Canvas changed externally. Do not overwrite.

### Both changed, converged

```text
L != B
C != B
L == C
```

No effective conflict; update baseline after verification.

### True conflict

```text
L != B
C != B
L != C
```

Requires explicit resolution.

This model should apply to normalized values rather than raw string formatting.

---

## 6. Reconciliation Dimensions

At minimum compare:

```text
grade/score
submission attempt
selected submission artifact identity
assignment points_possible
assignment mapping
student mapping
excused state where observed
```

Optional:

```text
feedback/comment publication fingerprints
rubric results
```

---

## 7. Grade Normalization

Canvas may expose:

```text
score
grade
```

Normalize comparison according to assignment grading type.

For points-based assignments, compare numeric score with a safe numeric tolerance.

Do not compare `"88"` and `"88.0"` as a conflict.

For non-numeric grading types, define explicit normalization.

## 15. Resolution Actions

### Adopt Canvas

Use current Canvas state as the local effective grade only if the instructor intentionally chooses that action.

Do not rewrite original historical grading evidence.

Create a grade-revision/import event explaining the adopted external change.

### Keep/Publish Local

Create/return item to publish queue using current local approved grade.

Require confirmation.

### Pull Newer Attempt

For newer submission conflicts:

```text
Pull Canvas Attempt N
```

Then route through canonical ingestion/grading.

### Investigate

Leave unresolved and block publish.

---

## 16. Adopting a Canvas Grade

Adopting Canvas should create an auditable local revision:

```text
reason_type = external_canvas_change_adopted
baseline = 76
adopted = 79
actor = instructor
```

Never simply overwrite the local database field with no provenance.

---

## 17. Newer Attempt Conflict

Example:

```text
App grade source:
Canvas attempt 1

Current Canvas:
attempt 2 submitted after grading
```

Classification:

```text
NEWER_CANVAS_ATTEMPT
```

Default resolution:

```text
Pull attempt 2
Review/grade it
Then reconcile
```

Do not publish attempt-1 grade over attempt 2 automatically.

---

## 18. Points-Possible Drift

Example:

```text
Baseline Canvas points: 70
Current local max:       70
Current Canvas points:  100
```

Classification:

```text
POINTS_POSSIBLE_DRIFT
```

Block ordinary publication until assignment/local scoring relationship is resolved.

Do not silently rescale.

---

## 19. Assignment Mapping Drift

If mapped Canvas assignment is deleted, replaced, or explicitly remapped:

```text
ASSIGNMENT_MAPPING_CONFLICT
```

Require instructor resolution.

Do not infer a replacement assignment by similar name.

---

## 20. Student Mapping Drift

If local student mapping no longer matches current Canvas user/enrollment state:

```text
STUDENT_MAPPING_CONFLICT
```

This is especially important before writes.

---

## 21. Baseline Update Rules

Update the reconciliation baseline only after:

- successful read sync with accepted state;
- verified publish;
- explicit adopt-Canvas resolution;
- confirmed converged state.

Do not update baseline before a failed write, because that would hide the mismatch.

---

## 22. Canvas Grade History Enrichment

Canvas exposes Gradebook History and Grade Change Log APIs, but access may depend on course/account permissions.

If available, use them to enrich:

```text
who changed grade
when changed
old/new values
```

Example conflict detail:

```text
Canvas changed:
Aug 18, 2026 8:17 PM
Grader: <if authorized data is available>
```

But reconciliation correctness must **not depend** on history access.

The B/L/C snapshot model is sufficient without privileged APIs.

---

## 23. Permission-Limited History

If history endpoint returns permission denied:

```text
History unavailable with current Canvas permissions.
Reconciliation still uses current-state comparison.
```

Do not treat that as overall reconciliation failure.

---

## 24. Canvas Audit Store

Maintain local records for:

```text
connection tests
course sync runs
roster syncs
assignment syncs
submission pulls
file downloads
publish jobs
publish items
verification results
reconciliation runs
conflict resolutions
baseline updates
```

This is the operational history of integration activity.

---

## 25. Audit Invariants

Audit history should be append-only under normal use.

Corrections create new events.

Do not delete failed publish attempts just because retry later succeeds.

## 29. Safe Batch Actions

Allowed:

```text
Publish all LOCAL_ONLY_CHANGE items
Acknowledge all IN_SYNC items
```

Not allowed:

```text
Auto-resolve all conflicts by choosing local
```

True conflicts require explicit policy/action.

## 30. Regrade Interaction

If a v2.3.5 regrade produces 81 while Canvas is manually changed to 79:

```text
Baseline = 76
Local = 81
Canvas = 79
```

This is a true conflict.

The reconciliation UI should show:

```text
Local change source:
Regrade case rg_...
```

so the instructor understands why the app changed.

---

## 31. Autograder Interaction

## 36. Testing — Three-Way Cases

Explicitly test:

```text
B=L=C
L!=B, C=B
L=B, C!=B
L!=B, C!=B, L=C
L!=B, C!=B, L!=C
```

Also test null/ungraded values.

---

## 37. Testing — Submission Conflicts

- newer Canvas attempt;
- local active attempt differs;
- Canvas attachment changed;
- local artifact missing.

---

## 38. Testing — Configuration Drift

- points possible changed;
- assignment mapping changed;
- student mapping changed;
- assignment removed.

---

## 39. Testing — History Permission

- history available;
- history 403;
- history partial.

Reconciliation must still function.

---

## 40. Testing — Audit

Verify:

- baseline not advanced after failed write;
- baseline advances after verified publish;
- adopt-Canvas creates local revision;
- failed publish remains in history;
- repeated reconciliation is idempotent.

## 41. Acceptance Criteria

- [ ] B/L/C reconciliation model is implemented;
- [ ] local-only, Canvas-only, converged, and true-conflict cases are distinct;
- [ ] newer attempts are blocking conflicts;
- [ ] points-possible drift is detected;
- [ ] mapping drift is detected;
- [ ] conflict UI shows baseline/local/Canvas values;
- [ ] adopt-Canvas is explicit and audited;
- [ ] keep/publish-local is explicit and audited;
- [ ] newer attempt can be pulled for review;
- [ ] baseline advances only after verified/accepted state;
- [ ] Gradebook History enrichment is optional;
- [ ] lack of history permission does not break reconciliation;
- [ ] publish preflight uses the same classifier;
- [ ] unresolved conflicts are visible in normal course/assessment UI;
- [ ] reconciliation/audit exports exist;
- [ ] regrade source is shown for regrade-driven changes;
- [ ] grading-run/submission provenance is shown where relevant;
- [ ] full repository tests pass.

---

## 42. Release Blockers

Do not release if:

- the app overwrites Canvas-only changes automatically;
- adopting Canvas destroys local historical grading evidence;
- failed publishes advance the baseline;
- a newer Canvas attempt can be ignored silently;
- points changes are silently rescaled;
- reconciliation requires admin-only history permissions;
- conflict resolution has no audit event.

## 44. Completion of v2.3.6

After v2.3.6.4, the full Canvas grading integration is:

```text
v2.3.6.1
Connect + sync courses/roster/sections/assignments

v2.3.6.2
Pull official submissions/files into canonical local records

v2.3.6.3
Publish approved grades/feedback through controlled writes

v2.3.6.4
Detect/resolve divergence and preserve an integration audit trail
```

This is the intended definition of **full Canvas integration for the grading workflow**.

It intentionally does not recreate:

- Microsoft absence automation;
- Microsoft late-day automation;
- Canvas course-content authoring;
- a student LMS.

## 45. Resulting Contract

After v2.3.6.4:

```text
Canvas and the grading app can exchange grading-relevant state
without silent overwrites.

The app knows what it last saw,
what it currently believes,
what Canvas currently contains,
and why any difference exists or remains unresolved.
```

## Canvas API Implementation Baseline

The implementation should be verified against the official Instructure Canvas LMS API documentation at build time.

Current API design assumptions used by this specification include:

- bearer/access-token authenticated REST requests;
- paginated list endpoints using HTTP `Link` headers;
- dynamic request throttling and HTTP 429 handling;
- course, enrollment, section, assignment, submission, file, rubric, and grade-history resources;
- submission update APIs for grading/commenting.

The Canvas HTTP client must centralize these mechanics rather than duplicating them in UI/service code.
