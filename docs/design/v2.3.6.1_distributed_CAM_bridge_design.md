# v2.3.6.1 Design — Distributed CAM Bridge

**Release:** `v2.3.6.1 — Distributed CAM Bridge`
**Parent feature:** `v2.3.6 — Distributed CAM Integration & Grade Publication`
**Repository:** `grading_app`
**Status:** Definitive design specification
**Date:** August 21, 2026
**Depends on:** v2.3.5
**CAM counterpart:** CAM v0.7.1 distributed grading relay
**Canvas access:** None
**Normal-grade publication:** Not yet; transport foundation only

---

## 1. Purpose

v2.3.6.1 makes the existing local CAM ↔ Grading App integration usable when the applications run on different Macs.

Production topology:

```text
INSTRUCTOR MAC

CAM
 ↓
CAM local integration endpoint
 ↓
push/pull transport
 ↓
────────────────────────────────────
SHARED UNIVERSITY LINUX SERVER

grading_bridge/schema-v1/
    cam-to-grading/
    grading-to-cam/
────────────────────────────────────
 ↓
push/pull transport
 ↓
Grading App local integration endpoint
 ↓
Grading App

TA MAC
```

The server is a mailbox, not an application host.

---

## 2. Goals

v2.3.6.1 shall provide:

1. relay configuration;
2. SSH-key-based authentication;
3. safe Grading App outbound push;
4. safe Grading App inbound pull;
5. atomic remote arrival;
6. duplicate-safe synchronization;
7. non-destructive transport semantics;
8. automatic synchronization while the app is running;
9. sync on app startup;
10. sync immediately after durable outbound event creation where practical;
11. manual `Sync Now`;
12. relay health/status;
13. outage recovery;
14. endpoint offline/sleep recovery;
15. clear separation of local processing state and relay state;
16. regrade event round-trip across two Macs;
17. generic event transport usable by v2.3.6.2.

---

## 3. Non-Goals

v2.3.6.1 shall not:

- call Canvas;
- store a Canvas token;
- publish grades;
- calculate late policy;
- interpret academic regrade decisions;
- run CAM;
- mount the relay as the active application bridge;
- use SSHFS/NFS/SMB as the local processing root;
- sync whole grading workspaces;
- sync raw student submissions;
- sync local processed/quarantine/claim/staging directories;
- delete relay messages merely because a local copy disappears;
- require the TA to manually use terminal commands in normal operation.

---

## 4. Relay Layout

Recommended:

```text
/shared/course_automation/grading_bridge/
    schema-v1/
        cam-to-grading/
        grading-to-cam/
```

Meaning:

```text
cam-to-grading/
    CAM publishes
    Grading App receives

grading-to-cam/
    Grading App publishes
    CAM receives
```

The exact server root is deployment configuration, not hard-coded domain logic.

---

## 5. Local Endpoint Layout

The Grading App continues to own local integration state:

```text
~/Library/Application Support/CourseAutomationIntegration/regrades/
    to-grading/
    from-grading/
    processed/
    quarantine/
    .staging/
    .event-claims/
```

For transport purposes:

```text
remote cam-to-grading/
    ↓ pull
local to-grading/

local from-grading/
    ↓ push
remote grading-to-cam/
```

The existing v2.3.5 adapter continues consuming/writing the same local folders.

---

## 6. Critical Separation

Only finalized transport messages synchronize.

Never synchronize:

```text
processed/
quarantine/
.staging/
.event-claims/
local databases
grading workspace
submission artifacts
autograder work directories
```

Each endpoint owns its own processing history.

---

## 7. Transport Service Boundary

Conceptual:

```python
class CourseAutomationRelaySyncService:
    def test_connection(self) -> RelayConnectionResult:
        ...

    def pull_inbound(self) -> RelaySyncResult:
        ...

    def push_outbound(self) -> RelaySyncResult:
        ...

    def sync_once(self) -> RelaySyncResult:
        ...

    def get_health(self) -> RelayHealth:
        ...
```

The service owns transport only.

It does not:

```text
parse regrade domain meaning
change academic records
calculate grades
call Canvas
```

After inbound pull completes, existing local adapters process the files.

---

## 8. Transport Mechanism

Initial implementation:

```text
SSH + rsync
```

Rationale:

- available on macOS/Linux;
- resumable/retry-friendly;
- efficient;
- scriptable;
- predictable exit codes;
- avoids mounting remote filesystems.

The app may invoke rsync through a narrowly wrapped subprocess service.

Do not scatter shell commands through UI/domain code.

---

## 9. Configuration Model

Conceptual:

```python
@dataclass
class CourseAutomationRelayConfig:
    enabled: bool

    host: str
    user: str
    remote_root: str

    ssh_identity_file: str | None

    sync_interval_seconds: int
    connect_timeout_seconds: int

    auto_sync_on_startup: bool
    auto_sync_after_outbound: bool
```

Default:

```text
enabled = false
```

Recommended initial interval:

```text
300 seconds
```

Configuration is per workstation/user.

---

## 10. Secret Handling

The relay does not need a server password in app config.

Preferred:

```text
SSH public/private key authentication
```

The private key stays on the TA Mac.

Never place:

```text
SSH private key contents
Canvas token
Microsoft token
password
```

in assessment/project files or the relay.

The app may store only a filesystem reference to the chosen SSH identity file.

---

## 11. Relay Permissions

The server directory contains educational records and must be restricted.

Preferred operational model:

```text
authorized instructor account
authorized TA account
shared restricted Unix group
setgid/shared-group relay directory where appropriate
```

Exact permission setup depends on the university server.

The app must fail clearly on permission errors.

---

## 12. Message File Rules

Relay messages must be:

- complete JSON;
- immutable after publication;
- schema-versioned;
- event-typed;
- stably identified;
- replay-safe.

Recommended naming:

```text
<event_type>__<stable-id>__v<version>.json
```

The payload, not filename alone, is authoritative identity.

---

## 13. Atomic Remote Upload

Never expose partial JSON as a final event.

Safe pattern:

```text
local final JSON
    ↓
remote temporary name
    ↓
complete transfer
    ↓
remote atomic rename
    ↓
final .json
```

Temporary names may use:

```text
.<name>.uploading
```

Receivers ignore non-final names.

---

## 14. Pull Semantics

Inbound:

```text
remote cam-to-grading/
        ↓
Grading App local to-grading/
```

Requirements:

- pull complete final-form files only;
- never blindly overwrite a different local payload with the same name;
- exact duplicates harmless;
- transport success does not itself mark the event processed;
- local v2.3.5 ingestion performs schema validation/claim/quarantine.

---

## 15. Push Semantics

Outbound:

```text
Grading App local from-grading/
        ↓
remote grading-to-cam/
```

Requirements:

- push finalized integration files only;
- staging/claim files excluded;
- retries safe;
- successful upload means only `DELIVERED_TO_RELAY`;
- it does not mean CAM ingested or Canvas changed.

---

## 16. No `--delete`

The relay is a durable mailbox.

Production synchronization must not use destructive mirror semantics.

Prohibited:

```text
rsync --delete
```

for event directories.

A deletion on one machine must not erase the only copy another endpoint still needs.

---

## 17. Transport State Model

Keep local bridge state and relay state separate.

Suggested outbound states:

```text
PENDING_LOCAL_BRIDGE
READY_FOR_RELAY
DELIVERED_TO_RELAY
RELAY_TRANSPORT_ERROR
```

Inbound transport states may be tracked per sync run rather than per domain object.

The regrade case remains:

```text
Academic RESOLVED
```

even if:

```text
Relay transport = ERROR
```

---

## 18. Automatic Synchronization

Recommended behavior:

### Startup

```text
Grading App starts
→ test/sync relay asynchronously
→ pull inbound
→ process local inbox
→ push pending outbound
```

### While open

Run periodically:

```text
every 5 minutes
```

configurable.

### After outbound domain event

After:

```text
regrade_case_ack
regrade_decision
future grade_publication_request
```

attempt an asynchronous push.

Failure leaves the event durable locally.

---

## 19. UI Responsiveness

SSH/rsync operations must not block the Qt UI thread.

Use the application's existing worker/task architecture.

Show progress/status without modal hanging.

---

## 20. Manual Controls

Settings/Integration area:

```text
COURSE AUTOMATION RELAY

Status: Healthy
Last sync: ...
Last pull: ...
Last push: ...
Pending outbound: 2

[Test Connection]
[Sync Now]
[Open Local Integration Folder]
[View Last Error]
```

The TA does not need to know CAM internals.

Conceptual:

```python

    enabled: bool
    status: str

    last_attempt_at: str | None
    last_success_at: str | None
    last_pull_at: str | None
    last_push_at: str | None

    consecutive_failures: int
    pending_outbound_count: int

    last_error_code: str | None

```

Statuses:

```text
DISABLED
HEALTHY
STALE
UNREACHABLE
AUTHENTICATION_FAILED
PERMISSION_DENIED
CONFIGURATION_ERROR
```

---

## 22. Staleness

Relay health may become `STALE` when no successful sync has occurred for a configurable multiple of the expected interval while the app is running.

Do not label a sleeping/offline TA Mac as data loss.

On next launch/wake, sync resumes.

---

## 23. Offline Semantics

### Instructor Mac asleep

```text
TA resolves regrade
→ Grading App pushes to relay
→ event waits
→ instructor Mac wakes
→ CAM pulls/processes
```

### TA Mac offline

```text
CAM pushes request/result
→ relay retains event
→ TA opens app
→ Grading App pulls/processes
```

### Relay temporarily unavailable

```text
local event remains
→ health degraded
→ retry later
```

No workflow rolls back.

---

## 24. Duplicate Handling

The same relay event may be transferred many times.

Requirements:

```text
same logical event + same payload
→ no-op replay

same logical event/version + conflicting payload
→ conflict/quarantine
```

Domain idempotency remains in the v2.3.5/v2.3.6.2 adapters.

The relay service itself should avoid unnecessary transfer but correctness must not rely on transfer uniqueness.

---

## 25. Corruption Handling

If a pulled event is malformed:

```text
transport succeeded
domain ingestion failed
```

Move/quarantine locally according to existing integration rules.

Do not delete the remote source merely because local parsing failed.

Expose diagnostics.

---

## 26. Retention

Initial production rollout should be conservative:

- do not automatically delete relay messages;
- retain for audit/recovery;
- no endpoint-driven destructive cleanup.

Later retention/archival can be added only with an explicit policy.

---

## 27. Logging

Each sync run records:

```text
sync_run_id
direction
started_at
finished_at
remote_host
remote_root
files_considered
files_transferred
files_skipped
bytes_transferred
status
error_code
error_message
```

Do not log:

```text
private key contents
secrets
raw student submission files
```

---

## 28. Generic Event Transport

v2.3.6.1 must not hard-code synchronization to only regrade event types.

It transports any valid finalized integration JSON.

This allows v2.3.6.2 to add:

```text
grade_publication_request
grade_publication_result
```

without changing the relay mechanism.

Domain adapters still validate event types.

---

## 29. Regrade Integration Acceptance

Use real two-machine topology.

### CAM → Grading App

1. CAM emits `regrade_request_delivery`.
2. CAM pushes to relay.
3. Grading App pulls.
4. v2.3.5 ingests exactly one case.
5. Grading App emits ACK.
6. Grading App pushes ACK to relay.
7. CAM later receives it.

### Grading App → CAM

1. Resolve test case.
2. Academic decision commits locally.
3. `regrade_decision` enters local outbox.
4. Push to relay.
5. CAM pulls.
6. CAM ingests once.
7. Duplicate sync creates no duplicate logical decision.

---

## 30. Outage Acceptance

Test:

```text
relay DNS/host unavailable
SSH authentication failure
permission denied
network disconnected
rsync interrupted
app closed during pending outbound
duplicate file already remote
duplicate file already local
malformed inbound event
```

Every recoverable scenario must preserve durable local state.

---

## 31. Sleep/Resume Acceptance

Simulate:

```text
Instructor CAM unavailable
TA emits event
relay receives event
time passes
CAM resumes later
event processed once
```

and the reverse.

The acceptance result is:

> **delay, never loss.**

---

## 32. Security Acceptance

Verify:

- [ ] no Canvas token on TA Mac;
- [ ] no Microsoft token in Grading App;
- [ ] SSH key path only, not key content;
- [ ] relay cannot be accessed by unauthorized local users;
- [ ] no secrets in logs;
- [ ] no path traversal;
- [ ] no executable bridge content;
- [ ] internal processing directories never cross relay.

---

## 33. Release Blockers

Do not release if:

- relay must be mounted as the active app bridge;
- `--delete` or equivalent destructive sync is required;
- partial JSON can appear final;
- duplicate transfer duplicates domain actions;
- an outage loses the only durable event;
- academic resolve depends on successful remote transport;
- SSH/rsync runs on UI thread and freezes app;
- processed/quarantine/claims/staging synchronize;
- raw submission artifacts are copied as part of generic event sync;
- TA requires CAM credentials;
- TA requires instructor Canvas credentials.

## 35. Resulting v2.3.6.1 Contract

After v2.3.6.1:

```text
The Grading App still reads/writes a local integration endpoint.

The shared Linux server is only a durable mailbox.

The Grading App automatically moves finalized event files between
its local endpoint and the Linux relay.

The existing v2.3.5 regrade contracts work across separate Macs
without modification.

Neither application needs the other machine to be awake at the
same moment.

A sleeping/offline endpoint causes delayed processing, not lost data.

The relay layer knows nothing about academic decisions or Canvas.

v2.3.6.2 can now add normal grade-publication events on top of the
same transport.
```
