# v2.3.5 Design — Structured Regrade Adjudication & Course Automation Integration

**Release:** `v2.3.5 — Structured Regrade Adjudication & CAM Integration`
**Repository:** `grading_app`
**Status:** Definitive revised design specification
**Date:** August 21, 2026
**Implementation baseline:** `v2.3.4.2`
**Depends on:** v2.3.2 Submission Core & Provenance Foundation, v2.3.3 autograding/`GradingRun` provenance, v2.3.4.1 shared Written/Programming assessment home, v2.3.4.2 canonical LaTeX-project submission provenance
**Production integration:** Course Automation Manager (CAM) v0.7.0+ local integration bridge + existing Microsoft Forms / SharePoint / Power Automate workflow
**Direct Canvas dependency:** None
**Direct Microsoft dependency:** None
**Canvas publication owner:** Course Automation Manager

---

## 1. Purpose

v2.3.5 makes the grading app the **sole academic adjudication and grade-revision workspace for student-request-driven regrades**.

It preserves the existing Microsoft student-facing regrade workflow and integrates with the already-implemented Course Automation Manager instead of duplicating Microsoft or Canvas integration logic.

The governing principle is:

> **A regrade is an auditable revision to academic grading evidence. It is not a Canvas operation and it is not a late-day decision.**

The grading app owns the academic question:

> **What raw score and feedback did the student earn after review?**

It does **not** own the operational question:

> **What score should ultimately be published in Canvas after already-settled course-policy adjustments are respected?**

---

## 2. Scope Decision for This Revision

The previously proposed **Instructor-Initiated Systematic Corrections** workflow is **removed from v2.3.5**.

This release is intentionally limited to **student-request-driven regrade adjudication**.

Deferred to a later dedicated release:

```text
New Systematic Correction
batch selection of grading records
batch old/new preview
revision batches
multi-student correction confirmation
systematic_correction publication handoff
batch correction acceptance testing
```

This keeps v2.3.5 focused on one complete and auditable workflow and avoids introducing a second high-impact multi-student mutation path into the same release.

The underlying objects created in v2.3.5 — especially `GradeRevision`, `ApprovedGradeChange`, audit history, and publication-status abstractions — should remain reusable by a future systematic-correction subsystem, but v2.3.5 shall not expose or execute that workflow.

## 3. Final System Boundary

```text
Student
  ↓
Microsoft Form
  ↓
Power Automate
  ↓
SharePoint Regrade Request / Window Lists
  ↓
Course Automation Manager
  - receives normalized workflow event
  - resolves course/student/assessment Canvas identity
  - enriches with current Canvas context
  - transports request locally
  ↓
Local versioned JSON bridge
  ↓
Grading App
  - maps request to exact local grading evidence
  - binds exact submission / attempt
  - snapshots original grade and feedback
  - performs academic adjudication
  - revises raw earned score / feedback
  - creates immutable GradeRevision
  - creates ApprovedGradeChange when raw total changes
  - emits versioned regrade_decision
  ↓
Local versioned JSON bridge
  ↓
Course Automation Manager
  - validates the academic handoff
  - synchronizes the student-safe decision to Microsoft
  - obtains authoritative publication-policy context
  - safely plans / publishes to Canvas when required
  - verifies Canvas result
  ↓
Microsoft workflow / Canvas

Canvas publication result
  ↓
Course Automation Manager
  ↓
Local bridge
  ↓
Grading App publication status
```

The user-facing ideal is:

```text
Student submits request
        ↓
Request appears in Grading App
        ↓
Instructor/TA reviews and clicks Resolve
        ↓
Academic review is complete
        ↓
Everything operational after the decision is automated by CAM/Microsoft
```

## 5. Goals

v2.3.5 shall support:

1. regrade inbox synchronization from a narrow pluggable adapter;
2. production ingestion through Course Automation Manager without Microsoft credentials in the grading app;
3. CSV fixture/fallback import for recovery and development;
4. fake adapter support for deterministic automated tests;
5. stable local regrade case IDs;
6. request-version lineage using `external_request_id + external_version`;
7. linkage to student, assessment, exact submission, question, and criterion;
8. immutable original-grade snapshots;
9. exact original-submission access during review;
10. approve / partially approve / deny;
11. score increases or decreases according to explicit policy;
12. feedback revision;
13. append-only regrade audit history;
14. immutable `GradeRevision` records;
15. question-centric grading integration;
16. programming-autograder `GradingRun` linkage where relevant;
17. student-safe external status/note output;
18. raw-score `ApprovedGradeChange` records independent of Canvas;
19. automatic handoff of resolved regrade decisions to Course Automation Manager;
20. publication-status feedback from Course Automation Manager;
21. idempotent synchronization and transport;
22. external-version, grading-record, publication, and reviewer-concurrency conflict detection;
23. CAM one-way deep-link support into the matching regrade case;
24. exportable request, criterion-change, summary, and audit reporting.

## 6. Non-Goals

v2.3.5 shall not:

- replace Microsoft Forms;
- replace SharePoint;
- replace Power Automate;
- send duplicate student status emails;
- create a new student regrade portal;
- calculate regrade-window timeliness;
- manage absences;
- manage late-day accounting;
- decide whether late days cover a submission;
- calculate, apply, waive, remove, or reverse-engineer a late penalty;
- automatically approve or deny academic requests;
- use an LLM to adjudicate requests;
- silently change grades;
- call Canvas directly;
- store a Canvas API token;
- implement Canvas assignment mapping;
- implement Canvas write retries or Canvas conflict recovery;
- call SharePoint, Power Automate, or Microsoft Graph directly in normal production;
- import CAM source code or share CAM's internal state database;
- require CAM's GUI to be open while adjudicating;
- make the external SharePoint item the grading app's internal primary key;
- treat the currently published Canvas score as the authoritative academic/raw grading score;
- implement instructor-initiated systematic/batch grade corrections;
- implement a generalized plugin framework for regrade adapters.

- SharePoint authentication;

## 8. CAM Schemas Are External Contracts

CAM's schema-v1 payloads must be treated as **strict cross-application contracts**.

The grading app should implement exact mirrors for:

```text
RegradeRequestDelivery
RegradeCaseAcknowledgement
ApprovedGradeChange
RegradeDecision
GradePublicationResult
```

Rules:

- `schema_version = 1` is explicit;
- required fields are required;
- event types and producers are validated exactly;
- timestamps must be valid timezone-aware ISO-8601 values where CAM requires them;
- invalid score ranges are rejected;
- unsupported future schema versions fail closed;
- same logical event/version with conflicting content is a conflict, not an update;
- do not accept vague aliases such as `student_info`, `requestId`, or other guessed field names.

If CAM someday emits an unsupported version:

```text
Unsupported regrade bridge schema version: 2
```

The grading app should stop that event safely rather than guessing.

## 9. Local Application-to-Application Bridge

Normal production integration uses the existing local bridge root:

```text
~/Library/Application Support/CourseAutomationIntegration/regrades/
    to-grading/
    from-grading/
    processed/
    quarantine/
    .staging/
    .event-claims/
```

### Ownership

Course Automation Manager writes request deliveries and publication results to:

```text
to-grading/
```

The grading app consumes them.

The grading app writes case acknowledgements and decisions to:

```text
from-grading/
```

Course Automation Manager consumes them.

### Safety requirements

- complete JSON is written to a temporary file first;
- final files appear atomically;
- every payload carries a supported schema version;
- every event has a stable logical identifier;
- repeated delivery is idempotent;
- malformed or contract-invalid files are quarantined;
- processed files are archived;
- no raw student submission artifact is transported;
- no Canvas token, Microsoft token, or secret is transported;
- local bridge directories should be user-only where practical.

The grading app should use grading-app-owned claim/staging state and must not race CAM's own claim machinery for `from-grading/`.

## 10. Durable Local Outbox and Academic Transaction Boundary

The grading app's academic correctness must **not depend on CAM availability**.

When the reviewer clicks `Resolve`, persist locally first:

```text
GradeRevision
ApprovedGradeChange, if needed
RegradeDecision
updated RegradeCase
append-only audit events
local outbound event / outbox record
```

Only after the local transaction succeeds should the app attempt atomic transport into:

```text
from-grading/
```

If the bridge is unavailable:

```text
Academic decision = RESOLVED
Decision transport = PENDING
```

The adjudication must not disappear or roll back merely because CAM is closed or the bridge is temporarily unavailable.

Suggested transport states:

```text
PENDING
DELIVERED_TO_BRIDGE
TRANSPORT_ERROR
```

`DELIVERED_TO_BRIDGE` means only that the versioned event has been safely placed in CAM's inbound queue. It does **not** mean CAM has processed it or Canvas has been changed.

A later sync retries the same logical event idempotently.

## 12. Canvas Context Is Informational, Not Academic Truth

This distinction must be visible in both the code and UI.

Example:

```text
ACADEMIC GRADE — authoritative in Grading App
Raw assessment score: 80 / 100

CANVAS CONTEXT — informational
Published Canvas score: 64 / 100
Canvas late: Yes
Canvas attempt: 1
```

A difference such as:

```text
Grading app raw score = 80
Canvas score          = 64
```

is **not automatically a conflict**. A previously settled 20% late penalty may explain it.

The grading app must never reverse-engineer the policy state and must never convert the academic regrade into `64 → 72`.

Its academic output remains:

```text
old_raw_score = 80
new_raw_score = 90
```

CAM + Microsoft determine whether the final published target is 90, 72, or another policy-correct value.

## 14. External Request Lineage and Versioning

The incoming identity is:

```text
external_request_id + external_version
```

Therefore:

```text
417 v3
417 v3
```

is an exact replay and must resolve to the same local case.

But:

```text
417 v3
417 v4
```

represents a genuinely newer external version.

Use separate immutable local cases within one lineage:

```text
External request 417
│
├── v3 → rg_A
│
└── v4 → rg_B
```

Do not silently rewrite `rg_A` with v4 content.

If v4 arrives while v3 is already under review:

```text
Needs Attention / CONFLICT
reason = external_version_advanced
```

Show:

```text
previous external version
new external version
changed request fields
local review state
```

The reviewer must explicitly reconcile the situation.

---

## 15. Keep Four Version Concepts Separate

These must never collapse into one generic `version` field.

| Version | Meaning |
|---|---|
| `external_version` | Microsoft/CAM revision of the incoming request |
| `case_version` | grading-app editable case / optimistic-concurrency version |
| `decision_version` | immutable sequence of academic decisions emitted for a case |
| `grading_record_version` | academic grading-record/revision concurrency version |

The values may coincidentally be equal, but they have different owners and semantics.

```text

    ↓

```


## 18. Question / Criterion Resolution

A request may identify:

- an exact question;
- an exact criterion;
- only an assessment;
- multiple related criteria;
- multiple unrelated questions.

During review, bind the request to:

```text
question_id
criterion_ids[]
```

If the request spans unrelated questions, create related child review items while preserving the external request/case lineage.

Suggested aggregation:

```text
all approved                  → Approved
all denied                    → Denied
mixed approved/denied         → Partially Approved
any child still open          → Under Review
```

The final grade revision remains traceable to the originating regrade case.

## 23. Exact Original Submission

The review dialog must expose the exact submission/attempt originally graded.

Use the existing canonical submission provenance foundation:

```text

```

## 30. ApprovedGradeChange — Exact Academic Handoff

`ApprovedGradeChange` is created by the grading app only when the assessment raw total changes.

Its CAM-compatible fields are:

```text
approved_grade_change_id
reason_type
reason_ref
student_id
assessment_id
old_raw_score
new_raw_score
points_possible
approved_by
approved_at
```

For v2.3.5 regrades:

```text
reason_type = regrade
reason_ref  = regrade_case_id
```

Recommended ID:

```text
agc_<uuid>
```

Critical rules:

- denied requests do not contain an `ApprovedGradeChange`;
- feedback-only changes do not contain an `ApprovedGradeChange`;
- no-op score decisions do not contain an `ApprovedGradeChange`;
- raw score changes create exactly one new `ApprovedGradeChange` per decision version;
- `new_raw_score` is not necessarily the final Canvas score.

Systematic-correction reason types are intentionally outside v2.3.5.

## 31. Regrade / Late-Day Separation

A regrade never creates, removes, recalculates, or waives late-day entitlement.

> **The grading app changes only the raw academic score. The previously settled late-day outcome remains authoritative during publication.**

### On-time submission

```text
Raw score 80
No penalty
Regrade raw score: 80 → 90
Grading-app output: 80 → 90
```

### Late submission fully covered / no penalty

```text
Existing policy outcome: no penalty
Raw score 80
Regrade raw score: 80 → 90
Grading-app output: 80 → 90
```

### Existing 20% penalty

```text
Before regrade:
Raw academic score = 80
Published Canvas   = 64

Regrade:
Raw academic score 80 → 90

Grading-app ApprovedGradeChange:
old_raw_score = 80
new_raw_score = 90

CAM + authoritative policy context:
90 adjusted by existing 20% penalty → published target 72
```

## 40. Conflict Handling

### External request changed during review

A newer external request version does not silently overwrite the local case.

Show:

```text
last reviewed external version
new external version
changed fields
local review state
```

Require explicit reconciliation.

### Local grading record changed during review

If `grading_record_version` changes after snapshot/review begins:

- block final resolve;
- preserve the original snapshot;
- require refresh/reconciliation;
- never write against stale academic state.

### Submission-attempt mismatch

If the request cannot be reconciled with the exact locally graded attempt:

- block adjudication;
- show the competing attempt identities;
- require explicit mapping/reconciliation.

### Publication conflict

Display operational conflict information but do not mutate the resolved academic decision automatically.

## 41. Reviewer Concurrency

If two graders open the same case:

```text
Reviewer A loads case_version N
Reviewer B loads case_version N

A saves → N+1
B attempts stale save against N
→ blocked
→ refresh/reconcile required
```

The later save must never silently erase the earlier reviewer's work.

The same optimistic-concurrency principle applies to `grading_record_version` during final resolution.
