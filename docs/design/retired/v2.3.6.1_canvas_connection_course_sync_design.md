# v2.3.6.1 Design — Canvas Connection, Course/Roster/Assignment Sync

**Release:** `v2.3.6.1 — Canvas Connection, Course/Roster/Assignment Sync`  
**Parent feature:** `v2.3.6 — Canvas Grading Integration`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Date:** August 18, 2026  
**Depends on:** v2.3.2 Submission Core & Provenance Foundation  
**Write capability:** None. This sub-release is strictly read-only.

---

## 1. Purpose

v2.3.6.1 establishes the Canvas integration layer and synchronizes the metadata needed to connect a local grading-app course to its Canvas course.

It provides:

```text
Canvas authentication
        ↓
Course discovery/linking
        ↓
Roster + enrollment sync
        ↓
Section sync
        ↓
Assignment metadata sync
        ↓
Local assessment ↔ Canvas assignment mapping
```

It deliberately does **not** download student submission files and does **not** write grades.

Those are v2.3.6.2 and v2.3.6.3.

---

## 2. Goals

v2.3.6.1 shall:

1. configure a Canvas base URL;
2. securely store/use an instructor API credential;
3. test the connection and identify the current Canvas user;
4. list Canvas courses available to the instructor;
5. link one local course to one Canvas course;
6. synchronize enrolled students;
7. synchronize sections;
8. synchronize assignment groups where useful;
9. synchronize assignments;
10. synchronize assignment due-date metadata and overrides;
11. expose Canvas IDs as external references only;
12. map Canvas students to local student IDs;
13. map Canvas assignments to local assessment IDs;
14. preserve sync snapshots/history;
15. handle pagination;
16. handle rate throttling/retry;
17. surface partial failures;
18. provide deterministic offline tests with mocked Canvas responses;
19. preserve a hard read-only boundary.

---

## 3. Non-Goals

v2.3.6.1 shall not:

- download student submission attachments;
- create canonical Canvas `Submission` records;
- publish grades;
- publish comments;
- write rubric assessments;
- change Canvas due dates;
- create assignments;
- create modules/pages;
- alter course settings;
- manage absences;
- manage late days;
- replace the regrade intake workflow;
- change Canvas posting policies;
- require Gradebook History permissions.

---

## 4. Canvas Credential Model

For the initial operational release, support the instructor's existing API access token.

UI:

```text
Settings → Canvas

Canvas Base URL:
[ https://... ]

API Token:
[ ••••••••••••••••••••• ]

[Test Connection]
```

Successful test:

```text
Connected
User: <Canvas user name>
Canvas user ID: <id>
```

The credential must never be stored in:

- Git;
- assessment JSON;
- submission metadata;
- exported reports;
- logs.

Preferred storage:

```text
OS credential/keychain store
```

Acceptable controlled alternatives:

```text
environment variable
secure local secret store
```

Do not silently persist plaintext tokens in normal app config.

---

## 5. Base URL

Store a normalized Canvas instance base URL separately from API resource paths.

Example logical composition:

```text
<canvas_base_url>/api/v1/...
```

Normalize:

- trailing slash;
- scheme;
- host;
- accidental `/api/v1` duplication.

Reject obviously invalid schemes/URLs.

---

## 6. `CanvasClient`

All HTTP details belong in one client.

Conceptual interface:

```python
class CanvasClient:
    def get(self, path, params=None):
        ...

    def put(self, path, data=None):
        ...

    def post(self, path, data=None):
        ...

    def iter_paginated(self, path, params=None):
        ...

    def download(self, url):
        ...
```

v2.3.6.1 should expose only read operations to higher layers.

Write methods may exist behind an explicit capability boundary but must not be callable by this release's services/UI.

---

## 7. HTTP Requirements

The client must:

- send the access token in authorization headers;
- set explicit timeouts;
- validate HTTP status;
- parse JSON errors;
- follow Canvas pagination `Link` headers;
- respect rate-limit responses;
- retry transient failures with bounded backoff;
- avoid retrying permanent 4xx validation/auth errors blindly;
- redact authorization headers from logs;
- expose request IDs/diagnostics where useful.

---

## 8. Throttling

Canvas uses dynamic throttling.

The client must treat HTTP 429 as a normal recoverable API condition.

Use bounded exponential/backoff behavior with server guidance where available.

Batch sync must not fan out hundreds of uncontrolled concurrent requests.

Recommended metadata:

```text
request_count
retry_count
throttle_count
duration
```

per sync run.

---

## 9. Pagination

Canvas list resources are paginated.

Never assume one response contains the full roster or assignment list.

Use HTTP `Link` response headers until no `rel="next"` remains.

Do not hard-code a maximum enrollment/class size.

---

## 10. Core Read Endpoints

The initial client should support these resource operations:

| Purpose | Canvas REST path |
|---|---|
| Current user profile | `GET /api/v1/users/self/profile` |
| List instructor-accessible courses | `GET /api/v1/courses` |
| Get linked course | `GET /api/v1/courses/:course_id` |
| Course enrollments | `GET /api/v1/courses/:course_id/enrollments` |
| Course sections | `GET /api/v1/courses/:course_id/sections` |
| Assignment groups | `GET /api/v1/courses/:course_id/assignment_groups` |
| Assignments | `GET /api/v1/courses/:course_id/assignments` |
| Assignment overrides | `GET /api/v1/courses/:course_id/assignments/:assignment_id/overrides` |

Rubric metadata may be synchronized where exposed/needed, but rubric grading/write behavior belongs later.

## 11. Local Canvas Connection Record

```python
@dataclass
class CanvasConnection:
    connection_id: str
    base_url: str

    canvas_user_id: str
    canvas_user_name: str

    credential_ref: str

    created_at: str
    last_tested_at: str
    status: str
```

`credential_ref` points to secure credential storage; it is not the token itself.

---

## 12. Course Link

```python
@dataclass
class CanvasCourseLink:
    local_course_id: str
    connection_id: str

    canvas_course_id: str
    canvas_course_name: str

    linked_at: str
    last_synced_at: str | None

    status: str
```

One local course should normally have one active Canvas course link.

Changing a link requires explicit confirmation.

---

## 13. External IDs

Use v2.3.2 external references.

Example:

```text
local course_id = course_f2026_cs2500

ExternalReference:
system = canvas
entity_type = course
external_id = 410438
```

Likewise for students/sections/assignments.

Canvas IDs must never replace local primary keys.

---

## 14. Roster Sync

Use Canvas enrollment records to build/update Canvas-to-local student mappings.

Required normalized fields where available:

```text
canvas_user_id
name
sortable_name
login_id if permitted
email if permitted
enrollment_id
enrollment_type
enrollment_state
section_id(s)
```

Only student-like enrollments should enter the student roster mapping.

Teacher/TA/designer enrollments may be synchronized as staff metadata separately if useful.

---

## 15. Student Mapping

Matching priority:

1. existing saved Canvas user ID mapping;
2. stable institutional/student ID if available in authorized response;
3. login ID/email;
4. explicit manual mapping.

Do not use display name as the sole silent match when ambiguous.

UI:

```text
CANVAS ROSTER MAPPING

Canvas Student       Local Student       Status
-----------------------------------------------------
Jane Doe             Jane Doe            Linked
Robert Smith         Robert Smith        Linked
Alex J. Lee          —                   Needs Mapping

[Resolve]
```

---

## 16. Enrollment Changes

A sync may detect:

```text
new student
inactive/concluded enrollment
section change
name/login metadata change
```

The app should not delete historical student grading records because a Canvas enrollment disappears or concludes.

Represent enrollment state separately from local student identity/history.

---

## 17. Section Sync

Store:

```text
canvas_section_id
name
sis_section_id if visible
start/end dates if useful
```

Map student enrollments to sections.

This enables:

- section-aware filtering;
- section-specific due-date context;
- later assignment override interpretation.

Do not cross-list or modify sections.

---

## 18. Assignment Sync

Normalize:

```text
canvas_assignment_id
name
description hash/metadata if useful
points_possible
grading_type
submission_types
due_at
lock_at
unlock_at
published
assignment_group_id
has_overrides
workflow-relevant flags
```

Do not copy HTML descriptions into grading logic unless explicitly needed.

---

## 19. Assignment Overrides

For each linked/mapped assignment, read overrides so the app can later understand effective due dates.

Possible override targets include:

```text
section
student
group
```

v2.3.6.1 only records metadata.

It does not change deadlines or implement late-day policy.

---

## 20. Effective Due-Date Context

The metadata layer should be capable of answering later:

```text
What due date did Canvas expose for this student/assignment?
```

This is useful for submission context and audit, even though absence/late-day decision logic remains outside the grading app.

---

## 21. Local Assessment Mapping

Do not map assignments by name automatically without confirmation.

UI:

```text
LOCAL ASSESSMENT             CANVAS ASSIGNMENT
---------------------------------------------------------
PS1                          Problem Set 1
PS2                          Problem Set 2
Lab 1 Programming            Lab 1 — Programming
Lab 1 Core Analysis          Lab 1 — Core Analysis
```

Actions:

```text
[Map]
[Change Mapping]
[Unlink]
```

Persist mappings.

## 25. Sync Preview vs Direct Apply

For first link/mapping:

```text
preview required
```

For routine metadata refresh:

```text
safe metadata can update automatically
```

But changes that alter a persistent mapping require explicit review.

Example:

```text
Canvas assignment previously mapped to PS1 is no longer present.
```

Do not remap silently.

## 29. Read-Only Guard

This release should have a defense-in-depth write guard.

Possible approaches:

- only expose GET methods to sync services;
- explicit `CanvasCapability.READ_ONLY`;
- unit test that no mutating endpoint is reachable from v2.3.6.1 UI;
- do not expose publish buttons.

This matters because the token may have broader permissions than the app should use at this stage.

---

## 30. Error Handling

Examples:

```text
AUTHENTICATION_FAILED
PERMISSION_DENIED
COURSE_NOT_FOUND
PAGINATION_ERROR
RATE_LIMITED_RETRY_EXHAUSTED
NETWORK_TIMEOUT
INVALID_JSON
ROSTER_SYNC_PARTIAL
ASSIGNMENT_SYNC_PARTIAL
MAPPING_CONFLICT
```

Partial sync must be visible.

Do not report "Sync complete" when one resource family failed.

---

## 31. Offline Test Client

Build a fake/mock transport with recorded synthetic responses.

Automated tests must not require the real Canvas instance.

Fixtures should cover:

- pagination;
- 429 retry;
- 401 token failure;
- 403 permission failure;
- course list;
- 60-student roster;
- two sections;
- assignments;
- overrides;
- changed assignment;
- removed/concluded enrollment.

---

## 32. Optional Live Smoke Test

A manually invoked integration test may run against an instructor-controlled Canvas course.

It must:

- be disabled by default;
- use environment/secure credential;
- perform GET only;
- never write.

- [ ] token can be stored/retrieved without plaintext project persistence;
- [ ] Test Connection identifies the current Canvas user;
- [ ] available courses can be listed;
- [ ] a local course can be explicitly linked;
- [ ] roster sync handles pagination;
- [ ] sections sync;
- [ ] assignments sync;
- [ ] assignment overrides sync;
- [ ] student mappings persist;
- [ ] assignment mappings persist;
- [ ] Canvas IDs remain external IDs;
- [ ] enrollment removal does not delete grading history;
- [ ] routine sync shows changes/unchanged counts;
- [ ] 429 responses are retried safely;
- [ ] partial failure is reported;
- [ ] sync history persists;
- [ ] no Canvas writes are possible through this release UI;
- [ ] existing local grading works with Canvas disconnected;
- [ ] full repository tests pass.

---

## 34. Release Blockers

Do not release if:

- API token is stored in plaintext course/repo data;
- list pagination is ignored;
- rate limits can crash/corrupt sync;
- Canvas IDs replace local IDs;
- assignment mapping can silently change;
- removing a Canvas enrollment deletes local grading history;
- any UI action can mutate Canvas.

## 36. Resulting Contract

After v2.3.6.1:

```text
The grading app knows which Canvas course it belongs to,
which Canvas students correspond to local students,
which sections they are in,
and which Canvas assignments correspond to local assessments.

Nothing has been written to Canvas.
```

## Canvas API Implementation Baseline

The implementation should be verified against the official Instructure Canvas LMS API documentation at build time.

Current API design assumptions used by this specification include:

- bearer/access-token authenticated REST requests;
- paginated list endpoints using HTTP `Link` headers;
- dynamic request throttling and HTTP 429 handling;
- course, enrollment, section, assignment, submission, file, rubric, and grade-history resources;
- submission update APIs for grading/commenting.

The Canvas HTTP client must centralize these mechanics rather than duplicating them in UI/service code.
