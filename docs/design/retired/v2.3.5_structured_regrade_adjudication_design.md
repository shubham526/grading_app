# v2.3.5 Design — Structured Regrade Adjudication & Grade Revision

**Release:** `v2.3.5 — Structured Regrade Adjudication & Grade Revision`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Date:** August 18, 2026  
**Depends on:** v2.3.2 Submission Core & Provenance Foundation and existing question-centric grading records  
**Integrates with:** Existing Microsoft Forms + SharePoint + Power Automate regrade intake/status system  
**Canvas dependency:** None; approved grade changes become Canvas-publishable automatically once v2.3.6.3 exists

---

## 1. Purpose

v2.3.5 makes the grading app the **adjudication and grade-revision workspace** for regrade requests while preserving the existing Microsoft-based student-facing workflow.

The grading app must **not** recreate:

- the Microsoft Form students already use;
- the SharePoint regrade request list;
- the regrade-window list;
- intake-timeliness logic already implemented in Power Automate;
- student receipt/status emails already implemented in Power Automate.

Instead, the system boundary is:

```text
Student
  ↓
Microsoft Form
  ↓
Power Automate
  ↓
SharePoint Regrade Request / Window Lists
  ↓
v2.3.5 Regrade Inbox Adapter
  ↓
Grading App Regrade Queue
  ↓
Instructor / TA adjudication
  ↓
Auditable grade revision
  ↓
Status/decision sync back to SharePoint
  ↓
existing Power Automate student notifications

Later:
approved grade revision
  ↓
v2.3.6.3 Canvas Publish Queue
```

The central principle remains:

> **A regrade is not an overwrite. It is an auditable revision to an existing grading record.**

---

## 2. Why This Release Changes From the Old Regrade Design

The previous design assumed a generic external form/CSV import.

The actual operational system already exists and should remain authoritative for intake:

- Microsoft Forms collects requests;
- Power Automate evaluates timing and updates SharePoint;
- SharePoint stores request status/data;
- existing flows send student emails.

Therefore v2.3.5 should separate:

### External request/intake state

Owned by the Microsoft workflow.

### Academic adjudication state

Owned by the grading app.

### Grade publication state

Owned by the grading app + Canvas integration later.

This avoids rebuilding functioning automation and keeps the app focused on the parts that currently require instructor/TA review.

---

## 3. Goals

v2.3.5 shall support:

1. regrade inbox synchronization from a pluggable source;
2. production mapping to the existing SharePoint request/window lists;
3. CSV fixture/fallback import for development and recovery;
4. stable local regrade case IDs;
5. linkage to student, assessment, submission, question, and criterion;
6. original-grade snapshots;
7. original-submission access during review;
8. approve / partially approve / deny;
9. score increases or decreases according to policy;
10. feedback revision;
11. append-only regrade audit history;
12. question-centric grading integration;
13. programming-autograder run linkage where relevant;
14. systematic instructor-initiated corrections;
15. status/decision synchronization back to the existing Microsoft workflow;
16. approved-grade-change records independent of Canvas;
17. later Canvas publish-queue compatibility;
18. idempotent synchronization;
19. conflict detection;
20. exportable regrade audit/reporting.

---

## 4. Non-Goals

v2.3.5 shall not:

- replace Microsoft Forms;
- replace SharePoint;
- replace Power Automate status emails;
- create a new student regrade portal;
- manage absences;
- manage late-day requests;
- duplicate absence/late-day business logic;
- automatically approve/deny academic requests;
- use an LLM to adjudicate requests;
- silently change grades;
- require Canvas;
- directly publish to Canvas before v2.3.6.3;
- make the external SharePoint item the grading app's internal primary key.

## 7. Source Adapter Design

Introduce:

```python
class RegradeInboxAdapter(Protocol):
    source_system: str

    def list_changed_requests(self, cursor=None):
        ...

    def get_request(self, external_id: str):
        ...

    def update_status(self, external_id: str, update):
        ...

    def list_windows(self):
        ...
```

Implementations:

```text
SharePointRegradeAdapter      production target
CsvRegradeAdapter             tests/manual recovery
FakeRegradeAdapter            automated tests
```

The regrade engine must not directly contain SharePoint HTTP/authentication logic.

---

## 8. SharePoint Integration Principle

The production adapter should use a user/institution-authorized Microsoft connection.

Authentication details must remain isolated in the adapter/configuration layer.

Do not place:

- access tokens;
- client secrets;
- refresh tokens;

in:

- Git;
- saved assessments;
- exported regrade reports.

If direct SharePoint credentials are not available during early development, the engine must still be testable through `FakeRegradeAdapter` and CSV fixtures, but operational completion should include direct sync so routine use does not require manual CSV export.

## 9. Local Regrade Case

External request identity and local case identity remain separate.

```python
@dataclass
class RegradeCase:
    regrade_case_id: str

    external_source: str
    external_request_id: str

    student_id: str
    assessment_id: str

    submission_id: str | None
    question_id: str | None
    criterion_ids: list[str]

    request_type: str | None
    student_reason: str
    submitted_at: str
    intake_timeliness: str | None

    status: str
    review_status: str

    original_snapshot_id: str | None
    created_at: str
    updated_at: str
```

Recommended local ID:

```text
rg_<uuid>
```

Do not derive it from student name or SharePoint row number alone.

The adapter normalizes whatever the external form provides.

Canonical request fields:

```text

student_name
student_email
assessment_label
submitted_at
intake_timeliness
external_status

```

Missing question/criterion IDs are allowed at intake because the grading app can resolve them during adjudication.

## 11. Student and Assessment Resolution

Map:

```text
external student identifier
    ↓
grading app student_id
```

and:

```text
SharePoint assessment label
    ↓
grading app assessment_id
```

Persist mapping.

Statuses:

```text
resolved
needs_mapping
ambiguous
unknown
```

Never silently resolve ambiguous requests.

---

## 12. Question/Criterion Resolution

A request may arrive with:

- exact question;
- exact criterion;
- only an assessment-level description.

During review, the app must allow the reviewer to bind the request to:

```text
question_id
criterion_ids[]
```

This mapping becomes part of the audit history.

One request should normally target one question and one or more criteria.

If the student's request spans unrelated questions, split it into related local review items while preserving the one external request ID.

## 13. Regrade State Model

External student-facing statuses may remain:

```text
Submitted
Under Review
Approved
Partially Approved
Denied
```

The app should preserve external labels but maintain a richer internal review state:

```text
SYNCED
NEEDS_MAPPING
READY
UNDER_REVIEW
NEEDS_INFORMATION
DECISION_DRAFT
RESOLVED
SYNC_ERROR
CONFLICT
INVALID
```

Resolution decision:

```text
approved
partially_approved
denied
withdrawn
invalid
```

Do not force SharePoint to adopt every internal technical status.

## 14. Synchronization State

## 21. Programming Autograder Regrades

If the affected grade came from v2.3.3, the case should show:

```text
original submission
original GradingRun
autograder version
raw score
manual adjustments
final score
```

Reviewer actions may include:

```text
inspect failed tests
re-run exact historical configuration

```

Any new autograder run remains a separate immutable `GradingRun`.

The regrade decision chooses which result/change becomes authoritative.

## 23. Score Decrease Policy

Per assessment/course:

```text
allow_score_decrease = true | false
```

Rules:

- opening a regrade never changes score;
- a decrease requires explicit reviewer action;
- if policy forbids decreases, block unless privileged override is intentionally supported;
- all decreases require confirmation and audit.

## 26. Canvas Boundary

v2.3.5 must not call Canvas directly.

Correct architecture:

```text
Regrade decision
      ↓
ApprovedGradeChange
      ↓
v2.3.6.3 CanvasPublishService
```

This keeps regrades usable when Canvas is unavailable and makes Canvas publishing generic for all grade changes.

---

## 27. External Status Sync

After resolution, the app should write back only the fields required by the existing student-facing workflow, for example:

```text
Status
Student Status Note
Status Updated At
```

Exact field mapping belongs in adapter configuration.

Example:

```text
local decision = partially_approved
external status = Partially Approved
student note = "Q4 logic criterion adjusted..."
```

This allows existing Power Automate flows to continue sending student notifications.

---

## 28. Do Not Duplicate Email

The grading app should not send the normal regrade status email if the existing Power Automate flow already owns that responsibility.

The app may show:

```text
External status sync successful
```

and rely on the existing automation.

---

## 29. Needs Information

If the instructor needs clarification:

```text
internal status = NEEDS_INFORMATION
```

If the existing external workflow supports a corresponding student status/note, map to it.

If it does not, keep the case internal and use the existing instructor process rather than inventing a parallel communication channel without deliberate design.

---

## 30. Instructor-Initiated Systematic Correction

Not every correction begins with a student request.

Support:

```text
New Systematic Correction
```

Example:

```text
Bad rubric mapping discovered for PS4 Q2
```

The instructor can:

1. select affected grading records;
2. preview old/new values;
3. create revision batch;
4. approve changes;
5. create `ApprovedGradeChange` records;
6. preserve audit history.

No external student request is required.

---

## 31. Batch Correction Safety

Show a mandatory preview:

| Student | Old | New | Delta |
|---|---:|---:|---:|
| A | 60 | 65 | +5 |
| B | 70 | 70 | 0 |
| C | 55 | 60 | +5 |

Require explicit confirmation.

Do not modify unrelated questions/criteria.

## 32. ABET/Outcome Awareness

The app already has earlier outcome/ABET infrastructure.

If a regrade touches fields that participate in existing ABET evidence, the app must:

- preserve the prior evidence snapshot;
- never silently infer a new categorical ABET rating from changed points;
- flag the affected evidence for review if required by the installed ABET schema.

The future Fall 2026 ABET redesign is now planned as v2.3.7, so v2.3.5 must not depend on that unreleased profile.

## 34. Idempotency

Repeated sync must not:

- duplicate cases;
- duplicate decisions;
- duplicate external status updates;
- duplicate grade revisions.

Use:

```text
external_request_id
external_modified/version marker
local decision version
```

and idempotency keys for outbound updates where practical.

---

## 35. Conflict Handling

Potential conflict:

```text
SharePoint request changed after local review began
```

Mark:

```text
CONFLICT
```

Show:

```text
Last synced external status
Current external status
Local status
Changed fields
```

Do not overwrite external changes silently.

---

## 36. Reviewer Concurrency

If two graders open the same case:

- store record version/update timestamp;
- detect stale save;
- require refresh/merge;
- never silently let the later save erase the earlier decision.

## 43. Operational Acceptance Workflow

1. Click `Sync Regrade Inbox`.
2. New SharePoint requests appear once.
3. Open a request.
4. App shows exact graded submission and original grading snapshot.
5. Resolve question/criterion mapping if needed.
6. Enter decision and revised points/feedback.
7. App previews total grade change.
8. Resolve case.
9. App creates immutable grade revision.
10. App creates `ApprovedGradeChange` if score changed.
11. App synchronizes status/note to external request.
12. Re-sync produces no duplicate case/change.
13. Later, v2.3.6.3 can publish the approved grade change to Canvas.

## 45. Release Blockers

Do not release if:

- resolving a request overwrites the only copy of original grading;
- a newer submission attempt is silently substituted;
- repeated synchronization creates duplicate cases;
- app sends duplicate student emails outside the established workflow;
- external status changes are overwritten without conflict detection;
- Canvas is required for local regrade resolution;
- grade changes cannot be traced to a case/correction and reviewer.
