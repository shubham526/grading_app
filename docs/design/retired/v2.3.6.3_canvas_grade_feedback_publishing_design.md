# v2.3.6.3 Design — Controlled Canvas Grade & Feedback Publishing

**Release:** `v2.3.6.3 — Controlled Canvas Grade & Feedback Publishing`  
**Parent feature:** `v2.3.6 — Canvas Grading Integration`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Date:** August 18, 2026  
**Depends on:** v2.3.6.2 and approved/final local grade records  
**First Canvas write release:** Yes

---

## 1. Purpose

v2.3.6.3 adds controlled app → Canvas publication.

The app may publish an instructor-approved local grade and selected feedback to a mapped Canvas assignment only after:

1. mapping is valid;
2. submission/attempt context is known;
3. local grading is finalized/approved;
4. current Canvas state is refreshed;
5. a publish preview is shown;
6. conflicts are blocked or explicitly resolved;
7. the instructor confirms the write.

The central safety principle:

> **Grading locally and publishing to Canvas are separate actions.**

---

## 2. Goals

v2.3.6.3 shall support:

1. publishing one approved score;
2. publishing selected/batch scores;
3. optional text feedback;
4. optional rubric assessment publication when an explicit rubric mapping exists;
5. publish preview;
6. selective exclusion;
7. preflight refresh of Canvas state;
8. conflict blocking;
9. idempotent/retry-safe publication;
10. partial-failure reporting;
11. append-only publish audit;
12. v2.3.5 approved regrade grade changes;
13. ordinary manual written grading;
14. v2.3.3 autograder final grades;
15. no automatic publication of unresolved/flagged grades.

---

## 3. Non-Goals

v2.3.6.3 shall not:

- automatically publish immediately after grading;
- change assignment due dates;
- manage absences/late days;
- change posting policy;
- automatically post/release hidden grades to students;
- create assignments;
- modify course pages/modules;
- overwrite Canvas conflicts silently;
- depend on Grade Change Log permissions;
- publish raw autograder results before review policy is satisfied.

---

## 4. Primary Write Endpoint

Primary Canvas operation:

```text
PUT /api/v1/courses/:course_id/assignments/:assignment_id/submissions/:user_id
```

Canvas supports assigning a posted grade through submission update parameters and supports submission comments; rubric-assessment data can also be supplied when the assignment/rubric context and mapping are valid.

The implementation must verify the exact request shape against current official Canvas docs when coding.

---

## 5. Publishable Local Grade

Introduce or normalize a publishable grade contract:

```python
@dataclass
class PublishableGrade:
    student_id: str
    assessment_id: str

    submission_id: str | None
    source_grading_record_id: str

    score: float | None
    grade_display: str | None

    approval_status: str

    feedback_text: str | None
    rubric_results: dict | None

    reason_type: str
    reason_ref: str | None
```

`reason_type` examples:

```text
initial_grading
regrade
systematic_correction
manual_adjustment
```

---

## 6. Eligible Publish States

Default eligible:

```text
APPROVED
FINALIZED
```

Default ineligible:

```text
UNREVIEWED
FLAGGED
GRADER_ERROR
SYNC_CONFLICT
MISSING
NO_LOCAL_GRADE
```

The app should not let a batch publish silently include an unresolved record.

---

## 7. Canvas Mapping Requirements

Before publish:

```text
local course ↔ Canvas course
local assessment ↔ Canvas assignment
local student ↔ Canvas user
```

must all be resolved.

If a grade is tied to a specific Canvas submission attempt, the app should verify that attempt context has not become stale.

---

## 8. Publish Preflight

Immediately before showing/confirming publication:

1. fetch current Canvas submission state;
2. compare current score/grade/attempt against the v2.3.6.2 baseline;
3. compare local active submission/grade source;
4. classify safe vs conflict;
5. build intended diff.

Do not rely on a days-old cached Canvas grade.

## 11. Score Publication

Use the Canvas submission update API to set the intended grade.

The app should preserve:

```text
requested value
Canvas response value
timestamp
```

A successful HTTP response is not enough; parse returned state and record what Canvas reports.

---

## 12. Feedback Publication

Text feedback should be optional per publish operation.

Policies:

```text
Publish score only
Publish score + feedback
Publish feedback only
```

Do not always resend the same long feedback on repeated safe retry.

Track comment/publication identity where possible.

---

## 13. Autograder Feedback

A programming grade can generate a concise Canvas-safe summary:

```text
Basic correctness: 30/30
Edge cases: 15/20
Efficiency: 15/15
Interface: 5/5

Final: 65/70
```

Do not expose hidden test source or sensitive hidden expected values.

Full instructor logs remain local.

---

## 14. Written-Grading Feedback

For written assignments, feedback may include:

- overall instructor comment;
- selected question/rubric summary;
- link-free concise note that detailed feedback is available in the grading workflow if applicable.

Do not publish internal audit notes.

---

## 15. Rubric Publication

Canvas rubric write-back should be enabled only when:

```text
local criterion
↔ Canvas rubric criterion
```

mapping is explicit and validated.

Store mapping:

```text
local_criterion_id
canvas_rubric_criterion_id
points semantics
```

If mapping is incomplete:

```text
publish score/comment
skip rubric
show warning
```

Do not infer rubric criterion mapping by display text alone.

---

## 16. Grade Scale / Points Validation

Before publish:

- confirm Canvas assignment `points_possible`;
- confirm local assessment max points;
- detect mismatch;
- block or require explicit mapping/transformation.

Do not silently scale a 70-point local score onto a 100-point Canvas assignment.

If intentional scaling exists, it must be explicit and audited.

---

## 17. Posting Policy

Canvas may use manual or automatic grade posting policies.

v2.3.6.3 should **not** change posting policy.

Publishing a grade means:

```text
write grading state to Canvas
```

It does not mean:

```text
force-release grade visibility to students
```

The instructor continues to control Canvas posting/release behavior in Canvas unless a future deliberately designed feature changes this.

---

## 18. Regrade Integration

v2.3.5 produces:

```text
ApprovedGradeChange
```

v2.3.6.3 consumes it.

Workflow:

```text
Regrade resolved
    ↓
ApprovedGradeChange
    ↓
Pending Canvas Publish
    ↓
Preview
    ↓
Publish
```

After success, update the approved change:

```text
canvas_publish_status = published
canvas_publish_record_id = ...
```

The regrade engine itself never calls Canvas.

---

## 19. Batch Publication

Support:

```text
Publish Selected
Publish All Ready
```

Never:

```text
Publish All Including Conflicts
```

without explicit per-conflict resolution.

Batch operations should process records independently and report partial success.

---

## 20. Publish Job Model

```python
@dataclass
class CanvasPublishJob:
    publish_job_id: str
    course_id: str
    assessment_id: str

    created_at: str
    created_by: str

    item_count: int
    status: str

    preflight_sync_run_id: str
```

Each item:

```python
@dataclass
class CanvasPublishItem:
    publish_item_id: str

    student_id: str
    canvas_user_id: str
    canvas_assignment_id: str

    source_grade_record_id: str

    baseline_canvas_score: float | None
    preflight_canvas_score: float | None
    intended_score: float | None

    feedback_hash: str | None

    status: str
    error: str | None
```

## 22. Idempotency

A retry must not create unintended duplicate grade/comment effects.

Use a stable logical publication fingerprint based on:

```text
course
assignment
student
source grade revision/version
intended score
feedback hash
rubric payload hash
```

If an identical publication is already verified:

```text
Already published
```

skip unless force-republish is explicitly selected.

---

## 23. Post-Write Verification

After update:

1. inspect returned submission;
2. optionally refetch the submission;
3. verify score/grade matches intended result;
4. mark publish item verified.

If not:

```text
VERIFY_FAILED
```

Do not claim success.

---

## 24. Partial Failure

Example:

```text
53 selected
51 published
1 conflict
1 permission failure
```

Show:

```text
PUBLISH COMPLETE WITH ISSUES
```

Do not retry permanent 403/validation errors indefinitely.

---

## 25. Retry

Provide:

```text
Retry Failed
```

only for retryable failures.

The app must not resend successful items unnecessarily.

---

## 26. Permission Failure

If token lacks grade-edit permission:

- stop affected writes;
- preserve pending queue;
- show the exact Canvas error;
- do not downgrade local grade state.

---

## 27. Conflict Preflight

v2.3.6.3 needs a minimal conflict check before every write.

If Canvas changed since baseline:

```text
BLOCKED_CONFLICT
```

Detailed resolution belongs to v2.3.6.4.

This means v2.3.6.3 can be safe before the full reconciliation UI exists.

---

## 28. Newer Attempt Preflight

If Canvas has a newer attempt than the one that produced the local grade:

```text
BLOCKED_NEWER_ATTEMPT
```

The instructor must pull/review the new attempt before ordinary publication.

Never publish an old-attempt grade over a newer unreviewed submission silently.

---

## 29. Audit Record

For every write attempt store:

```text
publish_job_id
publish_item_id
actor
timestamp

Canvas course/assignment/user IDs
local course/assessment/student IDs
source grade record ID
source submission ID/attempt

baseline Canvas grade
preflight Canvas grade
intended grade
Canvas returned grade

feedback hash
rubric payload hash

HTTP/result classification
verification result
```

Do not store bearer tokens or sensitive request headers.

## 32. Security

Write operations are consequential.

Requirements:

- explicit user action;
- clear course/assignment identity;
- preview;
- no hidden background automatic grade publication;
- credentials from secure store;
- server response validation;
- audit log.

---

## 33. Testing

Use fake Canvas server/transport.

Test:

- one grade;
- batch grades;
- score increase;
- score decrease;
- unchanged score;
- score + comment;
- comment only;
- rubric mapping valid;
- rubric mapping missing;
- points mismatch;
- 401/403;
- 429;
- 500 retry;
- partial batch failure;
- newer attempt;
- Canvas grade changed since baseline;
- retry idempotency;
- post-write verification mismatch.

---

## 34. Live Smoke Testing

If used, run only against a dedicated test/sandbox assignment.

Require explicit environment flag.

Never run automated write tests against a live production course by default.

---

## 35. Acceptance Criteria

- [ ] only approved/final local grades are eligible;
- [ ] publication requires valid Canvas mappings;
- [ ] preflight refresh occurs before write;
- [ ] Canvas changes since baseline block ordinary publish;
- [ ] newer attempt blocks old-attempt publish;
- [ ] preview clearly shows old/new values;
- [ ] instructor explicitly confirms write;
- [ ] score publication works;
- [ ] optional text feedback works;
- [ ] rubric publication requires explicit criterion mapping;
- [ ] points mismatch is detected;
- [ ] posting policy is not changed;
- [ ] regrade `ApprovedGradeChange` can enter publish queue;
- [ ] batch partial failures are visible;
- [ ] retry is idempotent;
- [ ] post-write state is verified;
- [ ] every write has an audit record;
- [ ] failed publication never changes local academic history;
- [ ] full repository tests pass.

---

## 36. Release Blockers

Do not release if:

- grading automatically writes without preview/confirmation;
- conflicts can be overwritten silently;
- old-attempt grades can publish over newer attempts;
- write retries can duplicate comments unpredictably;
- points mismatches silently scale;
- posting policy is changed implicitly;
- a 200 response is treated as success without validating Canvas state;
- audit history is missing.

## Canvas API Implementation Baseline

The implementation should be verified against the official Instructure Canvas LMS API documentation at build time.

Current API design assumptions used by this specification include:

- bearer/access-token authenticated REST requests;
- paginated list endpoints using HTTP `Link` headers;
- dynamic request throttling and HTTP 429 handling;
- course, enrollment, section, assignment, submission, file, rubric, and grade-history resources;
- submission update APIs for grading/commenting.

The Canvas HTTP client must centralize these mechanics rather than duplicating them in UI/service code.
