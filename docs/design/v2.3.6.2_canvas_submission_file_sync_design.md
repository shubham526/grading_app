# v2.3.6.2 Design — Canvas Submission & File Sync

**Release:** `v2.3.6.2 — Canvas Submission & File Sync`  
**Parent feature:** `v2.3.6 — Canvas Grading Integration`  
**Repository:** `grading_app`  
**Status:** Design specification  
**Date:** August 18, 2026  
**Depends on:** v2.3.6.1 and v2.3.2  
**Uses automatically:** v2.3.3 autograding and v2.3.4 ZIP ingestion through canonical submission routing  
**Write capability:** None. Canvas remains read-only in this sub-release.

---

## 1. Purpose

v2.3.6.2 adds the operational button the grading workflow needs:

```text
[Pull Canvas Submissions]
```

For a linked local assessment/Canvas assignment, the app retrieves Canvas submission state, downloads new/changed official artifacts, creates canonical v2.3.2 `Submission` records, preserves attempts and provenance, and routes the artifacts to the existing grading/ingestion stack.

This release must make Canvas a **submission source**, not a special grading mode.

## 3. Goals

v2.3.6.2 shall:

1. list submissions for a mapped Canvas assignment;
2. capture Canvas submission metadata;
3. capture attempt numbers;
4. capture submission timestamps;
5. capture workflow/late/missing/excused state;
6. capture current Canvas score/grade snapshot;
7. discover attached files;
8. download new/changed files;
9. hash downloaded bytes;
10. create canonical `Submission` and `ArtifactFile` records;
11. retain Canvas IDs only as external references;
12. preserve historical attempts;
13. detect newer Canvas attempts;
14. avoid re-downloading unchanged artifacts unnecessarily;
15. support multi-file submissions;
16. route `.py` to v2.3.3;
17. route PDF+ZIP to v2.3.4;
18. support ordinary PDF/DOCX written submissions where existing ingestion allows them;
19. show missing/unsubmitted students;
20. preserve sync history and baseline grade state;
21. remain strictly read-only.

---

## 4. Non-Goals

v2.3.6.2 shall not:

- post grades;
- post comments;
- change rubrics;
- change excused status;
- alter due dates;
- apply late-day policy;
- resolve absence cases;
- automatically grade on Canvas itself;
- delete Canvas submissions;
- assume the newest attempt should replace historical local grading silently.

---

## 5. Canvas Submission Endpoints

Primary operations:

| Purpose | Canvas REST path |
|---|---|
| List assignment submissions | `GET /api/v1/courses/:course_id/assignments/:assignment_id/submissions` |
| Get one submission | `GET /api/v1/courses/:course_id/assignments/:assignment_id/submissions/:user_id` |
| Get file metadata when needed | `GET /api/v1/files/:id` |

Submission responses can expose attachment/file metadata and grading/submission state.

Use Canvas pagination for class-wide submission lists.

## 6. Normalized Canvas Submission Snapshot

Store a normalized source snapshot:

```python
@dataclass
class CanvasSubmissionSnapshot:
    canvas_course_id: str
    canvas_assignment_id: str
    canvas_user_id: str

    attempt: int | None
    submitted_at: str | None

    workflow_state: str | None
    submission_type: str | None

    late: bool | None
    missing: bool | None
    excused: bool | None

    score: float | None
    grade: str | None
    graded_at: str | None
    grader_id: str | None

    attachment_refs: list[dict]

    fetched_at: str
    source_payload_hash: str
```

This snapshot becomes the Canvas baseline for later publishing/reconciliation.

## 7. Submission State Classification

UI-friendly normalized states:

```text

submitted
resubmitted
missing
late
excused
graded
ungraded
unsupported_submission_type
sync_error
```

Do not collapse Canvas's raw state permanently; preserve relevant source metadata.

---

## 8. Attempt Handling

Canvas attempt number maps naturally onto v2.3.2 `Submission.attempt`.

Example:

```text
Jane
Attempt 1 -> sub_old, inactive
Attempt 2 -> sub_new, active
```

Never overwrite attempt 1.

When a newer attempt appears after grading has begun:

```text
NEWER_CANVAS_ATTEMPT
```

flag the record.

The app must require deliberate choice about whether grading moves to the new attempt.

---

## 9. Active Attempt Rules

Default import behavior:

- newest successfully imported official Canvas attempt becomes active;
- prior attempts remain;
- if prior attempt already has a finalized grade, show a prominent warning;
- do not discard the finalized grade/run history;
- later reconciliation must know which attempt produced the app grade.

---

## 10. Attachment Discovery

For file-upload assignments, each attachment should become an `ArtifactFile`.

Store external references:

```text
canvas file ID
canvas submission/attempt context
Canvas original display name
```

Then store local:

```text
artifact_id
sha256
size
immutable bytes
```

Canvas file ID is not the local artifact ID.

---

## 11. Download Security

Downloads must:

- use the authenticated Canvas context as required;
- follow redirects safely;
- enforce timeout;
- cap maximum file size according to app policy;
- stream to temporary storage;
- hash bytes while/after downloading;
- commit only after successful complete download;
- never execute downloaded content;
- sanitize storage filename;
- preserve original display filename as metadata.

---

## 12. Smart Sync / Incremental Pull

`Pull Canvas Submissions` must not blindly create duplicates every time.

For each Canvas user/assignment/attempt compare:

```text
known external submission state
known Canvas file IDs
known local hashes
current Canvas attempt
current attachment metadata
```

Classify:

```text
UNCHANGED
NEW_SUBMISSION
NEW_ATTEMPT
CHANGED_ATTACHMENT
MISSING_LOCAL_ARTIFACT
NEEDS_DOWNLOAD
SYNC_CONFLICT
```

Download only what is needed.

---

## 13. Source Idempotency

A repeated pull with no Canvas change must produce:

```text
0 new canonical submissions
0 duplicate artifacts
N unchanged
```

Idempotency key can logically include:

```text
canvas course
canvas assignment
canvas user
attempt
canvas file id
```

plus hash validation after download.

---

## 14. Canvas-to-Local Student Mapping

v2.3.6.1 provides Canvas user → local student mapping.

If an assignment submission belongs to an unmapped user:

```text
NEEDS_STUDENT_MAPPING
```

Do not create a student record silently if that violates local roster conventions.

---

## 15. Assignment Mapping Requirement

`Pull Canvas Submissions` is enabled only when:

```text
local assessment
↔ Canvas assignment
```

mapping exists.

If mapping is broken, disable pull and show why.

---

## 16. Multi-File Submissions

A Canvas attempt can contain multiple files.

Create:

```text
one canonical Submission
many ArtifactFile records
```

Do not create one logical submission per attachment.

---

## 17. File Role Resolution

Rules may be assessment-specific.

Example written Overleaf assessment:

```text
*.pdf  -> role=rendered
*.zip  -> role=source, type=latex_project_zip
```

Programming assessment:

```text
*.py -> role=primary/source
```

If more than one file competes for the same required role, mark:

```text
NEEDS_ARTIFACT_RESOLUTION
```

Do not guess silently.

---

## 18. Submission Type Routing

Initial support should handle:

### `online_upload`

Download attachments and create file artifacts.

### Text entry

If Canvas exposes a text body and the local written pipeline supports it, preserve as a canonical text artifact.

### Other types

Preserve metadata and mark unsupported for automatic file ingestion unless a handler exists.

Do not pretend an external URL or media recording is a local file submission.

---

## 19. Canvas Official Artifact Principle

For Canvas-linked assessments:

> The official submitted artifact is the Canvas artifact associated with the selected Canvas attempt.

Local execution/parsing may create derived artifacts, but official bytes and Canvas provenance remain preserved.

## 32. Partial Failure

If 53/54 files download successfully:

```text
53 successful
1 failed
```

Do not roll back all successful imports unless transaction semantics demand it.

The failed student must remain clearly retryable.

---

## 33. Retry

Support:

```text
Retry Failed Downloads
```

Retries must not duplicate already successful artifacts.

---

## 34. Read-Only Guard

No Canvas mutation is allowed.

Submission pull may modify only the grading app's local storage/database.

Unit/integration tests should assert only GET/download operations occur.

## 36. Acceptance Criteria

- [ ] mapped assignment can pull Canvas submissions;
- [ ] pagination works;
- [ ] Canvas user maps to local student;
- [ ] attempts are preserved;
- [ ] newer attempts are detected;
- [ ] official Canvas files are downloaded immutably;
- [ ] each file receives local SHA-256;
- [ ] multi-file attempts become one canonical submission;
- [ ] repeated pull is idempotent;
- [ ] unchanged artifacts are not duplicated;
- [ ] PDF+ZIP routes to v2.3.4;
- [ ] Python routes to v2.3.3;
- [ ] PDF routes to existing written ingestion;
- [ ] missing/excused/unsupported states are visible;
- [ ] current Canvas grade state is snapshotted;
- [ ] partial download failures can be retried;
- [ ] no Canvas write occurs;
- [ ] full repository tests pass.

---

## 37. Release Blockers

Do not release if:

- repeated pulls create duplicate attempts/artifacts;
- newer Canvas attempts overwrite historical local records;
- downloaded bytes are not hashed;
- attachment files bypass v2.3.2;
- Canvas file IDs become local artifact IDs;
- submission failures disappear silently;
- Canvas write operations are reachable.

## Canvas API Implementation Baseline

The implementation should be verified against the official Instructure Canvas LMS API documentation at build time.

Current API design assumptions used by this specification include:

- bearer/access-token authenticated REST requests;
- paginated list endpoints using HTTP `Link` headers;
- dynamic request throttling and HTTP 429 handling;
- course, enrollment, section, assignment, submission, file, rubric, and grade-history resources;
- submission update APIs for grading/commenting.

The Canvas HTTP client must centralize these mechanics rather than duplicating them in UI/service code.
