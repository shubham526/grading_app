# v2.3.4.1 Design Document
## Dual-Mode Grading Interface

**Project:** Rubric Grading Tool  
**Release:** v2.3.4.1  
**Status:** Design approved for implementation  
**Primary theme:** Separate Written/Text grading and Programming grading into purpose-built workspaces  
**Predecessor:** v2.3.3 — Programming Submission & Autograding  
**Successor:** v2.3.4.2 — Overleaf / LaTeX Project ZIP Ingestion  

---

## 1. Executive Summary

v2.3.3 introduced a complete programming-autograding backend and instructor workflow, but the feature was added into an application whose user interface was originally designed around written/manual grading.

The current application therefore has an architectural mismatch:

- the **Written/Text grading workflow** is the dominant application surface;
- **Programming Autograding** is exposed primarily under `Tools`;
- programming grading inherits UI concepts that are irrelevant to automated code grading, such as:
  - side-by-side written submission and rubric panes;
  - question-by-question vs student-by-student grading modes;
  - written evidence rendering;
  - manual rubric-centric navigation.

v2.3.4.1 introduces a **dual-mode application shell** with two explicit grading workspaces:

1. **Written / Text Grading**
2. **Programming Grading**

The user selects the grading mode when entering the application. The selected mode determines which workspace and controls are shown.

The release does **not** alter the underlying programming execution, scoring, provenance, persistence, or canonical submission architecture delivered in v2.3.3. It is primarily an application-shell and presentation-layer redesign.

The long-term architecture becomes:

```text
                         Grading App
                              │
                      Grading Mode Shell
                              │
              ┌───────────────┴────────────────┐
              │                                │
       Written / Text                    Programming
          Workspace                       Workspace
              │                                │
       PDF / LaTeX                      Python submissions
       rubric grading                   Docker sandbox
       question grading                 pytest
       evidence                         deterministic scoring
       similarity                       batch grading
       regrades                         immutable run history
              │                                │
              └───────────────┬────────────────┘
                              │
                         Shared Core
                              │
                   Canonical submissions
                   roster / assessment
                   evidence / provenance
                   settings / persistence
```

# 2. Motivation

## 2.1 Current Problem

Before v2.3.3, the application's interaction model was fundamentally:

> Open a written submission, inspect the student's answer, compare it with a rubric, assign scores/feedback, then navigate to another student or question.

This model is appropriate for:

- PDFs;
- typed written work;
- LaTeX assignments;
- scanned work;
- future Overleaf/LaTeX project submissions.

Programming grading has a different mental model:

> Inspect the state of the entire assignment, determine which submissions are ready, run automated grading, investigate failures or review-required runs, and manage reruns/history.

The programming workflow is therefore:

- assignment-centric;
- roster-centric;
- batch-oriented;
- status-oriented;
- test/result-oriented.

It is not naturally:

- document-centric;
- question-pane-centric;
- rubric-pane-centric.

Keeping Programming Autograding as a submenu under `Tools` makes a first-class grading workflow appear auxiliary.

---

## 2.2 Design Principle

The application should expose **different workspaces for fundamentally different grading tasks**, while sharing the same data and evidence infrastructure.

This avoids two undesirable alternatives:

### Alternative A — One giant adaptive UI

```python
if programming_mode:
    hide_written_widget_1()
    hide_written_widget_2()
    ...
```

This would produce:

- fragile mode conditionals throughout `MainWindow`;
- difficult testing;
- accidental cross-mode controls;
- increasing complexity as future features are added.

### Alternative B — Two separate applications

This would duplicate:

- settings;
- roster handling;
- canonical submissions;
- evidence storage;
- assessment state;
- release packaging;
- future Canvas integration.

v2.3.4.1 therefore uses a **single application shell with two workspace implementations**.

---

# 3. Goals

v2.3.4.1 MUST:

1. Introduce an explicit grading mode:
   - `WRITTEN`
   - `PROGRAMMING`

2. Present a mode-selection screen when appropriate at application startup.

3. Preserve the existing written grading experience with minimal behavioral change.

4. Provide a dedicated Programming Grading workspace.

5. Promote the important programming actions from a nested Tools submenu into visible top-level workspace actions.

6. Make Programming mode class/roster-centric rather than written-submission-centric.

7. Retain all v2.3.3 programming functionality:
   - configure autograder;
   - check runtime;
   - grade selected/current submission;
   - grade all eligible active submissions;
   - inspect results;
   - inspect immutable run history;
   - rerun submissions.

8. Allow switching grading modes without restarting the application.

9. Protect unsaved work and active background operations when switching modes.

10. Preserve shared application state where appropriate:
    - assessment;
    - roster;
    - canonical submission repository;
    - Grades + Evidence Folder;
    - settings.

11. Maintain Python 3.9 compatibility.

12. Introduce no regression to the existing written-grading workflow.

---

# 4. Non-Goals

v2.3.4.1 MUST NOT introduce:

- Overleaf / LaTeX ZIP ingestion;
- LaTeX project reconstruction;
- Canvas integration;
- LLM grading;
- code compilation beyond the existing v2.3.3 Python/Docker path;
- new autograding scoring rules;
- new Docker execution behavior;
- changes to immutable autograding run storage;
- automatic merging of programming grades into written/manual rubric scores;
- hybrid manual + automated programming grading;
- a second executable;
- a new database.

These belong to later releases.

# 7. Application Architecture

## 7.1 Target Structure

The current `MainWindow` should become an application shell rather than the direct owner of every grading widget.

Target architecture:

```text
MainWindow
│
├── shared application state
├── shared menu bar
├── shared status bar
├── shared settings
├── shared controllers/services
│
└── QStackedWidget / workspace host
    │
    ├── ModeSelectionPage
    │
    ├── WrittenGradingWorkspace
    │
    └── ProgrammingGradingWorkspace
```

Recommended internal responsibilities:

```text
MainWindow
    decides WHICH workspace is active

WrittenGradingWorkspace
    owns HOW written grading is presented

ProgrammingGradingWorkspace
    owns HOW programming grading is presented
```

---

## 7.2 Shared vs Mode-Specific State

### Shared state

The following should remain application-level where possible:

- Grades + Evidence Folder;
- current assessment identity;
- roster/student records;
- canonical `SubmissionRepository`;
- application settings;
- global version/release information;
- status/error reporting;
- persistent settings;
- future Canvas connection state.

### Written-only state

Examples:

- current written student;
- current question;
- student-by-student vs question-by-question mode;
- rendered written submission;
- rubric criterion selection;
- unsaved manual rubric edits;
- written evidence selection;
- similarity view state.

### Programming-only state

Examples:

- selected programming student(s);
- active autograder bundle;
- Docker runtime image;
- runtime availability state;
- programming roster table filters/selections;
- latest run summaries;
- batch progress;
- active worker;
- programming run history.

---

# 8. Grading Mode Domain

Introduce an explicit mode type.

Example conceptual API:

```python
class GradingMode(str, Enum):
    WRITTEN = "written"
    PROGRAMMING = "programming"
```

The application should never infer mode solely from whether a `.py` or `.pdf` file happens to be selected.

Mode selection is an explicit user/application state.

Reasons:

- an assessment may contain multiple artifact types;
- future hybrid workflows may exist;
- explicit state is easier to test;
- mode-specific actions should be deterministic.

---

# 9. MainWindow Responsibilities After Refactor

`MainWindow` should retain:

- window lifecycle;
- workspace hosting;
- shared menus;
- shared settings;
- mode transitions;
- application-level dialogs;
- shared repository/controller construction;
- status bar;
- application close behavior.

`MainWindow` should gradually stop directly owning:

- written-specific layout composition;
- programming-dashboard layout composition;
- written-only navigation widgets;
- programming-only table widgets.

This release does not need to make `MainWindow` perfectly minimal, but it should establish the architectural boundary.

# 10. Written Grading Workspace

## 10.1 Core Requirement

**Preserve existing behavior.**

The safest migration strategy is to wrap/extract the working written UI rather than redesign it.

The Written workspace continues to support the current application model:

```text
Written Assignment
─────────────────────────────────────────────────────────────

Navigation / grading mode

Submission                        Rubric / Grading
┌──────────────────────┐          ┌──────────────────────┐
│ PDF / LaTeX / text   │          │ Criteria             │
│ rendered evidence    │          │ Scores               │
│                      │          │ Feedback             │
│                      │          │ Evidence             │
└──────────────────────┘          └──────────────────────┘

student-by-student / question-by-question
save / previous / next
```

---

## 10.2 Written-Mode Features That Must Remain

v2.3.4.1 must preserve:

- rubric loading;
- roster loading;
- submission import;
- canonical submission history;
- written PDF rendering;
- existing LaTeX ingestion;
- parsed submission handling;
- manual scores;
- comments/feedback;
- question-centric grading;
- student-centric grading;
- save/resume;
- submission evidence;
- similarity review;
- existing regrade-related behavior;
- existing keyboard/menu shortcuts unless incompatible with new mode switching.

---

## 10.3 Written Workspace Extraction Strategy

Avoid a large simultaneous rewrite.

Recommended migration:

```text
Current MainWindow written widgets
        ↓
extract as cohesive workspace
        ↓
WrittenGradingWorkspace
```

The initial implementation may receive references to existing shared controllers rather than introducing new controller layers.

A technically imperfect but behavior-preserving extraction is preferable to a clean rewrite that risks grading regressions.

# 11. Programming Grading Workspace

## 11.1 Primary Mental Model

Programming mode should answer:

> What is the grading state of this programming assignment across the class?

It should not primarily answer:

> Which document am I currently reading?

The central programming surface is therefore a **roster/status dashboard**.

---

## 11.2 Proposed Programming UI

```text
Programming Assignment — <Assessment Name>
────────────────────────────────────────────────────────────────────

[ Configure Autograder ] [ Import Submissions ] [ Check Runtime ]
[ Grade Selected ]       [ Grade All ]          [ Run History ]

────────────────────────────────────────────────────────────────────

Summary
42 roster students • 39 submissions • 34 graded • 3 review • 2 pending

────────────────────────────────────────────────────────────────────

☐  Student             Attempt   Submission       Status       Score
────────────────────────────────────────────────────────────────────
☐  Alice Smith            1      Active           Completed    10 / 10
☐  Bob Jones              2      Active           Completed     7 / 10
☐  Carol Brown            1      Active           Review            —
☐  Dave Lee               1      Active           Not graded        —
☐  Eve Kim                —      Missing          Missing           —

────────────────────────────────────────────────────────────────────

────────────────────────────────────────────────────────────────────
```

---

## 11.3 Required Top Actions

The following v2.3.3 capabilities should become visible workspace buttons:

### Configure Autograder

Equivalent to current:

```text
Tools → Programming Autograding → Configure Autograder…
```

### Import Submissions

Uses the existing canonical submission import path.

Programming mode should make this action immediately visible because importing code submissions is a primary workflow.

### Check Runtime

Checks:

- Docker CLI;
- daemon;
- configured runtime image;
- expected pytest version.

The current runtime state should also have a visible indicator.

Example:

```text
Runtime: ✓ Ready
```

or:

```text
Runtime: ⚠ Not configured
```

### Grade Selected

Runs the selected student's active canonical programming attempt.

This replaces the conceptual prominence of "Grade Current Submission."

### Grade All

Launches the existing batch workflow.

### Run History

Opens programming autograding history.

# 12. Programming Student Table

## 12.1 Row Model

Each roster student should have one row.

Recommended columns:

| Column | Meaning |
|---|---|
| Select | Checkbox for selected grading operations |
| Student | Display name |
| Student ID | Stable ID, optionally hidden/configurable |
| Attempt | Active canonical attempt number |
| Submission | Active / Missing / Invalid |
| Status | Not graded / Running / Completed / Review / Error |
| Score | Latest complete score or `—` |
| Last Run | Timestamp of most recent persisted run |

Optional later columns:

- bundle ID/version;
- run duration;
- number of failed tests.

Do not overload v2.3.4.1 with excessive columns.

---

## 12.2 Status Definitions

### Missing

No active canonical programming submission.

### Not graded

Eligible active programming submission exists, but no persisted autograding run exists.

### Running

Current background worker is grading the student.

### Completed

Most recent persisted run has:

```text
requires_review = False
final_score != None
```

### Review

Most recent run requires instructor review.

### Error

Last requested grading operation failed before a valid persisted result could be produced.

---

# 13. Programming Selection Model

The Programming workspace should allow:

- single-row selection for detail panel;
- optional checkboxes for multi-student grading.

Recommended distinction:

```text

→ selected student for details/history

checkboxes
→ selected students for multi-grade action
```

If multi-select is not implemented in this release, `Grade Selected` may initially act on the current row only. The UI should not imply unsupported multi-selection.

# 15. Existing Programming Dialogs

v2.3.4.1 should reuse rather than rewrite:

- `AutogradingSetupDialog`
- `AutogradingResultsDialog`
- `AutogradingHistoryDialog`
- `AutogradingBatchDialog`

The Programming workspace becomes their primary launcher.

Where appropriate, small visual refinements are allowed, but major behavioral changes belong outside this release.

---

# 16. Programming Autograding Service

The existing Qt-free `AutogradingService` remains the authoritative application-level orchestration API.

It already composes:

```text
canonical submission
        ↓
ExecutionPlan
        ↓
DockerPytestExecutionBackend
        ↓
PytestRunResult
        ↓
deterministic scoring
        ↓
immutable run persistence
```

v2.3.4.1 SHOULD NOT duplicate this logic inside the new workspace.

The workspace may call:

- `list_bundles()`
- `runtime_availability()`
- `eligible_active_students()`
- `grade_submission()`
- `grade_batch()`
- `list_history()`
- `load_run()`

through worker/controller wrappers.

---

# 17. Threading and Background Execution

Programming Docker execution must remain off the GUI thread.

Continue to use:

```text
QThreadPool
    ↓
AutogradingWorker
```

The Programming workspace should receive progress through signals.

The workspace must never:

- block waiting synchronously for Docker;
- directly invoke long-running grading from a button handler;
- mutate Qt widgets from worker threads.

---

# 18. Active-Run UI State

While a current grading run is active:

- disable conflicting grade actions;
- show the current row as `Running`;
- show progress/status text;
- prevent destructive mode transitions.

For batch:

- continue using cooperative cancellation;
- do not abruptly terminate the active Docker container from the UI.

---

# 19. Mode Transition Rules

Mode switching is not merely visual. It must protect application state.

---

## 19.1 Written → Programming

Before switching:

1. Check for unsaved written grading changes.
2. If none:
   - switch immediately.
3. If unsaved:
   - use the application's existing save/discard/cancel behavior where possible.

Required choices:

```text
Save and Switch
Discard and Switch
Cancel
```

Do not silently discard manual scores.

---

## 19.2 Programming → Written

If no programming worker is active:

```text
switch immediately
```

If current or batch grading is active:

**Initial v2.3.4.1 policy: block mode switching.**

Display a clear message:

```text
Programming grading is currently running.
Wait for the current operation to finish or cancel the batch after
the current student before switching grading modes.
```

This is safer than trying to detach/reparent active worker UI state.

---

## 19.3 Application Close During Programming Run

Preserve existing safe shutdown expectations.

The application should not create a path that abandons an active Docker run without cleanup.

If current architecture already blocks or warns on active workers, retain that behavior.

If it does not, v2.3.4.1 should introduce a guard.

---

# 20. Shared Assessment State

The same assessment identity may remain loaded when switching modes.

However, the UI must not assume every assessment is suitable for both modes.

Example:

```text
Assessment: PS3

Written mode:
    no written artifacts available

Programming mode:
    42 Python submissions
```

This is acceptable.

The mode indicates the workflow, not an irreversible assessment type.

Future releases may introduce explicit assignment-type metadata, but v2.3.4.1 does not require it.

---

# 21. Startup Persistence Policy

Recommended behavior:

### First run / no saved preference

Show mode chooser.

### Subsequent launches

Preferred initial implementation:

**Still show the mode chooser**, but optionally visually emphasize the last-used mode.

Reason:

- the application is used across multiple assignments;
- automatically reopening Programming because it was used yesterday may be surprising when today the instructor intends to grade written work.

Possible setting for later:

```text
Remember my choice and open directly next time
```

If implemented, it must always be reversible from:

```text
File → Switch Grading Mode…
```

This preference is optional for v2.3.4.1.

Do not force one shared toolbar to contain controls from both grading paradigms.

```text

    written-specific toolbar/actions

```

Recommended order:

# 24. Programming Mode and Manual Rubrics

v2.3.4.1 preserves the v2.3.3 boundary:

> An autograding score does not silently become or overwrite the manual rubric score.

Programming mode therefore does not need the existing manual rubric grading pane.

If an assessment has a loaded rubric, Programming mode may retain that shared assessment metadata internally, but it should not present irrelevant rubric editing controls.

A future hybrid model may support:

```text
Automated tests: 80
Manual code-quality review: 20
```

but that is explicitly out of scope.

---

# 25. Programming Results and Hidden Tests

Instructor Programming mode may show full instructor-visible results, including hidden tests.

Student-safe redaction remains a reporting/export concern and must not be weakened.

The programming dashboard itself should avoid exposing unnecessary low-level hidden-test detail in the class roster table.

Appropriate table:

```text
Score: 7/10
Status: Completed
```

Full hidden details:

```text
View Results
```

---

# 26. Error Handling

Programming dashboard should translate backend conditions into actionable UI messages.

Examples:

### Runtime unavailable

```text
Docker grading runtime is not ready.
Configure Autograder or check the runtime before grading.
```

### No autograder selected

```text
No autograder bundle is configured for this assessment.
```

### Missing canonical submission

```text
This student has no active programming submission.
```

### Requires review

```text
The run completed but cannot be assigned an automatic final score.
Open Results for instructor review.
```

### Persistence integrity failure

```text
Historical autograding evidence failed integrity verification.
The stored run cannot be trusted or displayed as valid history.
```

Do not turn infrastructure errors into normal student failures.

---

# 27. Data Refresh Model

The Programming workspace requires a reliable refresh mechanism.

Recommended method:

```python
workspace.refresh()
```

which rebuilds row state from:

- current roster;
- canonical active attempts;
- persisted autograding history;
- current worker state.

Refresh after:

- entering Programming mode;
- loading/changing roster;
- importing submissions;
- grading completion;
- batch completion;
- autograder configuration changes;
- historical rerun completion.

Avoid maintaining a second independent source of truth in the table model.

---

# 28. Programming Dashboard Performance

For normal course sizes, reading persisted latest-run references should be inexpensive.

Do not load full immutable run diagnostics for every student during dashboard refresh.

Dashboard should use lightweight history references such as:

```text
AutogradingRunReference
```

Full run verification/loading occurs only when:

```text
View Results
View History → View Selected Run
```

This prevents dashboard refresh from repeatedly opening every full run directory.

---

# 29. Accessibility and Keyboard Behavior

New controls must:

- have text labels;
- have accessible names;
- support logical keyboard focus order;
- avoid status meaning conveyed only through color;
- include textual status such as:
  - Completed;
  - Review;
  - Missing;
  - Running.

Programming table status icons may supplement but not replace text.

---

# 30. Visual Design Guidance

Programming mode should feel visually lighter than the written grader.

Avoid:

- giant split panes;
- nested tab hierarchies;
- dense rubric controls;
- excessive modal dialogs for routine state.

Prefer:

- action bar;
- summary metrics;
- central roster table;
- compact selected-student detail panel.

The Programming workspace should communicate:

```text
assignment status
→ action
→ result
```

rather than:

```text
document
→ criterion
→ navigation
```

# 32. Compatibility Strategy

v2.3.4.1 is a UI refactor over a stable backend.

The following v2.3.3 components should require **no behavioral redesign**:

```text
src/autograding/
    bundle validation
    canonical programming adapter
    ExecutionPlan
    Docker backend
    structured pytest
    scoring
```

# 33. Migration Strategy

Do not replace the current UI in one commit.

Recommended sequence:

```text
Commit 1
Add mode domain + shell without moving written internals.

Commit 2
Extract WrittenGradingWorkspace while keeping behavior identical.

Commit 3
Add ProgrammingGradingWorkspace using v2.3.3 services.

Commit 4
Harden transitions, menus, state, refresh, background-operation rules.

Commit 5
Acceptance, documentation, version, release.
```

This keeps each commit reviewable and recoverable.

# 38. Risks

## Risk 1 — MainWindow Regression

The current `MainWindow` likely contains substantial written-specific behavior.

**Mitigation:**

- incremental extraction;
- no simultaneous written redesign;
- regression tests after every extraction step.

---

## Risk 2 — Duplicate State Ownership

Both MainWindow and workspaces could accidentally maintain competing current-student/current-assessment state.

**Mitigation:**

- identify authoritative state owner explicitly;
- workspaces query shared state rather than duplicating it;
- centralize refresh hooks.

---

## Risk 3 — Worker Lifecycle

Programming mode switching during active execution could orphan worker UI state.

**Mitigation:**

- block mode switching during active grading in v2.3.4.1;
- retain cooperative batch cancellation.

---

## Risk 4 — Overengineering

A full application-framework rewrite would unnecessarily endanger a working grader.

**Mitigation:**

- create only the abstraction needed for two workspaces;
- do not introduce a new event bus, dependency-injection framework, or data store.

# 40. Final Architectural Direction

After v2.3.4.1, the application should no longer conceptually be:

> A written grading app with programming autograding under Tools.

It should be:

> A grading application with two purpose-built grading workspaces backed by one shared evidence, submission, and persistence core.

The final conceptual model is:

```text
                        Grading App
                             │
                      Choose Workflow
                             │
             ┌───────────────┴───────────────┐
             │                               │
        Written / Text                  Programming
             │                               │
      Read + evaluate                  Execute + inspect
      student work                     class grading state
             │                               │
      rubric / questions               tests / scores / history
             │                               │
             └───────────────┬───────────────┘
                             │
                    Canonical Evidence Core
```

That architecture should be treated as the foundation for v2.3.4.2 and subsequent releases.
