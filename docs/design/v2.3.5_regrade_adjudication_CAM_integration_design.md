# v2.3.5 Design — Structured Regrade Adjudication & Course Automation Integration

**Release:** `v2.3.5 — Structured Regrade Adjudication & CAM Integration`
**Repository:** `grading_app`
**Status:** Definitive current design specification
**Date:** August 21, 2026
**Implementation baseline:** `v2.3.4.2`
**Depends on:** v2.3.2 Submission Core & Provenance Foundation, v2.3.3 autograding/`GradingRun` provenance, v2.3.4.1 shared Written/Programming assessment home, v2.3.4.2 canonical LaTeX-project submission provenance
**CAM counterpart:** CAM v0.7.0 regrade integration contracts; final Fall 2026 cross-machine deployment completed by CAM v0.7.1 + Grading App v2.3.6.1
**Direct Canvas dependency:** None
**Direct Microsoft dependency:** None
**Canvas publication owner:** Course Automation Manager
**Distributed relay implementation:** Deferred to v2.3.6.1

---

## 1. Purpose

v2.3.5 makes the grading app the **sole academic adjudication and grade-revision workspace for student-request-driven regrades**.

It preserves the existing Microsoft student-facing regrade workflow and integrates with Course Automation Manager (CAM) instead of duplicating Microsoft or Canvas integration logic.

The governing principle is:

> **A regrade is an auditable revision to academic grading evidence. It is not a Canvas operation and it is not a late-day decision.**

The grading app owns:

> **What raw score and feedback did the student earn after review?**

It does not own:

> **What score should ultimately be published in Canvas after authoritative course-policy adjustments are respected?**

That operational publication question remains CAM's responsibility.

---

## 2. Scope Decision

v2.3.5 is intentionally limited to **student-request-driven regrade adjudication**.

The following are explicitly deferred:

```text
normal first-time grade publication
distributed Linux relay synchronization
instructor-initiated systematic corrections
multi-student correction batches
direct Canvas synchronization
Canvas submission downloading
full Canvas reconciliation
```

Normal first-time grade publication and the distributed relay are implemented in the v2.3.6 family.

Systematic corrections remain a later dedicated feature.

---

## 3. Current Architecture

### 3.1 Logical application contract

v2.3.5 itself operates against a local versioned filesystem integration endpoint:

```text
Course Automation Manager
        ↓
local versioned JSON bridge
        ↓
Grading App
        ↓
local versioned JSON bridge
        ↓
Course Automation Manager
```

The academic regrade engine must not know whether those local bridge files later cross machines.

### 3.2 Final Fall 2026 deployment

The intended deployed topology after v2.3.6.1 is:

```text
INSTRUCTOR MAC

Microsoft / OneDrive
        ↕
       CAM
        ↕
CAM local bridge
        ↕
──────────────────────────────
SHARED UNIVERSITY LINUX SERVER
durable relay mailbox
──────────────────────────────
        ↕
Grading App local bridge
        ↕
   Grading App

TA MAC
```

v2.3.5 must therefore be **relay-ready but relay-agnostic**.

It may only read/write its own local integration endpoint.

SSH, rsync, Linux relay configuration, relay health, and cross-machine synchronization are **not part of v2.3.5**. They are added by v2.3.6.1 without changing the regrade domain contract.

## 4. Final Responsibility Boundary

```text
Student
  ↓
Microsoft Form
  ↓
Power Automate
  ↓
SharePoint Regrade Request / Window Lists
  ↓
Course Automation Manager
  - receives normalized workflow event
  - resolves Canvas identity/context
  - enriches request
  - emits regrade_request_delivery
  ↓
local grading integration endpoint
  ↓
Grading App
  - maps exact local grading evidence
  - binds exact submission / attempt
  - snapshots original grade and feedback
  - performs academic adjudication
  - revises raw earned score / feedback
  - creates immutable GradeRevision
  - creates ApprovedGradeChange when raw total changes
  - emits regrade_decision
  ↓
local grading integration endpoint
  ↓
Course Automation Manager
  - validates academic handoff
  - synchronizes student-safe decision to Microsoft
  - resolves authoritative late-policy context
  - plans/publishes to Canvas if required
  - rereads/verifies Canvas
  - emits grade_publication_result
  ↓
Grading App
  - records operational publication closure
```

After v2.3.6.1, only the transport between the two local integration endpoints changes.

## 6. Goals

v2.3.5 shall support:

1. regrade inbox synchronization through a narrow CAM adapter;
2. exact CAM schema validation;
3. stable local regrade case IDs;
4. request lineage using `external_request_id + external_version`;
5. student, assessment, submission, attempt, question, and criterion linkage;
6. immutable original-grade snapshots;
7. exact original-submission access during review;
8. approve / partially approve / deny;
9. explicit score increases/decreases under local grading policy;
10. feedback revision;
11. append-only regrade audit history;
12. immutable `GradeRevision` records;
13. question-centric grading integration;
14. programming `GradingRun` provenance where relevant;
15. student-safe external decision/note output;
16. raw-score `ApprovedGradeChange` records independent of Canvas;
17. durable local outbound decision transport;
18. automatic handoff of resolved decisions to CAM's local integration endpoint;
19. publication-status feedback from CAM;
20. idempotent replay-safe synchronization;
21. external-version, case-version, grading-record, decision, and reviewer-concurrency conflict detection;
22. CAM deep-link support into the matching regrade case;
23. exportable request/change/audit reporting;
24. local academic correctness even when CAM is unavailable.

---

## 7. Non-Goals

v2.3.5 shall not:

- replace Microsoft Forms;
- replace SharePoint;
- replace Power Automate;
- send duplicate student status emails;
- calculate regrade-window timeliness;
- manage absences;
- manage late-day accounting;
- decide whether late days cover a submission;
- calculate/apply/waive/remove/reverse-engineer a late penalty;
- call Canvas directly;
- store a Canvas API token;
- implement Canvas assignment mappings;
- write Canvas grades;
- implement Canvas write retries/conflict recovery;
- implement normal first-time grade publication;
- implement distributed SSH/rsync transport;
- access the Linux relay directly;
- synchronize another endpoint's `processed`, `quarantine`, staging, or claim state;
- implement systematic/batch corrections;
- make CAM availability part of the local academic transaction;
- import CAM source code or use CAM's internal state database.

```text
CourseAutomationRegradeAdapter   Production/local integration endpoint
```

```text

SSH logic
rsync logic

```

## 9. CAM Contracts Are External Contracts

CAM schema payloads are strict cross-application contracts.

v2.3.5 mirrors:

```text
RegradeRequestDelivery
RegradeCaseAcknowledgement
ApprovedGradeChange
RegradeDecision
GradePublicationResult
```

Rules:

- explicit schema version;
- exact event type;
- exact producer where required;
- required fields remain required;
- timezone-aware timestamps;
- invalid score ranges rejected;
- unsupported future schema versions fail closed;
- exact replay is idempotent;
- same logical identity/version with conflicting content is a conflict;
- no guessed aliases.

The existing CAM v0.7 regrade publication-result contract remains the v2.3.5 authority.

The v2.3.6.2 normal-grade publication contract is a separate later contract and must not retroactively distort the regrade objects.

## 10. Local Integration Endpoint

Default local root:

```text
~/Library/Application Support/CourseAutomationIntegration/regrades/
    to-grading/
    from-grading/
    processed/
    quarantine/
    .staging/
    .event-claims/
```

Ownership:

```text
CAM writes:
    to-grading/

Grading App consumes:
    to-grading/

Grading App writes:
    from-grading/

CAM consumes:
    from-grading/
```

Safety:

- complete JSON written to staging first;
- final appearance atomic;
- stable logical event IDs;
- idempotent replay;
- malformed events quarantined;
- processed events archived locally;
- no raw student submission artifacts transported;
- no secrets transported;
- claim/staging state remains local to each application.

v2.3.6.1 later synchronizes only finalized transport messages between this local endpoint and the Linux relay.

## 11. Durable Local Outbox and Academic Transaction Boundary

The grading app's academic correctness must **not depend on CAM availability, relay availability, or network availability**.

When the reviewer clicks `Resolve`, persist locally first:

```text
GradeRevision
ApprovedGradeChange, if needed
RegradeDecision
updated RegradeCase
append-only audit events
durable outbound event/outbox record
```

Only after that transaction succeeds should delivery be attempted.

If delivery cannot occur:

```text
Academic decision = RESOLVED
Decision transport = PENDING
```

Suggested transport states:

```text
PENDING
DELIVERED_TO_LOCAL_BRIDGE
TRANSPORT_ERROR
```

After v2.3.6.1, additional relay transport state may be displayed separately, but the academic transaction remains unchanged.

`DELIVERED_TO_LOCAL_BRIDGE` never means CAM processed the event or Canvas changed.

## 12. Inbound `regrade_request_delivery`

CAM delivers a normalized request.

Logical identity:

```text
external_request_id + external_version
```

Required categories of data:

```text
schema/event identity
course
external request identity/version
intake timestamp/timeliness/status
student identity
workflow assessment label
student request text/type
question/criterion references when present
Canvas context observed by CAM
```

Canvas context is correlation/operational context only.

## 13. Canvas Context Is Informational

Example:

```text
ACADEMIC GRADE — authoritative in Grading App
Raw assessment score: 80 / 100

CANVAS CONTEXT — informational
Published Canvas score: 64 / 100
Canvas late: Yes
Canvas attempt: 1
```

A difference such as:

```text
Grading App raw = 80
Canvas published = 64
```

is not automatically a conflict.

The grading app never reverse-engineers policy from that difference.

Its regrade output remains:

```text
old_raw_score = 80
new_raw_score = 90
```

CAM + authoritative policy state determine the published target.



## 20. Regrade Acknowledgement

After first durable ingestion, emit the exact CAM-compatible acknowledgement.

Requirements:

- stable event identity;
- correlation to external request and local case;
- monotonic case version;
- exact replay no-op;
- conflicting same-version body fails closed.

Acknowledgement means:

> The grading app durably ingested the request.

It does not mean review is complete.

## 27. Academic Decision Transaction

Resolving a case must atomically:

1. validate case concurrency;
2. validate grading-record concurrency;
3. preserve immutable original snapshot;
4. apply question/criterion changes;
5. update current academic grading record;
6. create immutable `GradeRevision`;
7. create `ApprovedGradeChange` only if raw total changed;
8. create immutable `RegradeDecision`;
9. append audit events;
10. queue durable outbound integration event;
11. mark academic case resolved.

Transport happens after the local transaction.

## 28. Score Decrease Policy

Per course/assessment:

```text
allow_score_decrease = true | false
```

Rules:

- opening a regrade never changes score;
- decreases require explicit reviewer action;
- prohibited decreases are blocked;
- permitted decreases require confirmation;
- every decrease is auditable.

## 31. Regrade / Late-Day Separation

Invariant:

> **The grading app changes only raw academic state. Regrade resolution never creates, removes, recalculates, or waives late-day entitlement.**

Example:

```text
Before:
Raw academic = 80
Canvas published = 64
Settled penalty = 20%

Regrade:
Raw academic 80 → 90

Grading App emits:
old_raw_score = 80
new_raw_score = 90

CAM:
90 adjusted by authoritative existing policy → target 72
```

Never emit `64 → 72` as the academic change.

## 35. Publication Result Never Mutates Academic Truth

Valid state:

```text
ACADEMIC
Partially Approved
Raw 80 → 90
Resolved

PUBLICATION
Conflict

```

Publication conflict does not:

- roll back `GradeRevision`;
- delete `ApprovedGradeChange`;
- reopen the academic decision automatically;
- restore the old raw score;
- mutate the original snapshot.

Academic and operational histories remain separate.

## 38. Idempotency

Repeated synchronization must not duplicate:

- cases;
- child review items;
- acknowledgements;
- decisions;
- revisions;
- `ApprovedGradeChange`;
- outbound events;
- publication-result application.

Stable identities include:

```text
external_request_id + external_version
regrade_case_id
regrade_case_id + case_version
regrade_case_id + decision_version
approved_grade_change_id
publication result event_id / command_id
```

Exact replay is a no-op.

Conflicting replay is a conflict.

## 39. Conflict Handling

### External request advanced

Block silent overwrite and require reconciliation.

### Grading record advanced

If `grading_record_version` changes after review begins:

```text
block Resolve
preserve snapshot
refresh/reconcile
```

### Submission attempt mismatch

Block adjudication rather than guess.

### Publication conflict

Display operational failure without changing academic decision.

---

## 40. Reviewer Concurrency

Optimistic concurrency:

```text
Reviewer A loads case_version N
Reviewer B loads case_version N

A saves → N+1
B attempts save against N
→ blocked
→ refresh required
```

The same principle applies to `grading_record_version` at final resolution.
