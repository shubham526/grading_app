# v2.3.0 — Submission Similarity Review

## Release Summary

**Version:** `v2.3.0`  
**Release title:** **Submission Similarity Review**

v2.3.0 adds a deterministic, instructor-facing submission similarity review workflow to the grading application.

The release is designed to help instructors identify unusual textual overlap across student submissions for manual review. It does **not** determine whether plagiarism, cheating, or academic misconduct occurred.

The feature extends the v2.2.x submission-ingestion workflow and reuses the existing extracted student/question evidence rather than reimplementing LaTeX or PDF parsing.

---

## What This Release Adds

v2.3.0 introduces:

- exact source-file hash comparison;
- normalized answer-text hash comparison;
- question-level n-gram similarity;
- deterministic pairwise comparison across all students;
- configurable similarity thresholds;
- short-answer handling;
- side-by-side pair review;
- shared-text phrase display;
- sortable similarity results;
- JSON, CSV, matrix CSV, and standalone HTML exports;
- multiple submission-source modes;
- an instructor-facing Similarity Review dialog under the **Tools** menu.

All similarity computations are deterministic and can run fully offline.

---

# Similarity Methods

## 1. Exact File Hash

The strongest deterministic signal is an exact SHA-256 match of the original logical submission source.

Example:

```text
Alice main.tex SHA256 == Bob main.tex SHA256
→ Exact file match
```

Compiled PDFs are not treated as equivalent original source files for this signal.

An exact source-file match is reported as the strongest similarity level.

---

## 2. Normalized Text Hash

Student answer text is normalized and then hashed.

Normalization removes superficial differences while preserving substantive text structure.

Examples of differences that may be normalized include:

- capitalization;
- whitespace;
- selected LaTeX formatting;
- comments;
- selected template/preamble material;
- punctuation-level variation.

A normalized-text match can therefore detect effectively identical answers even when the raw source files are not byte-identical.

---

## 3. Question-Level N-Gram Similarity

The primary approximate-overlap signal is token n-gram Jaccard similarity.

Default behavior:

```text
normal answers:
    5-token shingles

very short answers:
    3-token shingles when appropriate
```

For each matching question ID:

```text
Jaccard(A, B)
=
|shared shingles|
/
|union of shingles|
```

The comparison is performed question by question.

The strongest question-level signal contributes to the pair's overall result.

---

# Default Similarity Thresholds

The default v2.3.0 thresholds are:

```text
Low:     0.50
Medium:  0.65
High:    0.80
Exact:   0.95
```

The instructor may change these values in the Similarity Review dialog.

The thresholds must remain ordered and valid.

---

# Short-Answer Handling

Very short answers can produce misleadingly high token-overlap values.

v2.3.0 therefore treats answers with fewer than approximately 30 tokens conservatively.

For short answers:

- n-gram evidence may be downgraded by one flag level;
- raw exact-file matches are never downgraded;
- normalized-text matches remain strong evidence;
- warnings are surfaced to the instructor where appropriate.

This behavior reduces over-flagging of brief standard answers.

---

# Pairwise Report Model

For an assignment with `N` students, the application evaluates each unique unordered pair once.

Example:

```text
10 students
→ 45 unique pairs
```

The report stores, for each pair:

- student A;
- student B;
- overall score;
- flag level;
- most similar question;
- exact-file-match status;
- normalized-text-match status;
- question-level n-gram scores;
- shared text spans;
- signal details;
- notes and warnings.

Pairs are deterministically sorted for reproducible output.

---

# Shared-Text Review

For question-level overlap, v2.3.0 identifies shared normalized phrases derived from matching shingles.

The Pair Similarity Detail dialog presents:

- Student A's answer;
- Student B's answer;
- question-level similarity;
- shared phrases;
- pair-level signals;
- warnings.

Shared phrases are intended to make the reason for a similarity score inspectable rather than presenting an unexplained number.

---

# Submission Sources

The Similarity Review dialog supports three source modes.

## Use Loaded Submissions

Uses the submissions already loaded in the grading workspace.

This is the preferred mode when the instructor is actively grading an assignment.

## Choose Submissions Folder

Loads a v2.2-compatible submissions folder directly.

The existing v2.2 submission parser is reused.

## Choose Assessment Folder

Loads saved assessment JSON files and associated persisted submission evidence when available.

If persisted evidence cannot be read, the application can fall back to the submission evidence stored inside the saved assessment when sufficient evidence exists.

Malformed or unusable assessment files are reported as warnings rather than crashing the review.

# Pair Similarity Detail UI

The Pair Similarity Detail dialog was refined during acceptance testing to avoid fixed-height panes.

Its layout uses nested resizable splitters.

The instructor can resize:

- Student A vs. Student B answer panes horizontally;
- answer area vs. shared-phrase area vertically;
- question tabs vs. pair-signal area vertically;
- pair-signal area vs. warnings vertically;
- the entire dialog window.

Pair signals are displayed as readable sections rather than compressed internal/debug strings.

Example:

```text

  Match: Yes
  File type: latex
  SHA256: ...

Normalized text hash
  Match: Yes

  Q1: 1.0000
```

# Warning Handling

Source problems are non-fatal where possible.

Examples include:

```text
persisted_evidence_unavailable
assessment_file_unreadable
assessment_missing_submission_evidence
```

The application reports these issues to the instructor and continues with usable submissions.

This makes the review robust to partially incomplete assessment folders.

# Known Limitations

v2.3.0 intentionally focuses on textual overlap.

It does not attempt to detect:

- semantic paraphrases with low lexical overlap;
- algorithmically equivalent pseudocode after extensive variable renaming;
- groups/clusters of related submissions;
- recurring pair patterns across multiple assignments;
- misconduct intent.

Those capabilities are intentionally deferred to later releases.

In particular, semantic embeddings, pseudocode-structure similarity, clustering, and cross-assignment trends belong to the planned **v2.3.1 — Advanced Similarity Review** release.
